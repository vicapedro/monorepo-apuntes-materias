# 3.1 Protocolos de Administración de Red

## Descripción

Los **protocolos de administración de red** son estándares que permiten **recopilar información** de dispositivos de red (routers, switches, servidores, impresoras) de forma centralizada y automatizada. Sin estos protocolos, el administrador tendría que conectarse manualmente a cada dispositivo para obtener métricas, configuraciones y estado.

**Problema sin protocolos de administración:**
```
Administrador necesita saber uso de CPU de 50 routers
→ SSH a router 1, ejecutar "show processes cpu"
→ SSH a router 2, ejecutar "show processes cpu"
→ ... (repetir 48 veces más)
→ Tiempo invertido: 2-3 horas
→ Imposible monitorear en tiempo real
```

**Solución con protocolos de administración:**
```
Sistema de monitoreo consulta vía SNMP a los 50 routers cada 30 segundos
→ Datos recopilados automáticamente
→ Gráficas históricas generadas
→ Alertas si CPU >80%
→ Dashboard en tiempo real
→ Tiempo del administrador: 0 (automatizado)
```

## Protocolos Principales

### 1. SNMP (Simple Network Management Protocol)

**Puerto:** UDP 161 (queries), UDP 162 (traps)  
**RFC:** 1157 (SNMPv1), 1901-1908 (SNMPv2), 3410-3418 (SNMPv3)

SNMP es el **estándar de facto** para monitoreo de dispositivos de red. Permite:
- ✅ Leer valores (GET): CPU, RAM, interfaces, uptime
- ✅ Modificar configuración (SET): Cambiar configuración remotamente
- ✅ Recibir notificaciones (TRAP): Alertas cuando ocurren eventos

#### Arquitectura SNMP

```

│              Network Management System                           │
│  - Prometheus                                                    │

│  - PRTG                                                          │
│  - Nagios                                                        │

               │ (Polling)            │ (Traps)
               │                      │

┌──────────────────────────────────────┼───────────────────────────┐
│           SNMP Agents                │                           │
│                                      │                           │
│  ┌─────────────┐  ┌─────────────┐  ┌┴────────────┐             │
│  │   Router    │  │   Switch    │  │   Servidor  │             │
│  │  SNMP Agent │  │  SNMP Agent │  │  snmpd      │             │
│  │  Puerto 161 │  │  Puerto 161 │  │  Puerto 161 │             │
```

#### Versiones de SNMP

| Versión | Año | Seguridad | Autenticación | Cifrado | Uso |
|---------|-----|-----------|---------------|---------|-----|
| **SNMPv1** | 1988 | ❌ Ninguna | Community string (plaintext) | ❌ No | ⚠️ Legacy |
| **SNMPv2c** | 1993 | ❌ Ninguna | Community string (plaintext) | ❌ No | ✅ Común |
| **SNMPv3** | 1998 | ✅ Sí | User-based (username/password) | ✅ DES/AES | ✅ Recomendado |

**Community String**: Contraseña compartida (como "public" para lectura, "private" para escritura)

**⚠️ ADVERTENCIA SNMPv1/v2c:**
```bash
# Community string viaja en texto plano
# Captura con tcpdump muestra:
tcpdump -A -i eth0 port 161

# Output:
# ...community...public...sysDescr...
#     ↑ Contraseña visible ❌
```

#### MIB (Management Information Base)

MIB es una **base de datos jerárquica** que define qué información puede ser consultada en un dispositivo.

**Estructura de OID (Object Identifier):**

```
                    │             │

                 dod(6)

                internet(1)
                    │
        ┌───────────┼───────────┬────────────┐
        │           │           │            │

        │           │
     mib-2(1)   enterprises(1)
        │           │

    │

              │ │ │ │ │ │ │ └─ sysDescr
```

| .1.3.6.1.2.1.2.2.1.5 | ifSpeed | Velocidad de interfaz (bps) |

**Ejemplo de consulta SNMP:**

```bash
# Obtener descripción del sistema
snmpget -v2c -c public 192.168.1.1 .1.3.6.1.2.1.1.1.0

# Output:
# SNMPv2-MIB::sysDescr.0 = STRING: Linux router 5.15.0-56-generic #62-Ubuntu SMP x86_64

# Obtener tabla de interfaces
snmpwalk -v2c -c public 192.168.1.1 .1.3.6.1.2.1.2.2.1.2

# Output:
# IF-MIB::ifDescr.1 = STRING: lo
# IF-MIB::ifDescr.2 = STRING: eth0
# IF-MIB::ifDescr.3 = STRING: wlan0
```

#### Operaciones SNMP

**1. GET** - Obtener valor de un OID específico

```bash
snmpget -v2c -c public 192.168.1.1 sysUpTime.0

# Respuesta:
# DISMAN-EVENT-MIB::sysUpTimeInstance = Timeticks: (123456789) 14 days, 6:56:07.89
```

**2. GETNEXT** - Obtener siguiente OID en el árbol

```bash
snmpgetnext -v2c -c public 192.168.1.1 system

# Devuelve el primer OID dentro del subárbol "system"
```

**3. GETBULK** - Obtener múltiples OIDs (más eficiente que GETNEXT repetido)

```bash
snmpbulkget -v2c -c public -Cn0 -Cr10 192.168.1.1 ifDescr

# -Cn0: No-repeaters (0 = ninguno)
# -Cr10: Max-repetitions (obtener 10 OIDs)
```

**4. WALK** - Recorrer todo un subárbol

```bash
# Obtener TODAS las interfaces
snmpwalk -v2c -c public 192.168.1.1 interfaces

# Devuelve cientos de OIDs: ifDescr, ifSpeed, ifInOctets, etc.
```

**5. SET** - Modificar valor (requiere community de escritura)

```bash
# Cambiar sysLocation
snmpset -v2c -c private 192.168.1.1 sysLocation.0 s "Datacenter Piso 3"

# -c private: Community de escritura
# s: Tipo STRING
# Otros tipos: i (integer), u (unsigned), t (timeticks), a (IP address)
```

**6. TRAP/INFORM** - Notificaciones asíncronas del agente al manager

```
Dispositivo detecta evento crítico:
- Interface caída
- Temperatura alta
- Login fallido
- Energía perdida

→ Envía TRAP a NMS inmediatamente (sin esperar polling)
→ NMS recibe alerta en tiempo real
```

**Diferencia TRAP vs INFORM:**
- **TRAP**: Fire-and-forget (UDP, no confirmación)
- **INFORM**: Requiere ACK del NMS (más confiable, más overhead)

#### Configuración de SNMP en Linux

**Instalar net-snmp:**

```bash
# Ubuntu/Debian
sudo apt install snmpd snmp -y

# Rocky Linux
sudo dnf install net-snmp net-snmp-utils -y
```

**Configurar snmpd (agente):**

```bash
sudo nano /etc/snmp/snmpd.conf
```

**Configuración básica (SNMPv2c):**

```conf
# /etc/snmp/snmpd.conf

# Community de solo lectura
rocommunity public localhost
rocommunity public 192.168.1.0/24

# Community de escritura (CUIDADO)
rwcommunity private localhost

# Información del sistema
syslocation "Datacenter - Rack 42"
syscontact Admin <admin@ejemplo.com>

# Escuchar en todas las interfaces
agentaddress udp:161

# Deshabilitar com2sec por defecto (seguridad)
# com2sec notConfigUser  default       public

# Habilitar acceso a todo el árbol MIB
view    systemview    included   .1

# Logs
dlmod cmaX /usr/lib/x86_64-linux-gnu/libnetsnmpmibs.so
```

**Configuración segura (SNMPv3):**

```bash
# Crear usuario SNMPv3
sudo net-snmp-create-v3-user -ro -A authpassword -X privpassword -a SHA -x AES snmpuser

# Esto crea entrada en /var/lib/snmp/snmpd.conf:
# createUser snmpuser SHA "authpassword" AES "privpassword"
```

```conf
# /etc/snmp/snmpd.conf - SNMPv3

# Escuchar en UDP 161
agentaddress udp:161

# Definir vista (qué OIDs puede ver)
view systemview included .1

# Grupo con acceso de lectura
rouser snmpuser authPriv -V systemview

# syslocation y syscontact
syslocation "Datacenter Principal"
syscontact "NOC <noc@ejemplo.com>"
```

**Iniciar servicio:**

```bash
# Iniciar snmpd
sudo systemctl enable snmpd --now

# Verificar que escucha en puerto 161
sudo ss -ulnp | grep 161

# Firewall (Rocky Linux)
sudo firewall-cmd --permanent --add-port=161/udp
sudo firewall-cmd --reload
```

**Probar SNMP localmente:**

```bash
# SNMPv2c
snmpwalk -v2c -c public localhost system

# SNMPv3
snmpget -v3 -l authPriv -u snmpuser -a SHA -A authpassword -x AES -X privpassword localhost sysDescr.0
```

**Usar snmp_exporter:**

```yaml

  - job_name: 'snmp'
    static_configs:
      - targets:
        - 192.168.1.1  # Router

```

**PromQL queries útiles:**


### 2. NetFlow / sFlow / IPFIX

**Propósito:** Análisis de **flujos de red** (quién habla con quién, cuánto tráfico, qué aplicación).

Un **flujo** es una secuencia de paquetes con mismas características:
- IP origen
- IP destino
- Puerto origen
- Puerto destino
- Protocolo (TCP/UDP)

#### NetFlow (Cisco)

**Versiones:**
- **NetFlow v5**: Antigua, limitada (solo IPv4, no VLAN tags)
- **NetFlow v9**: Flexible, templates, extensible
- **IPFIX**: Estándar IETF (RFC 7011) basado en NetFlow v9

**Arquitectura:**

```
┌─────────────────────────────────────────────────────────────────┐
│                    Router / Switch                               │
│                                                                   │
│  ┌──────────────┐                                                │
│  │  Traffic     │   Analiza paquetes que pasan                   │
│  │  Passing     │   Identifica flujos                            │
│  └──────┬───────┘                                                │
│         │                                                         │
│         ▼                                                         │
│  ┌──────────────┐                                                │
│  │ NetFlow      │   Agrega flujos                                │
│  │ Cache        │   Mantiene contadores                          │
│  └──────┬───────┘                                                │
│         │                                                         │
│         │ Exporta cada X segundos o cuando cache llena           │
│         │                                                         │
│         ▼                                                         │
│  ┌──────────────┐                                                │
│  │ NetFlow      │   Envía registros UDP                          │
│  │ Exporter     │   Puerto 2055 (NetFlow)                        │
│  └──────┬───────┘   Puerto 6343 (sFlow)                          │
└─────────┼─────────────────────────────────────────────────────────┘
          │
          │ UDP
          │
          ▼
┌─────────────────────────────────────────────────────────────────┐
│              NetFlow Collector                                   │
│  - nfdump                                                        │
│  - ntopng                                                        │
│  - ElastiFlow                                                    │
│  - pmacct                                                        │
│                                                                   │
│  Almacena flujos históricos                                      │
│  Genera reportes:                                                │
│  - Top talkers (quién usa más bandwidth)                         │
│  - Top protocols (HTTP, SSH, P2P)                                │
│  - Top conversations (pares IP origen-destino)                   │
│  - Análisis de anomalías (DDoS, escaneos)                        │
└───────────────────────────────────────────────────────────────────┘
```

#### sFlow (InMon)

**Diferencia con NetFlow:**
- **NetFlow**: Analiza TODOS los paquetes (CPU intensivo)
- **sFlow**: Muestreo estadístico (1 de cada N paquetes, menor overhead)

**Uso típico:**
- sFlow: Switches de alto throughput (10G, 40G, 100G)
- NetFlow: Routers, análisis forense detallado

#### Analizar NetFlow con nfdump

**Instalar nfdump:**

```bash
sudo apt install nfdump -y
```

**Recolectar flujos:**

```bash
# Iniciar collector

# -w: Actualizar archivo cada 5 minutos

# -l: Directorio de almacenamiento

```

**Analizar flujos:**

```bash
# Top 10 IPs que más tráfico generan
nfdump -R /var/cache/nfdump -s srcip -n 10

# Output:
# Top 10 Source IP Addresses:
# 192.168.1.50    1.2 GB
# 192.168.1.100   850 MB
# 192.168.1.25    600 MB

# Tráfico de una IP específica
nfdump -R /var/cache/nfdump 'src ip 192.168.1.50'

# Flujos mayores a 1MB
nfdump -R /var/cache/nfdump 'bytes > 1000000'
```

### 3. IPFIX (IP Flow Information Export)

**RFC:** 7011  
**Puerto:** UDP 4739

IPFIX es el **estándar IETF** sucesor de NetFlow v9. Funcionalidad casi idéntica, pero:
- ✅ Protocolo estandarizado (no propietario de Cisco)
- ✅ Soporta SCTP (además de UDP/TCP)
- ✅ Templates más flexibles

**Soporte:**
- Cisco, Juniper, Huawei (mayoría de vendors)
- Wireshark (decodifica IPFIX)
- Collectores: nfcapd, pmacct, Elastic Flow

## Comparación de Protocolos

| Característica | SNMP | NetFlow/IPFIX | sFlow |
|----------------|------|---------------|-------|
| **Propósito** | Estado de dispositivo | Análisis de flujos | Análisis de flujos |
| **Overhead** | Bajo (polling periódico) | Medio (todos los flujos) | Bajo (muestreo) |
| **Granularidad** | Agregado (total de interfaz) | Por flujo (5-tuple) | Por paquete (muestreado) |
| **Vendors** | Universal | Cisco, Juniper, otros | HP, Arista, otros |
| **Datos** | Contadores, estado | Flujos IP | Paquetes raw muestreados |
| **CPU en dispositivo** | Bajo | Alto | Bajo |
| **Casos de uso** | Uptime, CPU, RAM, tráfico total | Detección DDoS, top talkers | Switches 10G+ |
| **Puerto** | UDP 161/162 | UDP 2055 | UDP 6343 |

## Casos de Uso Prácticos

### Caso 1: Identificar usuario que consume todo el ancho de banda

**Problema:** Internet lento en oficina

**Con SNMP:**
```bash
# Ver tráfico total de interfaz WAN
snmpget -v2c -c public router ifHCInOctets.2
# → 95 Mbps de 100 Mbps (95% saturación)
# Pero NO sabemos QUIÉN lo está usando ❌
```

**Con NetFlow:**
```bash
# Top talkers
nfdump -R /var/cache/nfdump -s srcip -n 10
# → 192.168.1.77: 85 Mbps ✅ (encontrado)

# Qué está descargando
nfdump -R /var/cache/nfdump 'src ip 192.168.1.77' -s dstport
# → Puerto 51413 (BitTorrent) ✅

# Solución: Bloquear P2P en firewall o QoS
```

### Caso 2: Detectar escaneo de red (port scan)

**Con NetFlow:**
```bash
# Flujos con muchos puertos destino diferentes
nfdump -R /var/cache/nfdump -s srcip/dstport -n 100 | grep "192.168.1"

# IP 192.168.1.88 contacta puertos 1-65535 en múltiples hosts
# → Nmap scan detectado ✅

# Ver detalles
nfdump -R /var/cache/nfdump 'src ip 192.168.1.88'
```

### Caso 3: Análisis forense de brecha de seguridad

**Pregunta:** ¿Qué datos fueron exfiltrados?

**Con NetFlow histórico:**
```bash
# Flujos salientes de servidor comprometido en ventana de tiempo
nfdump -R /var/cache/nfdump -T \
  'src ip 192.168.1.200 and dst net not 192.168.0.0/16' \
  -t 2026/04/01.14:00:00-2026/04/01.16:00:00

# Detecta:
# - 500 MB enviados a IP en Rusia (datos exfiltrados) ✅
# - Puerto destino 443 (HTTPS, difícil de detectar en firewall)
# - Duración: 45 minutos

# Respuesta a incidente:
# - Bloquear IP atacante
# - Analizar logs de servidor
# - Identificar vulnerabilidad explotada
```

### Caso 4: Monitoreo de SLA (Service Level Agreement)

**Requerimiento:** Web debe estar disponible >99.9%

**Con SNMP + Prometheus:**

```yaml
# prometheus.yml - Blackbox exporter
- job_name: 'web-sla'
  metrics_path: /probe
  params:
    module: [http_2xx]
  static_configs:
    - targets:
      - https://app.ejemplo.com
  relabel_configs:
    - source_labels: [__address__]
      target_label: __param_target
    - target_label: __address__
      replacement: blackbox-exporter:9115
```

```promql
# Uptime percentage últimos 30 días
avg_over_time(probe_success[30d]) * 100

# Alerta si uptime <99.9%
```

**Dashboard de Grafana:**
- SLA actual: 99.95% ✅
- Downtime total: 21 minutos (objetivo: <43 minutos/mes)
- Incidentes: 3 (detalles en logs)

## Mejores Prácticas

### Seguridad

1. **Usar SNMPv3** en producción
   - ❌ SNMPv1/v2c: Community strings en plaintext
   - ✅ SNMPv3: Autenticación + cifrado (authPriv)

2. **Limitar acceso SNMP**
   ```conf
   # /etc/snmp/snmpd.conf
   # Solo desde red de monitoreo
   rocommunity public 10.0.100.0/24
   
   # Firewall
   sudo ufw allow from 10.0.100.0/24 to any port 161 proto udp
   sudo ufw deny 161/udp
   ```

3. **Community strings fuertes**
   ```bash
   # Malo
   rocommunity public
   
   # Bueno
   rocommunity "Zx9!kL2mP7@qR4s" 10.0.100.0/24
   ```

4. **Deshabilitar SET** si no es necesario
   ```conf
   # Solo lectura, NO escritura
   # NO poner: rwcommunity
   ```

### Performance

1. **Frecuencia de polling SNMP**
   - Interfaces de red: 30-60 segundos
   - CPU/RAM: 1-5 minutos
   - Uptime/sysDescr: 5-15 minutos

2. **Usar GETBULK** en lugar de múltiples GET
   ```bash
   # Lento: 100 GET requests
   for i in {1..100}; do snmpget ...; done
   
   # Rápido: 1 GETBULK request
   snmpbulkget -Cr100 ...
   ```

3. **NetFlow sampling**
   ```
   # 1:1 (todos los paquetes) → Alto CPU
   # 1:100 (1 de cada 100) → Menor CPU, suficiente para análisis
   ```

### Retención de datos

```yaml
# Prometheus retention
global:
  scrape_interval: 30s
  evaluation_interval: 30s

# Retener métricas por 90 días
--storage.tsdb.retention.time=90d
```

## Resumen Ejecutivo

Los **protocolos de administración de red** son esenciales para monitoreo automatizado y escalable:

**SNMP:**
- ✅ Monitoreo de estado de dispositivos (CPU, RAM, interfaces)
- ✅ Universal (todos los vendors)
- ⚠️ Usar SNMPv3 (v1/v2c inseguros)
- 📊 Integración con Prometheus/Grafana

**NetFlow/IPFIX:**
- ✅ Análisis de flujos de red (quién habla con quién)
- ✅ Detección de anomalías (DDoS, escaneos, exfiltración)
- ✅ Top talkers, protocolos, conversaciones
- 📊 Herramientas: nfdump, ntopng, ElastiFlow

**sFlow:**
- ✅ Muestreo estadístico (bajo overhead)
- ✅ Switches de alto throughput (10G+)
- ✅ Similar a NetFlow pero más eficiente

**Stack recomendado:**
- SNMP Exporter → Prometheus → Grafana (métricas)
- softflowd → nfcapd → ntopng (flujos)
- Blackbox Exporter → Prometheus (uptime)

**Conclusión:** Sin protocolos de administración, el monitoreo de red moderna es **imposible a escala**. SNMP + NetFlow proporcionan visibilidad completa de infraestructura y tráfico.
