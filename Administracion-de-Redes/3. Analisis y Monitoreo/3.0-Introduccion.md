# Unidad 3: Análisis y Monitoreo de Redes

## Introducción

> **"No puedes gestionar lo que no puedes medir"** - Peter Drucker

Después de haber instalado y configurado servicios críticos de red (DHCP, DNS, SSH, HTTP, correo electrónico, proxies) en la **Unidad 2**, surge una pregunta fundamental: **¿Cómo sabemos si nuestra red funciona correctamente?** ¿Está el ancho de banda siendo utilizado eficientemente? ¿Existen cuellos de botella? ¿Hay actividad maliciosa? ¿Los usuarios están experimentando latencia?

La **Unidad 3** aborda estas preguntas críticas mediante el **análisis y monitoreo** de redes, competencias esenciales para cualquier administrador de sistemas. No basta con configurar servicios; debemos **observar, medir, analizar y optimizar** continuamente la infraestructura de red para garantizar:

- ✅ **Rendimiento óptimo**: Identificar y resolver cuellos de botella
- ✅ **Disponibilidad**: Detectar fallos antes de que afecten a usuarios
- ✅ **Seguridad**: Identificar patrones de tráfico anómalos o ataques
- ✅ **Capacidad de planificación**: Predecir necesidades futuras de recursos
- ✅ **Resolución proactiva**: Actuar antes de que los problemas se conviertan en crisis

## Del Monitoreo Reactivo al Proactivo

### Enfoque Reactivo (❌ Ineficiente)

```
Usuario reporta problema → Administrador investiga → Encuentra causa 
→ Implementa solución → Tiempo de inactividad (downtime) alto
```

**Problemas:**
- ⏱️ Tiempo de respuesta lento (horas o días)
- 💸 Pérdida de productividad y dinero
- 😠 Usuarios insatisfechos
- 🔥 Administrador siempre "apagando incendios"

### Enfoque Proactivo (✅ Recomendado)

```
Monitoreo continuo → Alertas automáticas cuando métricas se desvían 
→ Administrador investiga antes de que usuarios noten 
→ Solución preventiva → Downtime mínimo o nulo
```

**Beneficios:**
- ✅ Detección temprana de problemas (minutos)
- ✅ Resolución antes de afectar usuarios
- ✅ Datos históricos para análisis de tendencias
- ✅ Planificación de capacidad basada en evidencia
- ✅ Administrador proactivo, no reactivo

## Contenido de la Unidad 3

### 3.1 Protocolos de Administración de Red

Estudiaremos los protocolos estándar para recopilar información de dispositivos de red:

**SNMP (Simple Network Management Protocol)**
- Versiones: SNMPv1, SNMPv2c, SNMPv3
- MIBs (Management Information Bases)
- Operaciones: GET, SET, TRAP
- Casos de uso: Monitoreo de routers, switches, servidores

**NetFlow / sFlow / IPFIX**
- Análisis de flujos de red
- Identificación de top talkers (quiénes consumen más ancho de banda)
- Detección de patrones de tráfico anómalos
- Herramientas: nfdump, ntopng, ElastiFlow

**SNMP Traps vs Polling**
```
Polling (Pull):                  Traps (Push):
┌──────────┐                     ┌──────────┐
│ Monitor  │ ──query cada X──>   │ Disposi- │ ──alerta cuando──>
│          │ <───respuesta────   │   tivo   │   evento crítico
└──────────┘                     └──────────┘

Pros: Control total              Pros: Tiempo real
Cons: Carga de red               Cons: Puede perderse
```

### 3.2 Bitácoras (Logs)

Los logs son la **caja negra** de la red. Todo evento importante debe ser registrado:

**Tipos de logs:**
- **Syslog**: Estándar universal (RFC 5424)
- **Application logs**: Apache, Nginx, Postfix, etc.
- **Security logs**: SSH failed attempts, firewall blocks
- **Audit logs**: Cambios de configuración, accesos administrativos

**Herramientas de gestión de logs:**
- **rsyslog/syslog-ng**: Centralización de logs
- **ELK Stack**: Elasticsearch (almacenamiento), Logstash (procesamiento), Kibana (visualización)
- **Loki + Promtail**: Alternativa ligera de Grafana Labs
- **Splunk**: Solución comercial enterprise

**Caso de estudio:**
```
Problema: Servidor web cae misteriosamente cada noche
Análisis de logs: 
1. /var/log/apache2/access.log → Pico de tráfico 3 AM
2. /var/log/syslog → OOM Killer mata Apache
3. Correlación: Cron job ejecuta backup pesado
Solución: Mover backup a horario de menor carga
```

### 3.3 Analizadores de Protocolos (Scanners y Sniffers)

Herramientas para **capturar y analizar paquetes** en tránsito:

**Sniffers (Packet Capture):**
- **Wireshark**: GUI poderosa para análisis profundo
- **tcpdump**: CLI para capturas rápidas
- **tshark**: Wireshark en modo CLI
- **ettercap**: MITM y análisis de protocolos

**Scanners (Network Discovery):**
- **Nmap**: Escaneo de puertos y servicios
- **Netcat**: Swiss army knife de redes
- **hping3**: Generación de paquetes personalizados
- **Masscan**: Escaneo rápido de grandes rangos

**Análisis de tráfico:**
```
Packet capture → Filtrado (BPF) → Decodificación → Análisis

Ejemplo: Diagnosticar latencia en aplicación web
1. tcpdump -i eth0 -w capture.pcap 'port 80 or port 443'
2. Wireshark: Follow TCP Stream
3. Identificar: Handshake 5ms, Request 2ms, Server processing 2000ms
4. Conclusión: Problema en backend, no en red
```

### 3.4 Análisis de Desempeño: Tráfico y Servicios

Métricas críticas para medir **salud de la red**:

**Métricas de red:**
- **Latencia (Ping)**: Tiempo de respuesta (objetivo: <50ms LAN, <200ms WAN)
- **Jitter**: Variación de latencia (crítico para VoIP/videoconferencia)
- **Pérdida de paquetes**: % de paquetes perdidos (objetivo: <1%)
- **Throughput**: Ancho de banda real utilizado vs disponible
- **Retransmisiones TCP**: Indicador de problemas de red

**Métricas de servicios:**
- **Uptime**: Disponibilidad (objetivo: 99.9% = 8.76 horas downtime/año)
- **Response time**: Tiempo de respuesta de aplicación
- **Error rate**: % de requests con error (HTTP 5xx)
- **Saturation**: % de recursos utilizados (CPU, RAM, disco)

**Herramientas:**
- **iperf3**: Medición de throughput
- **mtr**: Ping + traceroute continuo
- **smokeping**: Monitoreo de latencia histórica
- **MRTG/Cacti**: Gráficas de tráfico de interfaces

**Golden Signals (Google SRE):**
```
1. Latency:    ¿Cuánto tarda en responder?
2. Traffic:    ¿Cuántas peticiones por segundo?
3. Errors:     ¿Qué porcentaje de requests falla?
4. Saturation: ¿Qué tan llenos están los recursos?
```

### 3.5 QoS (Quality of Service)

**Problema:** Todo el tráfico es igual, pero algunos servicios son **más críticos** que otros.

**Ejemplo sin QoS:**
```
Red congestionada:
- Videoconferencia CEO: ❌ Se corta (crítico)
- Descarga de ISO: ✅ Continúa (no crítico)
- VoIP de soporte: ❌ Calidad mala (crítico)

Resultado: Servicios críticos sufren igual que no críticos
```

**Con QoS:**
```
Priorización de tráfico:
1. Alta prioridad: VoIP, videoconferencia, SSH (baja latencia requerida)
2. Media prioridad: HTTP, email (tiempo real, pero tolerante)
3. Baja prioridad: Backups, downloads (bulk transfer)

Resultado: Servicios críticos funcionan incluso con red congestionada
```

**Mecanismos QoS:**
- **Classification**: Identificar tipo de tráfico (por puerto, DSCP)
- **Marking**: Etiquetar paquetes (ToS, DSCP, CoS)
- **Queuing**: Diferentes colas de salida (FIFO, WFQ, CBWFQ)
- **Policing**: Limitar tráfico de cierto tipo
- **Shaping**: Suavizar ráfagas de tráfico

**DSCP Values comunes:**
```
EF (Expedited Forwarding) - 46: VoIP
AF41 - 34: Videoconferencia
AF31 - 26: Streaming
AF21 - 18: Tráfico de negocio
BE (Best Effort) - 0: Internet general
```

## Casos de Uso Reales

### Caso 1: Diagnóstico de Latencia en Aplicación Web

**Síntoma:** Usuarios reportan "la web está lenta"

**Herramientas usadas:**
1. **Browser Developer Tools**: Waterfall muestra 5s en una API
2. **Wireshark**: Captura muestra handshake TCP normal, pero request tarda 4.8s
3. **Application logs**: Backend está procesando query SQL compleja
4. **Database monitoring**: Query sin índice hace full table scan

**Solución:** Agregar índice a tabla → Tiempo baja de 5s a 200ms

### Caso 2: Consumo Anormal de Ancho de Banda

**Síntoma:** Internet corporativo "lento" en horas laborales

**Herramientas usadas:**
1. **NetFlow**: Identifica top talker: 192.168.1.50
2. **Nmap**: Host está ejecutando servidor BitTorrent
3. **Firewall logs**: Conexiones P2P salientes masivas
4. **SNMP**: Interface saturada al 95%

**Solución:** Bloquear P2P en firewall + QoS para priorizar tráfico legítimo

### Caso 3: Ataque DDoS

**Síntoma:** Servidor web no responde

**Herramientas usadas:**
1. **tcpdump**: 100,000 SYN packets/segundo
2. **iptables + fail2ban**: Bloquear IPs atacantes
3. **CloudFlare**: Activar "Under Attack Mode"
4. **Grafana**: Dashboard muestra tráfico anómalo

**Solución:** Activar protección DDoS en CDN + rate limiting

## Métricas de Éxito del Administrador

Un buen administrador de redes moderno debe lograr:

| Métrica | Objetivo |
|---------|----------|
| **MTBF (Mean Time Between Failures)** | >720 horas (1 mes sin fallos) |
| **MTTR (Mean Time To Repair)** | <30 minutos |
| **Uptime** | >99.9% (43 minutos downtime/mes) |
| **Alertas falso-positivas** | <5% (demasiadas alertas = alarma fatiga) |
| **Tiempo de detección de problemas** | <5 minutos (antes de que usuarios noten) |
| **Capacidad planificada vs real** | 80% (20% de headroom para picos) |

## Evolución: De Monitoreo a Observabilidad

### Monitoreo Tradicional
- Métricas predefinidas (CPU, RAM, red)
- Dashboards estáticos
- Alertas basadas en thresholds

### Observabilidad Moderna
- **Traces**: Seguimiento de requests entre microservicios
- **Metrics**: Datos cuantitativos (qué tan rápido/lento)
- **Logs**: Datos cualitativos (qué pasó exactamente)
- **Correlación**: Unir los tres pilares para contexto completo

**Herramientas de observabilidad:**
- **OpenTelemetry**: Estándar para instrumentación
- **Jaeger**: Distributed tracing
- **Tempo**: Tracing backend de Grafana
- **Honeycomb**: Observability-as-a-Service
