### ¿Qué es el Análisis de Desempeño?

El **análisis de desempeño de red** es el proceso de:

1. **Medir métricas** de comportamiento de la red
2. **Comparar** contra baselines y objetivos
3. **Identificar** problemas y cuellos de botella
4. **Validar** que la red cumple con SLAs
5. **Optimizar** recursos y configuraciones

### Objetivos del Análisis

- ✅ **Detectar degradación** antes de que afecte usuarios
- ✅ **Validar cambios** (¿mejoró o empeoró la red?)
- ✅ **Planificar capacidad** basándose en datos reales
- ✅ **Troubleshooting** de problemas de rendimiento
- ✅ **Justificar inversiones** en infraestructura
- ✅ **Cumplimiento de SLAs** con evidencia medible

## Métricas Clave de Desempeño

### Las 4 Métricas Fundamentales

```
┌─────────────────────────────────────────────────────────┐
│  MÉTRICAS CRÍTICAS DE PERFORMANCE DE RED                │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  1. LATENCIA (Latency/RTT)                             │
│     ├─ Definición: Tiempo que tarda paquete A→B→A     │
│     ├─ Unidad: milisegundos (ms)                      │
│     ├─ Objetivo típico: <50ms LAN, <150ms WAN         │
│     ├─ Impacto: Responsiveness, interactividad        │
│     └─ Herramientas: ping, mtr, smokeping             │
│                                                         │
│  2. THROUGHPUT / ANCHO DE BANDA                        │
│     ├─ Definición: Cantidad de datos transmitidos/seg │
│     ├─ Unidad: Mbps, Gbps                             │
│     ├─ Objetivo: Cumplir SLA contratado               │
│     ├─ Impacto: Velocidad de transferencias           │
│     └─ Herramientas: iperf3, speedtest-cli, nload     │
│                                                         │
│  3. PACKET LOSS (Pérdida de Paquetes)                  │
│     ├─ Definición: % de paquetes que no llegan        │
│     ├─ Unidad: porcentaje (%)                         │
│     ├─ Objetivo: <0.1% (mejor si 0%)                  │
│     ├─ Impacto: Retransmisiones, lentitud             │
│     └─ Herramientas: ping, mtr, smokeping             │
│                                                         │
│  4. JITTER (Variación de Latencia)                     │
│     ├─ Definición: Variación en tiempo entre paquetes │
│     ├─ Unidad: milisegundos (ms)                      │
│     ├─ Objetivo: <30ms para VoIP                      │
│     ├─ Impacto: Calidad de VoIP/video                │
│     └─ Herramientas: iperf3 -u, VoIP monitoring       │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

### Tabla Comparativa de Tolerancias

| Aplicación | Latencia | Packet Loss | Jitter | Throughput |
|------------|----------|-------------|--------|------------|
| **Navegación Web** | <200ms | <1% | No crítico | 5-10 Mbps |
| **Email** | <1s | <5% | No crítico | 1-5 Mbps |
| **Transferencia de archivos** | No crítico | <0.5% | No crítico | Variable |
| **VoIP** | <150ms | <0.5% | <30ms | 64-128 Kbps |
| **Video conferencia** | <150ms | <0.1% | <30ms | 1-5 Mbps |
| **Video streaming** | <500ms inicial | <1% | No crítico | 3-25 Mbps |
| **Gaming online** | <50ms | <0.1% | <10ms | 1-3 Mbps |
| **Aplicaciones financieras** | <10ms | <0.01% | <5ms | Variable |
| **Telemedicina** | <100ms | <0.05% | <20ms | 2-10 Mbps |
| **Control industrial** | <20ms | <0.001% | <5ms | 1-10 Mbps |

### Relación entre Métricas

```
Alta Latencia + Alta Pérdida = Red congestionada o enlace defectuoso
Baja Latencia + Alto Jitter = Problemas de buffering o QoS mal configurado
Bajo Throughput + Baja Pérdida = Limitación de ancho de banda (tasa contratada)
Bajo Throughput + Alta Pérdida = TCP reduciendo ventana por congestión
```

## Latencia y RTT (Round Trip Time)

### ¿Qué es la Latencia?

**Latencia** es el tiempo que tarda un paquete en viajar de origen a destino.  
**RTT (Round Trip Time)** es el tiempo total de ida y vuelta (A→B→A).

```
Origen ─────────────────→ Destino
         (Latencia 50ms)
         
Origen ←───────────────── Destino
         (Latencia 50ms)
         
RTT Total = 100ms
```

### Componentes de la Latencia

```
┌────────────────────────────────────────────────────┐
│  LATENCIA TOTAL = SUMA DE COMPONENTES              │
├────────────────────────────────────────────────────┤
│                                                    │
│  1. Propagation Delay (Retardo de Propagación)    │
│     ├─ Tiempo físico de la señal en el medio     │
│     ├─ Velocidad de la luz en fibra: ~200km/ms   │
│     └─ Ejemplo: México-España ~60ms mínimo       │
│                                                    │
│  2. Transmission Delay (Retardo de Transmisión)   │
│     ├─ Tiempo en poner bits en el enlace         │
│     ├─ Depende de: tamaño paquete / ancho banda  │
│     └─ Ejemplo: 1500 bytes / 100 Mbps = 0.12ms   │
│                                                    │
│  3. Processing Delay (Retardo de Procesamiento)   │
│     ├─ Tiempo de procesar headers en routers     │
│     ├─ Lookups en tabla de routing                │
│     └─ Ejemplo: 1-10ms por salto                  │
│                                                    │
│  4. Queuing Delay (Retardo de Cola)               │
│     ├─ Tiempo esperando en buffers                │
│     ├─ Variable según congestión                  │
│     └─ Ejemplo: 0-100ms+ (altamente variable)     │
│                                                    │
└────────────────────────────────────────────────────┘

Latencia Total = Propagación + Transmisión + Procesamiento + Queuing
```

### Medición con ping

**ping** es la herramienta más básica para medir latencia.

```bash
# Ping básico
ping google.com

# Salida típica:
PING google.com (142.250.185.46) 56(84) bytes of data.
64 bytes from mex07s49-in-f14.1e100.net (142.250.185.46): icmp_seq=1 ttl=117 time=12.3 ms
64 bytes from mex07s49-in-f14.1e100.net (142.250.185.46): icmp_seq=2 ttl=117 time=11.8 ms
64 bytes from mex07s49-in-f14.1e100.net (142.250.185.46): icmp_seq=3 ttl=117 time=12.1 ms

--- google.com ping statistics ---
3 packets transmitted, 3 received, 0% packet loss, time 2003ms
rtt min/avg/max/mdev = 11.8/12.1/12.3/0.2 ms
```

**Interpretación:**
- **time=12.3 ms**: RTT de ese paquete específico
- **min/avg/max**: Latencia mínima, promedio, máxima
- **mdev (standard deviation)**: Desviación estándar = jitter aproximado

#### Opciones Útiles de ping

```bash
# Especificar número de pings
ping -c 10 google.com

# Intervalo entre pings (segundos)
ping -i 0.2 google.com  # Cada 200ms (cuidado con flood)

# Tamaño de paquete (útil para MTU testing)
ping -s 1472 google.com  # 1472 + 28 (ICMP+IP headers) = 1500 bytes

# Flood ping (requiere root, para stress testing)
sudo ping -f 192.168.1.1

# IPv6
ping6 ipv6.google.com

# Establecer TTL específico
ping -t 5 google.com  # Solo alcanzará 5 saltos

# No resolver nombres DNS
ping -n 8.8.8.8

# Timestamp en cada línea
ping -D google.com

# Audible ping (beep en cada respuesta)
ping -a google.com
```

#### Análisis de Resultados de ping

```bash
# Ping continuo con timestamp
ping -D google.com > ping_results.txt

# Análisis estadístico
# Ver distribución de latencias
cat ping_results.txt | grep 'time=' | awk '{print $7}' | \
  cut -d= -f2 | sort -n | uniq -c

# Detectar picos de latencia (>50ms)
cat ping_results.txt | grep 'time=' | awk '{if ($7 > 50) print}'
```

### Medición con mtr (My Traceroute)

**mtr** combina ping + traceroute para análisis hop-by-hop.

```bash
# Instalación
sudo apt install mtr

# Modo interactivo (tiempo real)
mtr google.com

# Modo reporte (ejecutar N tests y mostrar estadísticas)
mtr -r -c 100 google.com

# Salida a archivo
mtr -r -c 100 google.com > mtr_report.txt

# Sin resolución DNS (más rápido)
mtr -n google.com

# Modo CSV para procesamiento
mtr --csv -c 100 google.com > report.csv

# TCP en lugar de ICMP (útil si ICMP bloqueado)
mtr --tcp -P 443 google.com

# UDP mode
mtr --udp google.com
```

```
 Host                                Loss%   Snt   Last   Avg  Best  Wrst StDev

 3. isp-gateway.net                   0.0%   100   12.3  12.5  12.0  15.2   0.6
 4. core-router1.isp.net              0.0%   100   18.7  19.2  18.3  25.1   1.2

```

**Interpretación:**
- **Loss%**: Pérdida de paquetes en cada salto
- **Snt**: Paquetes enviados
- **Last**: Latencia del último paquete
- **Avg**: Latencia promedio
- **Best/Wrst**: Mejor y peor latencia observada
- **StDev**: Desviación estándar (jitter)

**Diagnóstico común:**
```
✅ Pérdida en solo el último hop → Probablemente ICMP rate limiting (ignorar)
⚠️ Pérdida en un hop intermedio → Posible problema en ese router
⚠️ Incremento súbito de latencia → Cuellos de botella
⚠️ Alto StDev → Jitter alto, problemas de congestión
```

### Medición de Latencia en Aplicaciones

#### HTTP Response Time

```bash
# curl con tiempos detallados
curl -w "\ntime_namelookup: %{time_namelookup}\ntime_connect: %{time_connect}\ntime_appconnect: %{time_appconnect}\ntime_pretransfer: %{time_pretransfer}\ntime_starttransfer: %{time_starttransfer}\ntime_total: %{time_total}\n" -o /dev/null -s https://www.example.com

# Salida ejemplo:
# time_namelookup:    0.008s  ← DNS resolution
# time_connect:       0.032s  ← TCP handshake
# time_appconnect:    0.089s  ← TLS handshake
# time_pretransfer:   0.089s
# time_starttransfer: 0.145s  ← Time to First Byte (TTFB)
# time_total:         0.234s  ← Total time
```

#### Script para Monitoreo Continuo

```bash
#!/bin/bash
# monitor_latency.sh

TARGET="8.8.8.8"
LOG_FILE="/var/log/latency_monitor.log"
ALERT_THRESHOLD=100  # ms

while true; do
    TIMESTAMP=$(date '+%Y-%m-%d %H:%M:%S')
    PING_RESULT=$(ping -c 1 -W 2 $TARGET 2>/dev/null | grep 'time=' | awk -F'time=' '{print $2}' | awk '{print $1}')
    
    if [ -z "$PING_RESULT" ]; then
        echo "$TIMESTAMP - TIMEOUT" >> $LOG_FILE
        # Enviar alerta
        echo "ALERTA: Timeout a $TARGET" | mail -s "Network Alert" admin@example.com
    else
        echo "$TIMESTAMP - ${PING_RESULT}ms" >> $LOG_FILE
        
        # Verificar si excede threshold
        PING_INT=$(echo $PING_RESULT | cut -d. -f1)
        if [ "$PING_INT" -gt "$ALERT_THRESHOLD" ]; then
            echo "ALERTA: Alta latencia (${PING_RESULT}ms) a $TARGET" | mail -s "High Latency Alert" admin@example.com
        fi
    fi
    
    sleep 60  # Medir cada minuto
done
```

## Throughput y Ancho de Banda

### Diferencia: Ancho de Banda vs Throughput

```
┌──────────────────────────────────────────────────────────┐
│  ANCHO DE BANDA vs THROUGHPUT                            │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  ANCHO DE BANDA (Bandwidth)                             │
│  ├─ Capacidad máxima teórica del enlace                 │
│  ├─ Ejemplo: Enlace de 100 Mbps                         │
│  └─ Es un LÍMITE FÍSICO                                 │
│                                                          │
│  THROUGHPUT                                             │
│  ├─ Tasa real de datos transferidos                    │
│  ├─ Ejemplo: 85 Mbps en enlace de 100 Mbps             │
│  └─ Es el RENDIMIENTO EFECTIVO                          │
│                                                          │
│  Por qué Throughput < Bandwidth:                        │
│  ├─ Protocol overhead (headers TCP/IP/Ethernet)        │
│  ├─ Retransmisiones por pérdidas                       │
│  ├─ Latencia (TCP window limiting)                     │
│  ├─ Congestión en la red                               │
│  └─ Limitaciones de servidor/cliente                   │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### Medición con iperf3

**iperf3** es el estándar de facto para medir throughput.

#### Instalación

```bash

# Fedora/RHEL
```

#### Uso Básico

**Topología:**
```
Servidor                        Cliente
[192.168.1.100] ←─────────→ [192.168.1.200]

```

**En el servidor:**

#### Opciones Avanzadas de iperf3

**TCP Tests:**
```bash
# Duración personalizada
iperf3 -c 192.168.1.100 -t 60  # 60 segundos

# Reverse mode (servidor envía al cliente)
iperf3 -c 192.168.1.100 -R

# Bidireccional (simultáneo)
iperf3 -c 192.168.1.100 --bidir

# Múltiples streams paralelos
iperf3 -c 192.168.1.100 -P 5  # 5 streams simultáneos

# Window size específico
iperf3 -c 192.168.1.100 -w 512K

# Limitar ancho de banda objetivo
iperf3 -c 192.168.1.100 -b 100M  # Intentar 100 Mbps

# Intervalos de reporte
iperf3 -c 192.168.1.100 -i 1  # Reportar cada segundo

# Formato JSON (para scripting)
iperf3 -c 192.168.1.100 -J > results.json

# Salida a archivo
iperf3 -c 192.168.1.100 --logfile results.txt
```

**UDP Tests:**
```bash
# Test UDP (útil para medir jitter y packet loss)
iperf3 -c 192.168.1.100 -u

# UDP con ancho de banda específico
iperf3 -c 192.168.1.100 -u -b 50M

# UDP con tamaño de paquete personalizado
iperf3 -c 192.168.1.100 -u -l 1400  # 1400 bytes

# Salida ejemplo UDP:
[ ID] Interval           Transfer     Bitrate         Jitter    Lost/Total Datagrams
[  5]   0.00-10.00  sec  59.6 MBytes  50.0 Mbits/sec  0.123 ms  0/42500 (0%)  sender
[  5]   0.00-10.04  sec  59.3 MBytes  49.6 Mbits/sec  0.156 ms  23/42500 (0.054%)  receiver
```

**Interpretación UDP:**
- **Bitrate**: Throughput UDP
- **Jitter**: Variación de latencia entre paquetes
- **Lost/Total**: Paquetes perdidos / total enviados
- **Porcentaje de pérdida**: Debería ser <0.1% en red saludable

#### Scripts de Automatización

```bash
#!/bin/bash
# bandwidth_test.sh - Medir throughput periódicamente

SERVER="192.168.1.100"
DURATION=30
LOG_FILE="/var/log/bandwidth_tests.log"

echo "=== Bandwidth Test $(date) ===" >> $LOG_FILE

# TCP Test
echo "TCP Test:" >> $LOG_FILE
iperf3 -c $SERVER -t $DURATION -J | jq -r '.end.sum_sent.bits_per_second' | \
  awk '{print "TCP Throughput: " $1/1000000 " Mbps"}' >> $LOG_FILE

# UDP Test con 50 Mbps
echo "UDP Test:" >> $LOG_FILE
iperf3 -c $SERVER -u -b 50M -t $DURATION -J | \
  jq -r '.end.sum.bits_per_second, .end.sum.jitter_ms, .end.sum.lost_percent' | \
  awk 'NR==1{print "UDP Throughput: " $1/1000000 " Mbps"} 
       NR==2{print "Jitter: " $1 " ms"} 
       NR==3{print "Packet Loss: " $1 "%"}' >> $LOG_FILE

echo "" >> $LOG_FILE
```

## Packet Loss (Pérdida de Paquetes)

### ¿Qué es Packet Loss?

**Packet loss** es el porcentaje de paquetes que no llegan a destino.

**Causas comunes:**
1. **Congestión de red** - Buffers llenos, paquetes descartados
2. **Errores físicos** - Cable dañado, interferencia
3. **Equipos sobrecargados** - CPU/memoria insuficiente
4. **Configuración incorrecta** - MTU mismatch, duplex mismatch
5. **Firewall/ACL** - Paquetes bloqueados intencionalmente

### Impacto de Packet Loss

```
┌────────────────────────────────────────────────────┐
│  IMPACTO DE PACKET LOSS POR APLICACIÓN            │
├────────────────────────────────────────────────────┤
│                                                    │
│  TCP (HTTP, FTP, SSH, etc.)                       │
│  ├─ 0% loss: Óptimo                              │
│  ├─ 0.1-0.5% loss: Leve impacto, retransmisiones │
│  ├─ 1-2% loss: Throughput reducido ~50%          │
│  ├─ 3-5% loss: Muy lento, timeouts frecuentes    │
│  └─ >5% loss: Prácticamente inutilizable         │
│                                                    │
│  UDP (VoIP, Streaming)                            │
│  ├─ 0% loss: Óptimo                              │
│  ├─ 0.1-0.5% loss: Aceptable, casi imperceptible│
│  ├─ 1-2% loss: Degradación notable               │
│  ├─ 3-5% loss: Calidad pobre                     │
│  └─ >5% loss: Inutilizable                       │
│                                                    │
└────────────────────────────────────────────────────┘

Nota: TCP es especialmente sensible porque cada pérdida 
      desencadena retransmisión y reducción de ventana.
```

### Medición con ping

```bash
# Ping continuo para detectar pérdida
ping -c 1000 8.8.8.8

# Estadísticas finales:
--- 8.8.8.8 ping statistics ---
1000 packets transmitted, 998 received, 0.2% packet loss, time 999045ms
rtt min/avg/max/mdev = 11.234/12.567/25.891/1.234 ms

# Pérdida de 0.2% (2 de 1000 paquetes)
```

### Medición con mtr

```bash
# mtr muestra pérdida hop-by-hop
mtr -r -c 100 google.com

# Ejemplo de salida:
HOST: localhost          Loss%   Snt   Last   Avg  Best  Wrst StDev
  1. 192.168.1.1          0.0%   100    1.2   1.3   1.1   2.5   0.2
  2. 10.0.0.1             0.0%   100    8.5   8.7   8.3   9.8   0.3
  3. isp-gateway          2.0%   100   12.3  12.5  12.0  15.2   0.6  ⚠️
  4. core-router          1.0%   100   18.7  19.2  18.3  25.1   1.2  ⚠️
  5. google.com           0.0%   100   22.1  22.5  21.8  28.3   1.5

# Pérdida en hop 3 y 4 → Problema en ISP o peering
```

**Interpretación:**
- Pérdida solo en último hop → Probablemente ICMP rate limiting (ignorar)
- Pérdida en hop intermedio que no continúa → Rate limiting
- Pérdida en hop que se propaga → Problema real

### Script de Detección de Pérdida

```bash
#!/bin/bash
# packet_loss_monitor.sh

TARGET="8.8.8.8"
THRESHOLD=1.0  # 1% de pérdida
INTERVAL=300   # 5 minutos

while true; do
    TIMESTAMP=$(date '+%Y-%m-%d %H:%M:%S')
    
    # Enviar 100 pings
    RESULT=$(ping -c 100 -q $TARGET 2>&1)
    
    # Extraer porcentaje de pérdida
    LOSS=$(echo "$RESULT" | grep 'packet loss' | awk '{print $6}' | sed 's/%//')
    
    echo "$TIMESTAMP - Packet Loss: $LOSS%"
    
    # Verificar si excede threshold
    if (( $(echo "$LOSS > $THRESHOLD" | bc -l) )); then
        echo "ALERTA: Pérdida de paquetes ($LOSS%) excede threshold ($THRESHOLD%)"
        # Enviar notificación
        echo "Packet Loss Alert: $LOSS% to $TARGET at $TIMESTAMP" | \
          mail -s "Network Alert" admin@example.com
    fi
    
    sleep $INTERVAL
done
```

## Jitter (Variación de Latencia)

### ¿Qué es el Jitter?

**Jitter** es la **variación en el tiempo de llegada** de paquetes consecutivos.

```
Paquetes con Bajo Jitter:
Tiempo: ---|---|---|---|---|---|  (llegada regular)
        0ms 10ms 20ms 30ms 40ms

Paquetes con Alto Jitter:
Tiempo: -|----|-|--------|--|--  (llegada irregular)
        0ms  15ms 17ms  32ms 34ms
```

**Causas de jitter:**
- Congestión variable en la red
- Diferentes rutas tomadas por paquetes
- Buffering inconsistente
- QoS mal configurado

### Impacto del Jitter

**Especialmente crítico para:**
- **VoIP**: Jitter >30ms causa calidad pobre
- **Video conferencia**: Jitter >30ms causa video entrecortado
- **Gaming**: Jitter >10ms afecta jugabilidad

**Menos crítico para:**
- Navegación web
- Email
- Transferencia de archivos

### Medición con iperf3 UDP

```bash
# En servidor
iperf3 -s

# En cliente (test UDP para medir jitter)
iperf3 -c 192.168.1.100 -u -b 10M -t 60

# Salida incluye jitter:
[ ID] Interval           Transfer     Bitrate         Jitter    Lost/Total
[  5]   0.00-60.00  sec  71.5 MBytes  10.0 Mbits/sec  0.123 ms  0/51000 (0%)  sender
[  5]   0.00-60.04  sec  71.3 MBytes   9.96 Mbits/sec  0.156 ms  15/51000 (0.029%)  receiver

# Jitter: 0.156 ms (excelente para VoIP)
```

**Interpretación:**
- **<10ms**: Excelente (apto para gaming)
- **10-30ms**: Bueno (apto para VoIP)
- **30-50ms**: Aceptable (VoIP con degradación)
- **>50ms**: Pobre (no apto para tiempo real)

### Jitter Buffer

Aplicaciones de tiempo real usan **jitter buffers** para compensar:

```
┌────────────────────────────────────────────────┐
│  JITTER BUFFER                                 │
├────────────────────────────────────────────────┤
│                                                │
│  Paquetes llegan con jitter:                  │
│  Tiempo: -|----|-|--------|--|--              │
│                                                │
│  Buffer almacena y regulariza:                │
│  Salida: ---|---|---|---|---|---              │
│                                                │
│  Trade-off:                                   │
│  ├─ Buffer pequeño → Menor latencia           │
│  │                   pero más drops           │
│  └─ Buffer grande → Más latencia              │
│                     pero menos drops          │
│                                                │
└────────────────────────────────────────────────┘
```

### Monitoreo de VoIP Quality (MOS Score)

**MOS (Mean Opinion Score)**: Métrica de calidad de voz (1-5).

```
MOS Score   Calidad
  5.0       Excelente
  4.0-4.5   Bueno
  3.5-4.0   Aceptable
  2.5-3.5   Pobre
  <2.5      Inaceptable

Factores que afectan MOS:
- Latencia (<150ms preferible)
- Jitter (<30ms preferible)
- Packet Loss (<1% preferible)
- Codec usado (G.711, G.729, Opus, etc.)
```

## Análisis de Capacidad y Utilización

### Conceptos de Capacidad

```
Capacidad del Enlace: 100 Mbps
├─ Tráfico Actual: 65 Mbps
├─ Utilización: 65%
├─ Headroom: 35 Mbps (35%)
└─ Recomendación: OK (threshold típico 80%)

Si Utilización > 80%:
├─ Monitorear de cerca
├─ Planificar upgrade
└─ Implementar QoS si posible
```

### Monitoreo de Utilización

```bash
# Script para calcular utilización
#!/bin/bash
# interface_utilization.sh

INTERFACE="eth0"
CAPACITY_MBPS=1000  # 1 Gbps

# Obtener bytes transmitidos/recibidos
RX1=$(cat /sys/class/net/$INTERFACE/statistics/rx_bytes)
TX1=$(cat /sys/class/net/$INTERFACE/statistics/tx_bytes)

sleep 1

RX2=$(cat /sys/class/net/$INTERFACE/statistics/rx_bytes)
TX2=$(cat /sys/class/net/$INTERFACE/statistics/tx_bytes)

# Calcular tasa (bytes/s)
RX_RATE=$(( ($RX2 - $RX1) * 8 / 1000000 ))  # Mbps
TX_RATE=$(( ($TX2 - $TX1) * 8 / 1000000 ))  # Mbps

# Utilización
RX_UTIL=$(echo "scale=2; ($RX_RATE / $CAPACITY_MBPS) * 100" | bc)
TX_UTIL=$(echo "scale=2; ($TX_RATE / $CAPACITY_MBPS) * 100" | bc)

echo "RX: ${RX_RATE} Mbps (${RX_UTIL}%)"
echo "TX: ${TX_RATE} Mbps (${TX_UTIL}%)"

# Alertar si utilización >80%
if (( $(echo "$RX_UTIL > 80" | bc -l) )) || (( $(echo "$TX_UTIL > 80" | bc -l) )); then
    echo "ALERTA: Alta utilización en $INTERFACE"
fi
```

### Capacity Planning

**Fórmula básica de crecimiento:**

```
Capacidad_Futura = Capacidad_Actual × (1 + Tasa_Crecimiento) ^ Años

Ejemplo:
- Uso actual: 60 Mbps
- Crecimiento anual: 20% (0.20)
- Años: 3

Capacidad en 3 años = 60 × (1 + 0.20) ^ 3
                    = 60 × 1.728
                    = 103.68 Mbps

Recomendación: Actualizar a enlace ≥150 Mbps (margen 50%)
```

## Baselining y Benchmarking

### ¿Qué es un Baseline?

Un **baseline** es una captura del comportamiento **normal** de la red:

```
BASELINE = Comportamiento Normal
├─ Latencia típica: 12-15ms
├─ Throughput promedio: 45-60 Mbps
├─ Packet loss: <0.1%
├─ Utilización: 50-65% en horas pico
└─ Errores de interfaz: 0

Usos del baseline:
1. Detectar anomalías (desviación del normal)
2. Validar cambios (¿mejoró o empeoró?)
3. Capacity planning (tendencias)
4. Troubleshooting (comparar actual vs normal)
```

### Creación de Baseline

```bash
#!/bin/bash
# create_baseline.sh - Capturar baseline de red

OUTPUT_DIR="/var/baselines"
TIMESTAMP=$(date +%Y%m%d_%H%M%S)
BASELINE_FILE="$OUTPUT_DIR/baseline_$TIMESTAMP.txt"

mkdir -p $OUTPUT_DIR

echo "=== BASELINE $(date) ===" > $BASELINE_FILE
echo "" >> $BASELINE_FILE

# 1. Latencia
echo "=== LATENCY ===" >> $BASELINE_FILE
ping -c 100 8.8.8.8 | tail -2 >> $BASELINE_FILE
echo "" >> $BASELINE_FILE

# 2. Throughput
echo "=== THROUGHPUT ===" >> $BASELINE_FILE
iperf3 -c iperf-server.local -t 30 -J | jq -r '.end.sum_sent.bits_per_second' | \
  awk '{print "TCP Throughput: " $1/1000000 " Mbps"}' >> $BASELINE_FILE
echo "" >> $BASELINE_FILE

# 3. Interface stats
echo "=== INTERFACE STATS ===" >> $BASELINE_FILE
ip -s link show eth0 >> $BASELINE_FILE
echo "" >> $BASELINE_FILE

# 4. Utilization
echo "=== UTILIZATION ===" >> $BASELINE_FILE
vnstat -i eth0 -h | tail -15 >> $BASELINE_FILE
echo "" >> $BASELINE_FILE

# 5. Active connections
echo "=== ACTIVE CONNECTIONS ===" >> $BASELINE_FILE
netstat -an | grep ESTABLISHED | wc -l | \
  awk '{print "Active TCP connections: " $1}' >> $BASELINE_FILE

echo "Baseline guardado en: $BASELINE_FILE"
```

**Recomendaciones:**
- Crear baselines en **diferentes momentos** (hora pico, valle, fin de semana)
- Actualizar baselines **periódicamente** (cada 3-6 meses)
- Documentar **cambios en infraestructura** que invaliden baselines antiguos

### Benchmarking

**Benchmark** = Prueba estandarizada para comparar rendimiento.

```bash
# Benchmark de throughput entre dos servidores
#!/bin/bash
# network_benchmark.sh

SERVER="192.168.1.100"
RESULTS_FILE="benchmark_results.txt"

echo "=== NETWORK BENCHMARK $(date) ===" > $RESULTS_FILE

# TCP Throughput (1 stream)
echo "TCP 1 stream:" >> $RESULTS_FILE
iperf3 -c $SERVER -t 30 -J | jq -r '.end.sum_sent.bits_per_second' | \
  awk '{print $1/1000000 " Mbps"}' >> $RESULTS_FILE

# TCP Throughput (5 streams paralelos)
echo "TCP 5 streams:" >> $RESULTS_FILE
iperf3 -c $SERVER -t 30 -P 5 -J | jq -r '.end.sum_sent.bits_per_second' | \
  awk '{print $1/1000000 " Mbps"}' >> $RESULTS_FILE

# UDP con diferentes tamaños de paquete
for SIZE in 512 1024 1400; do
    echo "UDP size=$SIZE:" >> $RESULTS_FILE
    iperf3 -c $SERVER -u -b 100M -l $SIZE -t 10 -J | \
      jq -r '.end.sum.bits_per_second, .end.sum.lost_percent' | \
      awk 'NR==1{print "  Throughput: " $1/1000000 " Mbps"} NR==2{print "  Loss: " $1 "%"}' >> $RESULTS_FILE
done

echo "Benchmark completado: $RESULTS_FILE"
```

### Cuellos de Botella Comunes

#### 1. CPU en Router/Firewall

**Síntomas:**
- Alta latencia variable
- Packet loss aleatorio
- Degradación con tráfico alto

**Diagnóstico:**
```bash
# Si tienes acceso SSH al router
ssh router "show processes cpu"

# SNMP query
snmpwalk -v2c -c public router .1.3.6.1.4.1.9.2.1.58.0
# OID para CPU usage en Cisco
```

**Solución:**
- Upgrade de hardware
- Offloading (hardware acceleration)
- Optimización de ACLs/rules

#### 2. Saturación de Enlace

**Síntomas:**
- Throughput no supera cierto límite
- Alta utilización consistente (>80%)
- Packet loss en horas pico

**Diagnóstico:**
```bash
# Ver utilización con vnstat
vnstat -l 60  # Live por 60 segundos

# Gráfica histórica
vnstat -hg

# SNMP (bytes in/out de interfaz)
snmpwalk -v2c -c public router ifInOctets
snmpwalk -v2c -c public router ifOutOctets
```

**Solución:**
- Upgrade de enlace (más ancho de banda)
- Implementar QoS
- Compression (si aplicable)
- Optimización de aplicaciones

#### 3. Duplex Mismatch

**Síntomas:**
- Throughput muy bajo (típicamente ~50% del esperado)
- Muchas colisiones o errores CRC
- Performance intermitente

**Diagnóstico:**
```bash
# Ver configuración actual
ethtool eth0

# Output:
Settings for eth0:
        Speed: 1000Mb/s
        Duplex: Full  # ← Debe ser igual en ambos lados
        Auto-negotiation: on

# Verificar errores
ethtool -S eth0 | grep -i crc

# Ver colisiones
ip -s link show eth0 | grep collisions
```

**Solución:**
```bash
# Forzar full duplex (si auto-negotiation falla)
sudo ethtool -s eth0 speed 1000 duplex full autoneg off

# O configurar permanentemente en /etc/network/interfaces (Debian):
auto eth0
iface eth0 inet static
    address 192.168.1.100
    netmask 255.255.255.0
    gateway 192.168.1.1
    post-up ethtool -s eth0 speed 1000 duplex full autoneg off
```

#### 4. MTU Mismatch / Path MTU Issues

**Síntomas:**
- Conexiones HTTP/SSH fallan aleatoriamente
- Throughput bajo
- Algunos sitios no cargan

**Diagnóstico:**
```bash
# Verificar MTU local
ip link show eth0 | grep mtu

# Test de Path MTU Discovery
ping -M do -s 1472 8.8.8.8
# -M do: Don't Fragment
# -s 1472: 1472 + 28 (ICMP+IP) = 1500 bytes

# Si falla, probar menor:
ping -M do -s 1400 8.8.8.8

# Traceroute con MTU discovery
tracepath google.com
# Mostrará el MTU mínimo en la ruta
```

**Solución:**
```bash
# Ajustar MTU si necesario
sudo ip link set dev eth0 mtu 1400

# Permanente (Debian/Ubuntu):
# En /etc/network/interfaces:
auto eth0
iface eth0 inet static
    mtu 1400

# O con NetworkManager:
nmcli connection modify eth0 802-3-ethernet.mtu 1400

# Habilitar MSS clamping en router (para PPPoE comúnmente):
iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu
```

#### 5. Bufferbloat

**Síntomas:**
- Latencia dispara cuando hay tráfico pesado
- Ping normal: 10ms, durante download: 500ms+
- Jitter extremo

**Diagnóstico:**
```bash
# Test específico de bufferbloat
# http://www.dslreports.com/speedtest

# O manual:
# Terminal 1: Ping continuo
ping -i 0.2 8.8.8.8

# Terminal 2: Download grande
curl -O http://speedtest.tele2.net/100MB.zip

# Observar si latencia aumenta significativamente
```

**Solución:**
```bash
# Implementar algoritmos de cola más inteligentes
# fq_codel (Fair Queueing with Controlled Delay)

sudo tc qdisc replace dev eth0 root fq_codel

# O con SQM (Smart Queue Management) en routers
# Disponible en OpenWrt y otros firmwares custom
```

## Casos de Uso Real

### Caso 1: Aplicación Web Lenta

**Reporte:** "La aplicación web está muy lenta"

**Diagnóstico paso a paso:**

```bash
# 1. Verificar conectividad básica
ping -c 10 webserver.com
# ✅ RTT promedio: 15ms (normal)

# 2. Medir latencia HTTP
curl -w "\ntime_total: %{time_total}s\n" -o /dev/null -s http://webserver.com/
# ⚠️ time_total: 8.5s (muy alto)

# 3. Desglosar tiempos
curl -w "DNS: %{time_namelookup}s\nConnect: %{time_connect}s\nTTFB: %{time_starttransfer}s\nTotal: %{time_total}s\n" -o /dev/null -s http://webserver.com/

# Output:
# DNS: 0.015s        ← OK
# Connect: 0.045s    ← OK
# TTFB: 7.8s         ← ⚠️ PROBLEMA AQUÍ
# Total: 8.5s

# Conclusión: El servidor tarda 7.8s en empezar a responder
# Problema NO es de red, es del servidor/aplicación/DB

# 4. Verificar desde el servidor
# SSH al servidor web
ssh webserver.com

# Ver carga del servidor
top
# Si CPU/RAM OK, revisar DB

# Latencia a DB
ping -c 10 database-server

# Query a DB
time mysql -h database-server -e "SELECT COUNT(*) FROM large_table;"
# ⚠️ Tarda 7.5 segundos

# Encontrado: Query lenta en DB
# Solución: Optimizar query, agregar índices
```

### Caso 2: Transferencia de Archivos Lenta

**Reporte:** "Copiar archivos al servidor tarda horas"

```bash
# 1. Baseline: ¿Cuánto ancho de banda tenemos?
iperf3 -c file-server.local
# ⚠️ Throughput: 12 Mbps (esperado: 100 Mbps)

# 2. Verificar utilización de interfaz
bmon  # O nload
# Utilización: Solo 12% del enlace

# 3. Revisar errores de interfaz
ip -s link show eth0
# ✅ No errors, no drops

# 4. Capturar tráfico
sudo tcpdump -i eth0 host file-server.local -w slow_transfer.pcap

# 5. Analizar en Wireshark
wireshark slow_transfer.pcap

# Buscar: tcp.analysis.retransmission
# ⚠️ Muchas retransmisiones

# Buscar: tcp.window_size
# ⚠️ Window size muy pequeño (8KB)

# 6. Ajustar TCP window scaling en servidor
ssh file-server.local
sudo sysctl -w net.ipv4.tcp_window_scaling=1
sudo sysctl -w net.core.rmem_max=134217728
sudo sysctl -w net.core.wmem_max=134217728
sudo sysctl -w net.ipv4.tcp_rmem="4096 87380 67108864"
sudo sysctl -w net.ipv4.tcp_wmem="4096 65536 67108864"

# 7. Re-test
iperf3 -c file-server.local
# ✅ Throughput: 94 Mbps (mejorado)
```

### Caso 3: VoIP con Calidad Pobre

**Reporte:** "Llamadas VoIP se escuchan entrecortadas"

```bash
# 1. Medir latencia
ping -c 100 voip-server.com | tail -2
# RTT avg: 45ms ✅ (aceptable)

# 2. Medir jitter y packet loss
iperf3 -c voip-server.com -u -b 128K -t 60
# Jitter: 85ms ⚠️ (>30ms es malo para VoIP)
# Packet Loss: 2.3% ⚠️ (>1% es malo)

# 3. Verificar ruta
mtr -r -c 100 voip-server.com
# Saltos 5-7 muestran pérdida intermitente

# 4. Implementar QoS
# En router Linux con tc
sudo tc qdisc add dev eth0 root handle 1: htb default 30

# Clase de alta prioridad para VoIP
sudo tc class add dev eth0 parent 1: classid 1:1 htb rate 100mbit
sudo tc class add dev eth0 parent 1:1 classid 1:10 htb rate 10mbit prio 1
sudo tc class add dev eth0 parent 1:1 classid 1:20 htb rate 90mbit prio 2

# Filtro para VoIP (puertos 5060-5061 SIP, 10000-20000 RTP)
sudo tc filter add dev eth0 protocol ip parent 1:0 prio 1 u32 \
  match ip dport 5060 0xffff flowid 1:10

sudo tc filter add dev eth0 protocol ip parent 1:0 prio 1 u32 \
  match ip sport 5060 0xffff flowid 1:10

# Marcar DSCP para VoIP (EF - Expedited Forwarding)
sudo iptables -t mangle -A OUTPUT -p udp --dport 5060:5061 -j DSCP --set-dscp 46
sudo iptables -t mangle -A OUTPUT -p udp --dport 10000:20000 -j DSCP --set-dscp 46

# 5. Re-test
iperf3 -c voip-server.com -u -b 128K -t 60 --dscp 46
# Jitter: 18ms ✅ (mejorado)
# Packet Loss: 0.2% ✅ (aceptable)
```

```bash
#!/usr/bin/env python3
# capacity_planning.py

import pandas as pd
from sklearn.linear_model import LinearRegression
import numpy as np

# Cargar datos históricos de utilización
df = pd.read_csv('bandwidth_history.csv')
# Columnas: date, avg_mbps

# Preparar datos
df['date'] = pd.to_datetime(df['date'])
df['days'] = (df['date'] - df['date'].min()).dt.days

X = df[['days']].values
y = df['avg_mbps'].values

# Modelo de regresión lineal
model = LinearRegression()
model.fit(X, y)

# Proyectar 6 meses (180 días)
future_days = df['days'].max() + 180
future_usage = model.predict([[future_days]])[0]

print(f"Uso proyectado en 6 meses: {future_usage:.2f} Mbps")
```
