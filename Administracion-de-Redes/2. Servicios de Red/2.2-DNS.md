# 2.2 DNS - Domain Name System

## Descripción

**DNS (Domain Name System)** es el sistema de nombres jerárquico y distribuido que traduce nombres de dominio legibles por humanos (como `www.google.com`) en direcciones IP numéricas (como `142.250.185.46`) que los computadores utilizan para comunicarse. DNS es fundamental para el funcionamiento de Internet y redes empresariales, actuando como la "agenda telefónica" de Internet.

### ¿Por Qué Existe DNS?

```
SIN DNS:
Usuario: "Quiero entrar a www.google.com"
Sistema: "No sé qué es google.com, necesito una IP: 142.250.185.46"
Usuario: "¿Cómo voy a recordar millones de IPs?"

CON DNS:
Usuario: "Quiero entrar a www.google.com"
DNS: "www.google.com es 142.250.185.46"
Sistema: "Conectando a 142.250.185.46..."
Usuario: ✓ Conectado sin recordar números
```

### Jerarquía de DNS

DNS es un sistema **jerárquico descentralizado** con estructura de árbol invertido:

```
                          . (root)
                          |
        ┌─────────────────┼─────────────────┐
        |                 |                 |
      .com              .org              .mx
        |                 |                 |
    ┌───┴───┐         ┌───┴───┐         ┌───┴───┐
    |       |         |       |         |       |
 google  amazon   wikipedia  eff      gob    edu
    |                 |                 |
 ┌──┴──┐           ┌──┴──┐           ┌──┴──┐
www   mail        www   es          www   www
 |                 |                 |
142.250.185.46  208.80.154.224   189.240.97.129
```

**Niveles de la jerarquía:**

1. **Root (.)** - 13 servidores raíz (a.root-servers.net hasta m.root-servers.net)
2. **TLD (Top-Level Domain)** - .com, .org, .net, .mx, .uk, etc.
3. **Second-Level Domain** - google, amazon, wikipedia
4. **Subdominios** - www, mail, ftp, blog
5. **Host específico** - server01.datacenter.empresa.com

### Proceso de Resolución DNS

#### Resolución Recursiva (Típica)

```
CLIENTE                RESOLVER      ROOT    TLD     AUTHORITATIVE
  |                      |            |       |            |
  | 1. www.google.com    |            |       |            |
  |--------------------->|            |       |            |
  |                      |            |       |            |
  |                      | 2. ¿google.com?    |            |
  |                      |----------->|       |            |
  |                      |            |       |            |
  |                      | 3. Pregunta a .com TLD          |
  |                      |<-----------|       |            |
  |                      |                    |            |
  |                      | 4. ¿google.com?    |            |
  |                      |------------------->|            |
  |                      |                    |            |
  |                      | 5. Pregunta a ns1.google.com   |
  |                      |<-------------------|            |
  |                      |                                 |
  |                      | 6. www.google.com?              |
  |                      |-------------------------------->|
  |                      |                                 |
  |                      | 7. 142.250.185.46               |
  |                      |<--------------------------------|
  |                      |                                 |
  | 8. 142.250.185.46    |                                 |
  |<---------------------|                                 |
  |                      |                                 |
```

**Pasos detallados:**

1. **Cliente solicita** www.google.com al resolver DNS configurado (típicamente ISP o 8.8.8.8)
2. **Resolver pregunta a Root Server** "¿Quién maneja .com?"
3. **Root responde** "Pregunta a los servidores TLD de .com"
4. **Resolver pregunta a .com TLD** "¿Quién maneja google.com?"
5. **TLD responde** "Pregunta a ns1.google.com (servidor autoritativo de Google)"
6. **Resolver pregunta a ns1.google.com** "¿Cuál es la IP de www.google.com?"
7. **Servidor autoritativo responde** "142.250.185.46"
8. **Resolver entrega respuesta al cliente** y la almacena en caché

#### Resolución Iterativa

```
CLIENTE                RESOLVER      ROOT    TLD     AUTHORITATIVE
  |                      |            |       |            |
  | 1. www.google.com    |            |       |            |
  |--------------------->|            |       |            |
  |                      |            |       |            |
  |                      | 2. ¿google.com?    |            |
  |                      |----------->|       |            |
  |                      |            |       |            |
  |                      | 3. ns.gtld-servers.net          |
  |                      |<-----------|       |            |
  |                      |                    |            |
Cliente realiza         |                    |            |
consultas iterativas    |                    |            |
(resolver no recursivo) |                    |            |
```

### Tipos de Registros DNS (Resource Records)

| Tipo | Nombre Completo | Propósito | Ejemplo |
|------|----------------|-----------|---------|
| **A** | Address Record | Traduce nombre → IPv4 | `www.empresa.com. IN A 192.168.1.100` |
| **AAAA** | IPv6 Address | Traduce nombre → IPv6 | `www.empresa.com. IN AAAA 2001:db8::1` |
| **CNAME** | Canonical Name | Alias de otro nombre | `blog.empresa.com. IN CNAME www.empresa.com.` |
| **MX** | Mail Exchange | Servidores de correo | `empresa.com. IN MX 10 mail.empresa.com.` |
| **NS** | Name Server | Servidores DNS autoritativos | `empresa.com. IN NS ns1.empresa.com.` |
| **PTR** | Pointer Record | Resolución inversa (IP → nombre) | `100.1.168.192.in-addr.arpa. IN PTR www.empresa.com.` |
| **SOA** | Start of Authority | Información de zona | `empresa.com. IN SOA ns1.empresa.com. admin.empresa.com. 2024033101 3600 600 86400 3600` |
| **TXT** | Text Record | Texto arbitrario (SPF, DKIM, verificación) | `empresa.com. IN TXT "v=spf1 mx -all"` |
| **SRV** | Service Record | Ubicación de servicios | `_ldap._tcp.empresa.com. IN SRV 0 5 389 ldap.empresa.com.` |
| **CAA** | Certification Authority Authorization | Autoridades CA permitidas | `empresa.com. IN CAA 0 issue "letsencrypt.org"` |

### Caché DNS

**El caché es crucial para eficiencia**:

```
Primera consulta a www.google.com:
  Tiempo: 150-300ms (consultas a root, TLD, autoritativo)
  
Consultas subsecuentes (en TTL):
  Tiempo: <5ms (respuesta desde caché)
  
TTL (Time To Live):
  www.google.com. 300 IN A 142.250.185.46
                  ↑
            TTL = 300 segundos (5 minutos)
            
Después de 5 minutos: Caché expira, nueva consulta necesaria
```

## RFCs de Referencia

DNS está definido por una extensa colección de RFCs, comenzando en la década de 1980 y extendiéndose hasta la actualidad.

### RFCs Fundamentales (Núcleo DNS)

```
RFC 1034 - "Domain Names - Concepts and Facilities" (1987)
  • RFC fundamental que define conceptos de DNS
  • Jerarquía de dominios
  • Modelo cliente-servidor
  • Name servers y resolvers
  • Estado: ESTÁNDAR INTERNET

RFC 1035 - "Domain Names - Implementation and Specification" (1987)
  • Implementación técnica de DNS
  • Formato de mensajes DNS
  • Tipos de registros (A, NS, CNAME, SOA, PTR, MX, TXT)
  • Formato de zona files
  • Compresión de mensajes
  • Estado: ESTÁNDAR INTERNET

RFC 2181 - "Clarifications to the DNS Specification" (1997)
  • Clarificaciones y correcciones a RFC 1034/1035
  • TTL de 0 segundos
  • Comportamiento de CNAME
  • Límites de tamaño de labels
```

### RFCs de Tipos de Registro Importantes

```
RFC 1886 - "DNS Extensions to Support IPv6" (1995)
  • Define registro AAAA para direcciones IPv6
  • Posteriormente actualizado por RFC 3596

RFC 3596 - "DNS Extensions to Support IPv6" (2003)
  • Reemplaza RFC 1886
  • AAAA records y resolución inversa IPv6 (ip6.arpa)

RFC 2782 - "A DNS RR for Specifying the Location of Services (DNS SRV)" (2000)
  • Define SRV records
  • Usado por LDAP, Kerberos, SIP, XMPP
  • Formato: _service._proto.name. TTL class SRV priority weight port target

RFC 6844 - "DNS Certification Authority Authorization (CAA) Resource Record" (2013)
  • Define CAA records
  • Control sobre qué CAs pueden emitir certificados
  • Mitigación de emisión fraudulenta de certificados
```

### RFCs de Seguridad (DNSSEC)

```
RFC 4033 - "DNS Security Introduction and Requirements" (2005)
  • Introducción a DNSSEC
  • Amenazas de seguridad en DNS
  • Arquitectura de DNSSEC
  
RFC 4034 - "Resource Records for DNS Security Extensions" (2005)
  • Registros DNSSEC: RRSIG, DNSKEY, DS, NSEC
  • Firma criptográfica de registros DNS
  
RFC 4035 - "Protocol Modifications for DNS Security Extensions" (2005)
  • Modificaciones al protocolo DNS para DNSSEC
  • Validación de firmas
  • Chain of trust

RFC 5155 - "DNS Security (DNSSEC) Hashed Authenticated Denial of Existence" (2008)
  • NSEC3 record (reemplaza NSEC)
  • Previene zone enumeration
  • Hashing de nombres para privacidad

RFC 6698 - "The DNS-Based Authentication of Named Entities (DANE)" (2012)
  • TLSA records
  • Asociación de certificados TLS con nombres DNS
  • Alternativa/complemento a PKI tradicional
```

### RFCs de Operación y Mejores Prácticas

```
RFC 2136 - "Dynamic Updates in the Domain Name System (DNS UPDATE)" (2000)
  • Actualización dinámica de zonas DNS
  • Usado por DHCP para registrar hostnames
  • Integración con Active Directory

RFC 1996 - "A Mechanism for Prompt Notification of Zone Changes (DNS NOTIFY)" (1996)
  • Notificación de servidores secundarios sobre cambios
  • Reduce latencia de propagación de cambios

RFC 5936 - "DNS Zone Transfer Protocol (AXFR)" (2010)
  • Transferencia completa de zona
  • Usado por servidores secundarios

RFC 1995 - "Incremental Zone Transfer in DNS" (1996)
  • IXFR (Incremental Zone Transfer)
  • Solo transfiere cambios (más eficiente que AXFR)

RFC 2308 - "Negative Caching of DNS Queries (DNS NCACHE)" (1998)
  • Caché de respuestas negativas (NXDOMAIN)
  • Reduce carga en servidores autoritativos
  • SOA TTL para controlar caché negativo

RFC 7871 - "Client Subnet in DNS Queries" (2016)
  • EDNS Client Subnet (ECS)
  • Permite CDNs dirigir tráfico geográficamente
  • Usado por Google Public DNS, Cloudflare, etc.
```

### RFCs de Extensiones y Mejoras

```
RFC 6891 - "Extension Mechanisms for DNS (EDNS(0))" (2013)
  • Extiende DNS más allá de 512 bytes
  • Permite paquetes UDP >512 bytes
  • Flags adicionales (DO bit para DNSSEC)
  • OPT pseudo-record
  • Reemplaza RFC 2671

RFC 7858 - "Specification for DNS over Transport Layer Security (TLS)" (2016)
  • DNS over TLS (DoT)
  • Puerto 853
  • Cifrado de consultas DNS
  • Privacidad contra ISPs y eavesdroppers

RFC 8484 - "DNS Queries over HTTPS (DoH)" (2018)
  • DNS over HTTPS
  • Usa puerto 443 (HTTPS estándar)
  • Integración con navegadores web
  • Mayor privacidad y resistencia a censura

RFC 8490 - "DNS Stateful Operations" (2018)
  • DNS sobre conexiones persistentes
  • Reduce overhead de handshakes
```

### RFCs de Internacionalización

```
RFC 5891 - "Internationalized Domain Names in Applications (IDNA)" (2010)
  • Dominios con caracteres no-ASCII
  • Punycode encoding (ejemplo: münchen.de → xn--mnchen-3ya.de)
  • Soporte para idiomas no-latinos
```

### Resumen de RFCs por Categoría

| Categoría | RFCs Principales | Propósito |
|-----------|------------------|-----------|
| **Fundamentos** | 1034, 1035, 2181 | Definición base de DNS |
| **IPv6** | 3596 | Soporte IPv6 (AAAA) |
| **DNSSEC** | 4033, 4034, 4035, 5155 | Seguridad y autenticación |
| **Operación** | 1995, 1996, 2136, 5936 | Transferencias, updates dinámicos |
| **Extensiones** | 6891 (EDNS), 7858 (DoT), 8484 (DoH) | Mejoras modernas |
| **Tipos de Registro** | 2782 (SRV), 6844 (CAA) | Registros especializados |

## Objetivo

### Propósitos Principales de DNS

1. **Traducción Nombre → IP**
   - Permitir acceso a recursos mediante nombres memorables
   - Abstracción de direcciones IP subyacentes
   - Facilitar cambios de infraestructura sin afectar usuarios

2. **Descentralización y Escalabilidad**
   - Sistema distribuido globalmente
   - Sin punto único de falla
   - Millones de dominios administrados independientemente

3. **Servicios de Resolución Inversa**
   - PTR records: IP → nombre
   - Verificación de servidores de correo (anti-spam)
   - Logging y auditoría de conexiones

4. **Descubrimiento de Servicios**
   - MX records para correo electrónico
   - SRV records para servicios (LDAP, SIP, Kerberos)
   - TXT records para verificación (SPF, DKIM, DMARC)

5. **Load Balancing y Redundancia**
   - Múltiples registros A para un nombre (round-robin)
   - GeoDNS: respuestas según ubicación geográfica
   - Failover automático entre servidores

### Casos de Uso Reales

```
NAVEGACIÓN WEB:
- Usuario ingresa www.facebook.com en navegador
- DNS resuelve a 157.240.22.35
- Navegador se conecta a esa IP
- Página cargada

RED CORPORATIVA:
- DNS interno: server01.empresa.local → 192.168.10.50
- DNS externo: www.empresa.com → IP pública
- Split-horizon DNS: respuestas diferentes interna/externamente

CORREO ELECTRÓNICO:
- MX record: empresa.com → mail.empresa.com (prioridad 10)
- Servidor de correo consulta MX para entregar email
- SPF/DKIM en TXT records valida remitente

SERVICIOS EMPRESARIALES:
- SRV record: _ldap._tcp.empresa.com → ldap.empresa.com:389
- Clientes descubren servicios automáticamente
- Kerberos usa SRV para KDCs

CDN y GEOLOCALIZACION:
- www.netflix.com resuelve a IP diferente según ubicación
- 192.0.2.50 en México
- 203.0.113.75 en Europa
- Reduce latencia, mejora experiencia
```

**BIND** es el servidor DNS más usado en Internet, especialmente en Linux/Unix.

```bash
# Actualizar repositorios
```

#### Configuración: DNS Caché/Forwarder (Más Simple)

**Caso de uso:** Servidor DNS interno que reenvía consultas a DNS externo (8.8.8.8)

```bash
# Editar opciones
sudo nano /etc/bind/named.conf.options
```

```
// /etc/bind/named.conf.options

options {
    // Directorio de trabajo
    directory "/var/cache/bind";

    // Forwarders: DNS upstream (Google Public DNS)
    forwarders {
        8.8.8.8;
        8.8.4.4;
    };

    // Forward only: siempre usar forwarders, no consultas recursivas
    forward only;

    // ACL: quién puede hacer consultas
    allow-query { 
        localhost;
        192.168.1.0/24;  // Red interna
    };

    // Deshabilitar transferencias de zona (seguridad)
    allow-transfer { none; };

    // Escuchar en IPv4 (deshabilitar IPv6 si no se usa)
    listen-on { 192.168.1.10; 127.0.0.1; };
    listen-on-v6 { none; };

    // DNSSEC validation
    dnssec-validation auto;

    // Recursión habilitada (necesaria para resolver)
    recursion yes;
};
```

```bash
# Verificar sintaxis
sudo named-checkconf

# Reiniciar BIND
sudo systemctl restart bind9

# Ver logs
sudo journalctl -u bind9 -f
```

**Prueba desde cliente:**

```bash
# Configurar este servidor como DNS
sudo nano /etc/resolv.conf
nameserver 192.168.1.10

# Prueba
nslookup google.com
# Debe resolver correctamente
```

#### Configuración: DNS Autoritativo (Zona Propia)

**Caso de uso:** DNS interno para dominio `empresa.local`

##### 1. Configurar zona en named.conf.local

```bash
sudo nano /etc/bind/named.conf.local
```

```
// /etc/bind/named.conf.local

// Zona directa (nombre → IP)
zone "empresa.local" {
    type master;
    file "/etc/bind/zones/db.empresa.local";
    allow-transfer { 192.168.1.11; };  // Servidor DNS secundario
    allow-query { any; };
};

// Zona inversa (IP → nombre)
zone "1.168.192.in-addr.arpa" {
    type master;
    file "/etc/bind/zones/db.192.168.1";
    allow-transfer { 192.168.1.11; };
    allow-query { any; };
};
```

##### 2. Crear archivo de zona directa

```bash
# Crear directorio para zonas
sudo mkdir -p /etc/bind/zones

# Crear zona directa
sudo nano /etc/bind/zones/db.empresa.local
```

```
; /etc/bind/zones/db.empresa.local
; Zona DNS para empresa.local

$TTL    3600
@       IN      SOA     ns1.empresa.local. admin.empresa.local. (
                        2024033101      ; Serial (YYYYMMDDnn)
                        3600            ; Refresh (1 hora)
                        600             ; Retry (10 minutos)
                        86400           ; Expire (1 día)
                        3600 )          ; Negative Cache TTL (1 hora)

; Name Servers
@       IN      NS      ns1.empresa.local.
@       IN      NS      ns2.empresa.local.

; A Records (IPv4)
ns1             IN      A       192.168.1.10
ns2             IN      A       192.168.1.11
server01        IN      A       192.168.1.50
server02        IN      A       192.168.1.51
web             IN      A       192.168.1.100
web             IN      A       192.168.1.101    ; Load balancing (round-robin)
mail            IN      A       192.168.1.120
ftp             IN      A       192.168.1.130

; CNAME Records (Aliases)
www             IN      CNAME   web.empresa.local.
blog            IN      CNAME   web.empresa.local.
intranet        IN      CNAME   server01.empresa.local.

; MX Records (Mail Exchange)
@               IN      MX      10      mail.empresa.local.
@               IN      MX      20      mail-backup.empresa.local.

; TXT Records (SPF, DKIM, etc.)
@               IN      TXT     "v=spf1 mx -all"
_dmarc          IN      TXT     "v=DMARC1; p=quarantine; rua=mailto:admin@empresa.local"

; SRV Records (Services)
_ldap._tcp      IN      SRV     0 5 389 ldap.empresa.local.
_kerberos._tcp  IN      SRV     0 5 88  kdc.empresa.local.

; AAAA Records (IPv6) - Opcional
web             IN      AAAA    2001:db8:1::100
```

##### 3. Crear archivo de zona inversa

```bash
sudo nano /etc/bind/zones/db.192.168.1
```

```
; /etc/bind/zones/db.192.168.1
; Zona inversa para 192.168.1.0/24

$TTL    3600
@       IN      SOA     ns1.empresa.local. admin.empresa.local. (
                        2024033101      ; Serial
                        3600            ; Refresh
                        600             ; Retry
                        86400           ; Expire
                        3600 )          ; Negative Cache TTL

; Name Servers
@       IN      NS      ns1.empresa.local.
@       IN      NS      ns2.empresa.local.

; PTR Records (IP → nombre)
10      IN      PTR     ns1.empresa.local.
11      IN      PTR     ns2.empresa.local.
50      IN      PTR     server01.empresa.local.
51      IN      PTR     server02.empresa.local.
100     IN      PTR     web.empresa.local.
101     IN      PTR     web.empresa.local.
120     IN      PTR     mail.empresa.local.
130     IN      PTR     ftp.empresa.local.
```

##### 4. Verificar configuración

```bash
# Verificar sintaxis de named.conf
sudo named-checkconf

# Verificar zona directa
sudo named-checkzone empresa.local /etc/bind/zones/db.empresa.local
# Output: zone empresa.local/IN: loaded serial 2024033101
#         OK

# Verificar zona inversa
sudo named-checkzone 1.168.192.in-addr.arpa /etc/bind/zones/db.192.168.1
# Output: zone 1.168.192.in-addr.arpa/IN: loaded serial 2024033101
#         OK

# Reiniciar BIND
sudo systemctl restart bind9

# Verificar estado
sudo systemctl status bind9
```

##### 5. Pruebas

```bash
# Desde el mismo servidor o cliente configurado

# Resolución directa

# Debe responder: 192.168.1.50

# Resolución inversa
```

#### Configuración: DNS Secundario (Slave)

**En servidor secundario (192.168.1.11):**

```
// /etc/bind/named.conf.local

zone "empresa.local" {
    type slave;
    file "/var/cache/bind/db.empresa.local";
    masters { 192.168.1.10; };  // IP del DNS primario
};

zone "1.168.192.in-addr.arpa" {
    type slave;
    file "/var/cache/bind/db.192.168.1";
    masters { 192.168.1.10; };
};
```

**En servidor primario, permitir transferencias:**

```
// En named.conf.local del primario
zone "empresa.local" {
    type master;
    file "/etc/bind/zones/db.empresa.local";
    allow-transfer { 192.168.1.11; };  // IP del secundario
    notify yes;  // Notificar cambios automáticamente
};
```

**Prueba de transferencia de zona:**

```bash
# Desde secundario, forzar transferencia
sudo rndc reload

# Verificar que se transfirió
sudo ls -lh /var/cache/bind/
# Debe aparecer db.empresa.local
```

### Opción 2: Unbound (DNS Recursivo Moderno)

**Unbound** es un resolver DNS recursivo moderno, seguro y rápido, ideal para caching DNS.

```bash
# Instalar Unbound
sudo apt install unbound -y

# Configuración básica
sudo nano /etc/unbound/unbound.conf.d/myconfig.conf

server:
    interface: 0.0.0.0
    access-control: 192.168.1.0/24 allow
    do-ip4: yes
    do-ip6: no
    do-udp: yes
    do-tcp: yes
    hide-identity: yes
    hide-version: yes
    
    # Forwarders
    forward-zone:
        name: "."
        forward-addr: 8.8.8.8
        forward-addr: 8.8.4.4

# Iniciar
sudo systemctl restart unbound
```

```
   - Name: server01
```

## Aspectos de Seguridad

### Vulnerabilidades Comunes de DNS

#### 1. DNS Cache Poisoning (Envenenamiento de Caché)

**Problema:**
- Atacante inyecta registros falsos en caché del resolver
- Usuarios son redirigidos a sitios maliciosos
- Robo de credenciales, malware, phishing

**Ataque Kaminsky (2008):**
```
Atacante consulta: subdomain12345.banco.com
  ↓
Mientras resolver espera respuesta, atacante inunda con respuestas falsas:
  Transaction ID: guess1, banco.com → 1.2.3.4 (IP maliciosa)
  Transaction ID: guess2, banco.com → 1.2.3.4
  Transaction ID: guess3, banco.com → 1.2.3.4
  ...
  ↓
Si adivina Transaction ID correcto: caché envenenado
  ↓
Todos los usuarios que consulten banco.com → 1.2.3.4 (sitio falso)
```

**Mitigaciones:**
- **Randomización de puertos fuente** (no solo 53)
- **Transaction ID aleatorio** (16 bits)
- **0x20 encoding** (case randomization)
- **DNSSEC** (firma criptográfica)

---

#### 2. DNS Amplification DDoS

**Problema:**
- Atacante envía consulta DNS pequeña con IP spoofed (víctima)
- Servidor DNS responde con respuesta grande a la víctima
- Factor de amplificación: 50-100x

**Ataque:**
```
Atacante → Consulta 60 bytes a DNS abierto (IP fuente: víctima)
              "ANY google.com" o "TXT _dmarc.google.com"
  ↓
DNS responde → 3000 bytes a víctima
  ↓
Amplificación: 50x
  ↓
10 Gbps atacante → 500 Gbps tráfico a víctima (DDoS)
```

**Mitigaciones:**
```
1. ACLs: Permitir consultas solo desde redes autorizadas
   allow-query { 192.168.1.0/24; };

2. Rate Limiting (RRL)
   rate-limit {
       responses-per-second 5;
       window 5;
   };

3. Response Policy Zones (RPZ) - filtrar dominios maliciosos

4. Deshabilitar recursión para Internet público
   recursion no;  // Solo para servidores autoritativos públicos
```

---

#### 3. DNS Tunneling (Exfiltración de Datos)

**Problema:**
- Malware usa consultas DNS para exfiltrar datos
- DNS suele estar permitido por firewalls
- Datos codificados en subdominios

**Ejemplo:**
```
Datos a exfiltrar: "password123"
  ↓
Codificado en consultas DNS:
  cGFzc3dvcmQxMjM.malware-c2.com
  YWRtaW4ucGFzc3dvcmQ.malware-c2.com
  ↓
Servidor C&C recibe datos en consultas
```

**Detección:**
- Monitorear consultas con subdominios excesivamente largos
- Detectar patrones inusuales (alta frecuencia de consultas a mismo dominio)
- Analizar entropía de subdominios (texto aleatorio)
- Usar herramientas: DNSQuerySniffer, RITA

---

#### 4. DNS Hijacking / Pharming

**Problema:**
- Modificación de configuración DNS del usuario
- Redirección a DNS malicioso
- Resoluciones falsas sin necesidad de cache poisoning

**Vectores:**
```
- Malware modifica /etc/resolv.conf o DNS de adaptador de red
- Compromiso de router (DNS del DHCP alterado)
- Ataque a ISP (BGP hijacking del DNS del ISP)
```

**Prevención:**
- Usar DNS confiable (8.8.8.8, 1.1.1.1)
- DNS over TLS (DoT) o DNS over HTTPS (DoH)
- Monitorear cambios en configuración DNS
- Validación DNSSEC

---

### DNSSEC (DNS Security Extensions)

**DNSSEC** agrega autenticación criptográfica a DNS, previniendo cache poisoning.

#### Conceptos Clave

```
ZONA SIN DNSSEC:
www.empresa.com. 300 IN A 192.168.1.100
  ↑
Cualquiera puede falsificar esta respuesta

ZONA CON DNSSEC:
www.empresa.com. 300 IN A 192.168.1.100
www.empresa.com. 300 IN RRSIG A 13 3 300 ... (firma digital)
  ↑
Respuesta está firmada, solo el dueño de la clave privada puede firmar
Resolver valida la firma antes de confiar en la respuesta
```

**Registros DNSSEC:**

- **DNSKEY**: Clave pública de la zona
- **RRSIG**: Firma digital de un conjunto de registros
- **DS (Delegation Signer)**: Hash de DNSKEY, almacenado en zona padre (crea chain of trust)
- **NSEC/NSEC3**: Prueba de no existencia de un nombre

#### Chain of Trust

```
. (root) ← DNSKEY (root keys: KSK)
  │
  ├─→ .com DS record (signed by root)
      │
      ├─→ empresa.com DS record (signed by .com)
          │
          └─→ www.empresa.com A record (signed by empresa.com)

Resolver valida cada nivel:
1. Root key es trust anchor (conocido previamente)
2. Valida firma de .com DS con root key
3. Valida firma de empresa.com DS con .com key
4. Valida firma de www.empresa.com con empresa.com key
5. Si todas válidas → respuesta confiable
   Si alguna falla → respuesta rechazada
```

#### Implementar DNSSEC en BIND

```bash
# 1. Generar claves para la zona
cd /etc/bind/zones
sudo dnssec-keygen -a RSASHA256 -b 2048 -n ZONE empresa.local  # ZSK (Zone Signing Key)
sudo dnssec-keygen -a RSASHA256 -b 4096 -n ZONE -f KSK empresa.local  # KSK (Key Signing Key)

# Output:
# Kempresa.local.+008+12345 (ZSK)
# Kempresa.local.+008+67890 (KSK)

# 2. Incluir claves en zona
sudo nano /etc/bind/zones/db.empresa.local

$INCLUDE Kempresa.local.+008+12345.key  ; ZSK
$INCLUDE Kempresa.local.+008+67890.key  ; KSK

# 3. Firmar la zona
sudo dnssec-signzone -A -3 $(head -c 1000 /dev/random | sha1sum | cut -b 1-16) \
     -N INCREMENT -o empresa.local -t db.empresa.local

# Output: db.empresa.local.signed

# 4. Actualizar named.conf.local para usar zona firmada
zone "empresa.local" {
    type master;
    file "/etc/bind/zones/db.empresa.local.signed";
    allow-transfer { none; };
};

# 5. Reiniciar BIND
sudo systemctl restart bind9

# 6. Verificar DNSSEC
dig @127.0.0.1 empresa.local DNSKEY
dig @127.0.0.1 empresa.local +dnssec
```

**Validación DNSSEC en resolver:**

```
// /etc/bind/named.conf.options

options {
    dnssec-validation auto;  # Habilitar validación
    # ...
};
```

### DNS over TLS (DoT) y DNS over HTTPS (DoH)

**Problema:** Consultas DNS tradicionales viajan en texto plano, visibles para ISPs y eavesdroppers.

#### DNS over TLS (DoT)

```
CONSULTA DNS TRADICIONAL:
Cliente → UDP puerto 53 → DNS Server
         (texto plano, visible)

CONSULTA DNS over TLS:
Cliente → TLS puerto 853 → DNS Server
         (cifrado, privado)
```

```bash
sudo nano /etc/systemd/resolved.conf

[Resolve]

```

**Ventaja:** Usa puerto 443 (HTTPS), más difícil de bloquear.

**Navegadores modernos (Firefox, Chrome) soportan DoH:**

```
  Settings → Privacy and Security → Security
  → Use secure DNS → Cloudflare (1.1.1.1)
```

**Proveedores DoH públicos:**
- Cloudflare: `https://cloudflare-dns.com/dns-query`

- Quad9: `https://dns.quad9.net/dns-query`

### Hardening de Servidor DNS

#### 1. ACLs (Access Control Lists)

```
// /etc/bind/named.conf.options

acl "trusted" {
    127.0.0.1;
    192.168.1.0/24;
    192.168.10.0/24;
};

options {
    allow-query { trusted; };        # Solo trusted puede consultar
    allow-recursion { trusted; };    # Solo trusted puede recursión
    allow-transfer { none; };         # Nadie puede hacer AXFR (excepto explícito)
    allow-update { none; };           # No dynamic updates
};
```

#### 2. Ocultar Versión de BIND

```
options {
    version "DNS Server";  # No revelar versión real
    hostname "dns";        # No revelar hostname real
};
```

#### 3. Rate Limiting (Mitigar DDoS)

```
options {
    rate-limit {
        responses-per-second 5;
        window 5;
        ipv4-prefix-length 24;
        log-only no;
    };
};
```

#### 4. Separar Recursivo de Autoritativo

**Buena práctica:** No usar el mismo servidor para recursión (caché) y autoritativo.

```
SERVIDOR RECURSIVO (interno):
- Resuelve consultas para usuarios internos
- Caché habilitado
- No expuesto a Internet

SERVIDOR AUTORITATIVO (externo):
- Solo responde por dominios propios
- Recursión deshabilitada
- Expuesto a Internet
```

#### 5. Firewall

```bash
# iptables - permitir DNS solo desde redes internas
sudo iptables -A INPUT -p udp --dport 53 -s 192.168.1.0/24 -j ACCEPT
sudo iptables -A INPUT -p tcp --dport 53 -s 192.168.1.0/24 -j ACCEPT
sudo iptables -A INPUT -p udp --dport 53 -j DROP
sudo iptables -A INPUT -p tcp --dport 53 -j DROP
```

### Mejores Prácticas de Seguridad

```
✓ Implementar DNSSEC en dominios propios
✓ Validar DNSSEC en resolvers
✓ ACLs restrictivas (allow-query, allow-recursion)
✓ Rate limiting contra DDoS
✓ Ocultar versión de software DNS
✓ Separar DNS recursivo de autoritativo
✓ Monitoreo de consultas anómalas (tunneling)
✓ Logs centralizados (SIEM)
✓ Firewall: DNS solo desde redes autorizadas
✓ DNS redundante (primario + secundario)
✓ Backups de archivos de zona
✓ Actualizar software DNS regularmente
✓ Considerar DoT/DoH para privacidad

✗ NO habilitar recursión en DNS público autoritativo
✗ NO exponer servidores DNS internos a Internet
✗ NO usar DNS abierto (open resolver) sin rate limiting
✗ NO ignorar alertas de consultas anómalas
✗ NO usar TTLs excesivamente largos (dificulta cambios)
```

## Alta Disponibilidad y Load Balancing

### Arquitectura DNS Redundante

```
┌──────────────────────────────────────────────────────────┐
│                    INTERNET                              │
└───────────────────┬──────────────────────────────────────┘
                    │
         ┌──────────┴──────────┐
         │                     │
    NS1 (Primary)         NS2 (Secondary)
    192.0.2.1            198.51.100.1
    8.8.8.8              8.8.4.4
         │                     │
         └──────────┬──────────┘
                    │
         Clientes obtienen lista:
         NS1: 192.0.2.1
         NS2: 198.51.100.1
           ↓
         Cliente intenta NS1 primero
         Si falla → intenta NS2
```

### DNS Round-Robin (Load Balancing)

```
; Múltiples registros A para mismo nombre
www.empresa.com.  300  IN  A  192.168.1.100
www.empresa.com.  300  IN  A  192.168.1.101
www.empresa.com.  300  IN  A  192.168.1.102

Consultas sucesivas retornan IPs en orden rotativo:
  Consulta 1 → 192.168.1.100
  Consulta 2 → 192.168.1.101
  Consulta 3 → 192.168.1.102
  Consulta 4 → 192.168.1.100 (ciclo)
```

**Limitaciones:**
- No detecta servidores caídos
- No considera geolocalización
- No balancea cargas reales (cliente cachea)

**Solución avanzada:** GeoDNS o servicios como AWS Route 53, Cloudflare DNS

### Split-Horizon DNS (Vista Interna/Externa)

**Problema:** Necesitamos que `www.empresa.com` resuelva a IP interna para usuarios internos, e IP pública para externos.

```
CONFIGURACIÓN BIND con Views:

// /etc/bind/named.conf.local

acl "internal" { 192.168.0.0/16; 10.0.0.0/8; };

view "internal" {
    match-clients { internal; };
    
    zone "empresa.com" {
        type master;
        file "/etc/bind/zones/internal/db.empresa.com";
    };
};

view "external" {
    match-clients { any; };
    
    zone "empresa.com" {
        type master;
        file "/etc/bind/zones/external/db.empresa.com";
    };
};
```

```
// /etc/bind/zones/internal/db.empresa.com
www  IN  A  192.168.1.100  ; IP interna

// /etc/bind/zones/external/db.empresa.com
www  IN  A  203.0.113.50   ; IP pública
```

## Conclusión

DNS es el servicio que hace Internet usable, traduciendo nombres memorables en direcciones IP. Su correcta implementación, con énfasis en seguridad (DNSSEC, DoT/DoH), redundancia (servidores primario/secundario) y monitoreo, es fundamental para cualquier infraestructura de red moderna.

**Puntos Clave:**
- DNS es jerárquico y distribuido (root → TLD → autoritativo)
- BIND es el servidor más popular (Linux/Unix)
- Tipos de registro: A/AAAA, CNAME, MX, NS, TXT, SRV, PTR
- DNSSEC previene cache poisoning mediante firmas criptográficas
- DoT/DoH proporcionan privacidad en consultas DNS
- Separar DNS recursivo (interno) de autoritativo (público)
- Redundancia con servidores secundarios y AXFR/IXFR
- Monitoreo de consultas anómalas (tunneling, DDoS)
