# 2.4 FTP y TFTP - Protocolos Legacy de Transferencia de Archivos

## ⚠️ ADVERTENCIA IMPORTANTE

**FTP (File Transfer Protocol) y TFTP (Trivial File Transfer Protocol) son protocolos OBSOLETOS e INSEGUROS.** Este documento los cubre como contexto histórico y pedagógico, pero **NO se recomienda su uso en producción moderna.**

```
┌─────────────────────────────────────────────────────────────┐
│  ❌ NO USAR EN PRODUCCIÓN:                                  │
│     • FTP - Credenciales y datos en texto plano             │
│     • TFTP - Sin autenticación, sin cifrado                 │
│                                                             │
│  ✅ USAR ALTERNATIVAS MODERNAS:                             │
│     • SFTP (SSH File Transfer Protocol)                     │
│     • SCP (Secure Copy over SSH)                            │
│     • FTPS (FTP over TLS) - Si legacy es requerido         │
│     • HTTPS/WebDAV                                          │
│     • Rsync sobre SSH                                       │
│     • Cloud Storage (S3, Azure Blob, GCP Storage)           │
│     • Git/GitHub para código fuente                         │
└─────────────────────────────────────────────────────────────┘
```

## Descripción

### FTP (File Transfer Protocol)

**FTP** fue diseñado en 1971 (RFC 114, actualizado en RFC 959 en 1985) para transferir archivos entre sistemas en ARPANET. Durante décadas fue el estándar para compartir archivos en redes.

#### Arquitectura de FTP

```
CLIENTE FTP                                    SERVIDOR FTP
┌──────────────┐                              ┌──────────────┐
│   Usuario    │                              │  Proceso FTP │
│              │                              │   (puerto 21)│
└───────┬──────┘                              └──────┬───────┘
        │                                            │
        │  CANAL DE CONTROL (puerto 21)             │
        │  - Comandos: USER, PASS, LIST, RETR, STOR │
        │  - ⚠️ TEXTO PLANO (credenciales visibles) │
        │<──────────────────────────────────────────>│
        │                                            │
        │  CANAL DE DATOS (puerto 20 o aleatorio)   │
        │  - Transferencia de archivos              │
        │  - Listados de directorios                │
        │  - ⚠️ SIN CIFRADO (archivos visibles)     │
        │<══════════════════════════════════════════>│
        │                                            │
```

**Dos modos de conexión:**

1. **Modo Activo (PORT):**
```
Cliente abre puerto aleatorio → servidor se conecta de vuelta
  Problema: Bloqueado por firewalls/NAT
  Cliente puerto 1234 ← Servidor puerto 20 (datos)
```

2. **Modo Pasivo (PASV):**
```
Servidor abre puerto aleatorio → cliente se conecta
  Solución para NAT/firewalls
  Cliente puerto 1234 → Servidor puerto aleatorio (datos)
```

### TFTP (Trivial File Transfer Protocol)

**TFTP** es una versión ultra-simplificada de FTP (RFC 1350, 1992), diseñada para:
- Boot de diskless workstations (PXE boot)
- Transferencia de configuraciones a routers/switches
- Firmware updates de dispositivos de red

```
CARACTERÍSTICAS TFTP:

✓ Extremadamente simple (solo 5 tipos de paquetes)
✓ Usa UDP (puerto 69) - sin conexión persistente
✓ Pequeño (cabe en ROM de dispositivos embebidos)

❌ SIN autenticación (cualquiera puede conectar)
❌ SIN cifrado (todo en texto plano)
❌ SIN listado de directorios (cliente debe saber nombre de archivo)
❌ SIN manejo de permisos
❌ SIN compresión
❌ SIN resumir transferencias interrumpidas
```

**Flujo de Transferencia TFTP:**

```
CLIENTE                                    SERVIDOR TFTP
  │                                              │
  │  1. RRQ (Read Request) - Solicitar archivo  │
  │     Archivo: "config.txt", Mode: octet      │
  │─────────────────────────────────────────────>│
  │                                              │
  │  2. DATA (bloque 1, 512 bytes)              │
  │<─────────────────────────────────────────────│
  │                                              │
  │  3. ACK (bloque 1)                          │
  │─────────────────────────────────────────────>│
  │                                              │
  │  4. DATA (bloque 2, 512 bytes)              │
  │<─────────────────────────────────────────────│
  │                                              │
  │  5. ACK (bloque 2)                          │
  │─────────────────────────────────────────────>│
  │                                              │
  │  ... (continúa hasta fin de archivo)        │
  │                                              │
  │  N. DATA (bloque final, <512 bytes)         │
  │<─────────────────────────────────────────────│
  │                                              │
  │  ACK (bloque final)                         │
  │─────────────────────────────────────────────>│
  │                                              │
```

### 3. Vulnerabilidades Comunes FTP

#### Bounce Attack (FTP Bounce)

```
ATAQUE:
1. Atacante se conecta a servidor FTP vulnerable
2. Usa comando PORT para que servidor FTP se conecte a víctima
3. Servidor FTP actúa como proxy para escanear puertos de víctima

Comando FTP malicioso:
  PORT 192,168,1,50,0,22
  (Servidor FTP intenta conectar a 192.168.1.50:22)
  
Resultado: Port scanning usando servidor FTP como proxy
```

#### Anonymous FTP Misconfiguration

```
PROBLEMA:
Servidores FTP permiten login "anonymous" con cualquier password

$ ftp servidor-vulnerable.com
Name: anonymous
Password: cualquier-cosa@example.com
230 Login successful

Riesgo:
  - Acceso público a archivos sensibles
  - Subida de malware (si write habilitado)
  - Distribución de contenido ilegal
```

#### Brute Force Attacks

```
FTP es objetivo fácil para fuerza bruta:

#!/bin/bash
# ftp-brute.sh (simplificado)

for pass in $(cat passwords.txt); do
  ftp -n servidor.com <<EOF
  user admin $pass
  quit
EOF
done

Sin rate limiting ni account lockout:
  Puede probar miles de passwords rápidamente
```

### 4. Problemas de TFTP

#### Sin Autenticación

```
CUALQUIER cliente puede:
  - Leer archivos (si conoce el nombre)
  - Escribir archivos (si el directorio lo permite)

$ tftp 192.168.1.1
tftp> get startup-config
(Descarga configuración de router sin credenciales)

tftp> put malicious-config startup-config
(Sobreescribe configuración sin autenticación)
```

#### Amplificación DDoS

```
TFTP puede ser abusado para ataques de amplificación:

Atacante envía RRQ pequeño con IP spoofed (víctima):
  Source IP: víctima (spoofed)
  Destination: servidor TFTP
  Payload: 20 bytes (Read Request)

Servidor TFTP responde:
  Destination: víctima
  Payload: archivo de 10MB

Amplificación: 500,000x (20 bytes → 10MB)
```

## RFCs de Referencia

### FTP (File Transfer Protocol)

```
RFC 959 - "File Transfer Protocol (FTP)" (1985)
  • Definición estándar de FTP
  • Comandos, códigos de respuesta
  • Modo activo y pasivo
  • Estado: ESTÁNDAR INTERNET (pero OBSOLETO en práctica)

RFC 2228 - "FTP Security Extensions" (1997)
  • Extensiones de seguridad para FTP
  • TLS/SSL integration (base para FTPS)
  • No resuelve completamente los problemas

RFC 2428 - "FTP Extensions for IPv6 and NATs" (1998)
  • Comandos EPRT y EPSV para IPv6
  • Mejor compatibilidad con NAT

RFC 4217 - "Securing FTP with TLS" (2005)
  • FTPS (FTP over TLS) especificación
  • Cifrado de canal de control y datos
  • Mejora seguridad pero no resuelve problemas de diseño
```

### TFTP (Trivial File Transfer Protocol)

```
RFC 1350 - "The TFTP Protocol (Revision 2)" (1992)
  • Definición estándar de TFTP
  • 5 tipos de paquetes (RRQ, WRQ, DATA, ACK, ERROR)
  • UDP puerto 69
  • Estado: ESTÁNDAR INTERNET

RFC 2347 - "TFTP Option Extension" (1998)
  • Extensiones opcionales (block size, timeout)

RFC 2348 - "TFTP Blocksize Option" (1998)
  • Permite bloques >512 bytes (mejora rendimiento)

RFC 2349 - "TFTP Timeout Interval and Transfer Size Options" (1998)
  • Negociación de timeout y tamaño de transferencia
```

## Objetivo (Contexto Histórico)

### Propósitos Originales de FTP/TFTP

**FTP fue diseñado para:**
1. Transferencia eficiente de archivos grandes
2. Listado de directorios remotos
3. Gestión de archivos (crear, eliminar, renombrar)
4. Interoperabilidad entre sistemas heterogéneos (Unix, VMS, mainframes)

**TFTP fue diseñado para:**
1. PXE boot (diskless workstations)
2. Firmware updates de routers/switches
3. Backup/restore de configuraciones de red
4. Entornos con recursos limitados (ROM pequeña)

### Casos de Uso Legítimos HISTÓRICOS

```
DÉCADA 1980-2000:
✓ Distribución de software (drivers, patches)
✓ Hosting de archivos públicos (mirrors, ISO images)
✓ Backup de servidores (scripts nocturnus)
✓ Intercambio de archivos interdepartamental

DÉCADA 2000-2010:
⚠️ Gradual migración a SFTP/FTPS
⚠️ FTP relegado a sistemas legacy
⚠️ TFTP solo en equipos de red (routers, switches)

DÉCADA 2010-2026:
❌ FTP considerado inseguro (violación de compliance)
❌ TFTP solo en entornos muy específicos (PXE boot interno)
✅ SFTP/HTTPS/Cloud Storage son estándar
```

## ⚠️ Por Qué YA NO Usar FTP/TFTP

### Razones de Seguridad

```
1. EXPOSICIÓN DE CREDENCIALES
   - Passwords en texto plano capturables con Wireshark
   - Violación de PCI-DSS, HIPAA, SOX, GDPR

2. EXPOSICIÓN DE DATOS
   - Archivos transferidos sin cifrado
   - Propiedad intelectual, PII, PHI expuestos

3. FALTA DE INTEGRIDAD
   - Sin verificación de que archivo no fue modificado en tránsito
   - Ataques MITM pueden inyectar malware

4. AUTENTICACIÓN DÉBIL (FTP) / INEXISTENTE (TFTP)
   - Susceptible a brute force
   - Sin soporte para 2FA, SSO, certificados

5. PROBLEMAS CON FIREWALLS/NAT
   - FTP requiere múltiples puertos (20, 21, rangos dinámicos)
   - Complicado de configurar en firewalls modernos
   - TFTP usa UDP (a veces bloqueado)
```

### Razones de Cumplimiento Normativo

| Estándar | Requisito | FTP/TFTP Cumple? | Alternativa |
|----------|-----------|------------------|-------------|
| **PCI-DSS 4.0** | Cifrado de datos de tarjetas en transmisión | ❌ NO | SFTP, FTPS, HTTPS |
| **HIPAA** | Cifrado de PHI (Protected Health Information) | ❌ NO | SFTP con FIPS 140-2 |
| **GDPR** | Protección de datos personales en tránsito | ❌ NO | SFTP, HTTPS |
| **SOX** | Controles de acceso y auditoría | ❌ Insuficiente | SFTP con logging detallado |
| **ISO 27001** | Cifrado de información sensible | ❌ NO | SFTP, MFT con cifrado |
| **NIST 800-52** | Uso de TLS 1.2+ | ❌ NO (FTP plano) | FTPS, HTTPS |

**Ejemplo de auditoría:**
```
Auditor: "¿Cómo protegen datos de tarjetas en transmisión?"
Admin: "Usamos FTP para backups de la base de datos."
Auditor: "❌ INCUMPLIMIENTO. FTP transmite sin cifrado.
          Multa: $50,000-$500,000 (PCI-DSS).
          Plazo corrección: 30 días o suspensión de procesamiento."
```

## ✅ Alternativas Modernas Recomendadas

### 1. SFTP (SSH File Transfer Protocol)

**SFTP es el reemplazo moderno de FTP.**

```
VENTAJAS:
✅ Cifrado completo (credenciales + datos) vía SSH
✅ Autenticación por password O llaves públicas
✅ Un solo puerto (22) - firewall-friendly
✅ Integridad de datos (HMAC)
✅ Listado de directorios, permisos Unix
✅ Resumir transferencias interrumpidas
✅ Compresión integrada
✅ Cumple PCI-DSS, HIPAA, GDPR

DESVENTAJAS:
⚠️ Ligeramente más overhead que FTP (cifrado)
⚠️ No es FTP (protocolos incompatibles)
```

**Instalación y Uso (Ver archivo 2.3-SSH.md):**

```bash
# Servidor: Ya incluido con OpenSSH Server
sudo apt install openssh-server

# Cliente: Conectar
sftp usuario@servidor.com

# Comandos interactivos
sftp> ls                    # Listar archivos remotos
sftp> cd /var/www           # Cambiar directorio remoto
sftp> get archivo.txt       # Descargar
sftp> put local.txt         # Subir
sftp> exit

# Comando único (no interactivo)
echo "get /remoto/archivo.txt" | sftp usuario@servidor

# Desde GUI (FileZilla, WinSCP)
# Protocolo: SFTP
# Puerto: 22
```

### 2. SCP (Secure Copy Protocol)

**SCP es más simple que SFTP, ideal para copias rápidas.**

```bash
# Copiar archivo local → remoto
scp archivo.txt usuario@servidor:/destino/

# Copiar directorio recursivo
scp -r directorio/ usuario@servidor:/destino/

# Copiar remoto → local
scp usuario@servidor:/remoto/archivo.txt /local/

# Con compresión (útil para archivos grandes)
scp -C archivo-grande.iso usuario@servidor:/destino/

# Limitar ancho de banda (1 MB/s)
scp -l 8192 archivo.iso usuario@servidor:/destino/
# 8192 Kbps = 1024 KB/s = 1 MB/s
```

**SCP vs SFTP:**

| Característica | SCP | SFTP |
|---------------|-----|------|
| **Uso típico** | Copias rápidas | Sesión interactiva |
| **Listado directorios** | ❌ No | ✅ Sí |
| **Resumir transferencias** | ❌ No | ✅ Sí |
| **Gestión archivos remotos** | ❌ No | ✅ Sí (chmod, rm, mkdir) |
| **Velocidad** | ⚡ Más rápido | ⚠️ Ligero overhead |
| **Scripting** | ✅ Excelente | ⚠️ Más complejo |

---

### 3. Rsync sobre SSH

**Rsync es ideal para sincronización y backups.**

```bash
# Sincronizar local → remoto
rsync -avz /local/directorio/ usuario@servidor:/remoto/directorio/

# Opciones:
# -a: archive (preserva permisos, timestamps, symlinks)
# -v: verbose
# -z: compresión

# Solo transferir cambios (incremental)
rsync -avz --delete /local/ usuario@servidor:/remoto/
# --delete: elimina archivos en destino que no están en origen

# Excluir archivos
rsync -avz --exclude='*.log' --exclude='cache/' /local/ usuario@servidor:/remoto/

# Dry-run (simular sin cambios)
rsync -avzn /local/ usuario@servidor:/remoto/

# Con progreso detallado
rsync -avz --progress /local/archivo-grande.iso usuario@servidor:/destino/

# Backup diario con timestamp
rsync -avz /datos/ backup@servidor:/backups/$(date +%Y-%m-%d)/
```

**Rsync vs SCP vs SFTP:**

| Característica | Rsync | SCP | SFTP |
|---------------|-------|-----|------|
| **Transferencias incrementales** | ✅ Solo cambios | ❌ Archivo completo | ❌ Archivo completo |
| **Sincronización bidireccional** | ✅ Sí | ❌ No | ❌ No |
| **Velocidad (archivos grandes)** | ⚡⚡ Muy rápido | ⚡ Rápido | ⚡ Rápido |
| **Velocidad (muchos archivos pequeños)** | ⚡⚡⚡ Excelente | ⚠️ Lento | ⚠️ Lento |
| **Backup/Sync** | ✅ Diseñado para esto | ⚠️ Manual | ⚠️ Manual |
| **Complejidad** | ⚠️ Más opciones | ✅ Simple | ✅ Simple |

### 4. FTPS (FTP over TLS/SSL)

**FTPS agrega cifrado TLS a FTP. Usar SOLO si legacy FTP es requerido.**

```
FTPS vs SFTP:

┌────────────────┬──────────────────┬──────────────────┐
│ Característica │ FTPS             │ SFTP             │
├────────────────┼──────────────────┼──────────────────┤
│ Protocolo base │ FTP + TLS        │ SSH              │
│ Puerto(s)      │ 21 + rango datos │ 22 (uno solo)    │
│ Firewall       │ ⚠️ Complicado    │ ✅ Simple        │
│ Cifrado        │ ✅ TLS 1.2+      │ ✅ SSH           │
│ Certificados   │ ✅ X.509         │ ❌ SSH keys      │
│ Compatibilidad │ ✅ Clientes FTP  │ ⚠️ Clientes SSH  │
│ Uso recomendado│ Transición legacy│ Nuevo desarrollo │
└────────────────┴──────────────────┴──────────────────┘

CUÁNDO USAR FTPS:
✓ Migración gradual desde FTP (clientes viejos)
✓ Requisito explícito de FTP con cifrado
✓ Integración con sistemas legacy que no soportan SSH

CUÁNDO NO USAR FTPS:
✗ Nuevo proyecto (usar SFTP)
✗ Firewall restrictivo (SFTP más compatible)
✗ Automatización (SFTP más simple)
```

**Instalación vsftpd con TLS:**

```bash
# Instalar vsftpd
sudo apt install vsftpd -y

# Generar certificado (producción: usar Let's Encrypt)
sudo openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout /etc/ssl/private/vsftpd.key \
  -out /etc/ssl/certs/vsftpd.crt

# Configurar /etc/vsftpd.conf
sudo nano /etc/vsftpd.conf

# SSL/TLS Configuration
ssl_enable=YES
allow_anon_ssl=NO
force_local_data_ssl=YES
force_local_logins_ssl=YES
ssl_tlsv1=YES
ssl_sslv2=NO
ssl_sslv3=NO
require_ssl_reuse=NO
ssl_ciphers=HIGH

rsa_cert_file=/etc/ssl/certs/vsftpd.crt
rsa_private_key_file=/etc/ssl/private/vsftpd.key

# Reiniciar
sudo systemctl restart vsftpd

# Conectar con FileZilla
# Server: ftps://servidor.com
# Port: 21
# Encryption: Require explicit FTP over TLS
```

**⚠️ NOTA:** Incluso con FTPS, SFTP es generalmente mejor opción.

### 5. HTTPS / WebDAV

**HTTPS para descarga pública, WebDAV para gestión de archivos.**

#### HTTPS Simple (Nginx)

```nginx
# /etc/nginx/sites-available/files

server {
    listen 443 ssl http2;
    server_name files.empresa.com;

    ssl_certificate /etc/letsencrypt/live/files.empresa.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/files.empresa.com/privkey.pem;

    root /var/www/files;

    # Listado de directorios
    autoindex on;
    autoindex_exact_size off;
    autoindex_localtime on;

    # Autenticación básica
    auth_basic "Restricted Area";
    auth_basic_user_file /etc/nginx/.htpasswd;

    location / {
        try_files $uri $uri/ =404;
    }
}
```

```bash
# Crear usuario para auth básica
sudo htpasswd -c /etc/nginx/.htpasswd usuario

# Descargar archivo
wget https://usuario:password@files.empresa.com/archivo.zip
curl -u usuario:password -O https://files.empresa.com/archivo.zip

# Desde navegador
https://files.empresa.com/
# Pide usuario/password, muestra listado de archivos
```

#### WebDAV (Gestión Completa de Archivos)

```nginx
# /etc/nginx/sites-available/webdav

server {
    listen 443 ssl http2;
    server_name dav.empresa.com;

    ssl_certificate /etc/letsencrypt/live/dav.empresa.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/dav.empresa.com/privkey.pem;

    root /var/www/webdav;

    client_max_body_size 10G;

    location / {
        # WebDAV methods
        dav_methods PUT DELETE MKCOL COPY MOVE;
        dav_ext_methods PROPFIND OPTIONS;
        dav_access user:rw group:rw all:r;

        # Autenticación
        auth_basic "WebDAV";
        auth_basic_user_file /etc/nginx/.htpasswd;

        # Headers
        add_header 'Access-Control-Allow-Origin' '*';
        add_header 'Access-Control-Allow-Methods' 'GET, POST, PUT, DELETE, MKCOL, COPY, MOVE, PROPFIND, OPTIONS';
    }
}
```

```bash
# Conectar desde Linux
sudo apt install davfs2
sudo mount -t davfs https://dav.empresa.com /mnt/webdav

# Conectar desde Windows
# Map Network Drive → https://dav.empresa.com

# Desde macOS Finder
# Go → Connect to Server → https://dav.empresa.com

# Comandos con curl
curl -T archivo.txt -u usuario:pass https://dav.empresa.com/archivo.txt
curl -X MKCOL -u usuario:pass https://dav.empresa.com/nuevo-directorio/
curl -u usuario:pass https://dav.empresa.com/archivo.txt -o descargado.txt
```

## Demostración: Migración FTP → SFTP

### Escenario: Empresa Migra de FTP Inseguro a SFTP

**Estado Actual (INSEGURO):**
```bash
# Script de backup con FTP (INSEGURO)
#!/bin/bash
# backup-ftp.sh

FTP_HOST="ftp.empresa.com"
FTP_USER="backup"
FTP_PASS="P@ssw0rd123"  # ⚠️ Password hardcoded

ftp -n $FTP_HOST <<EOF
user $FTP_USER $FTP_PASS
binary
cd /backups
put database_backup_$(date +%Y%m%d).sql
quit
EOF

# ☠️ PROBLEMAS:
# - Credenciales en texto plano (script + red)
# - Sin cifrado de datos
# - Password hardcoded en script
# - Violación PCI-DSS
```

**Migración a SFTP (SEGURO):**

```bash
#!/bin/bash
# backup-sftp.sh

SFTP_HOST="sftp.empresa.com"
SFTP_USER="backup"
SFTP_KEY="/home/backup/.ssh/id_backup"
BACKUP_FILE="database_backup_$(date +%Y%m%d).sql"

# Crear backup
pg_dump dbname > $BACKUP_FILE

# Subir vía SFTP (con llave SSH, sin password)
sftp -i $SFTP_KEY $SFTP_USER@$SFTP_HOST <<EOF
cd /backups
put $BACKUP_FILE
quit
EOF

# Limpiar backup local
rm $BACKUP_FILE

# ✅ SEGURIDAD:
# - Cifrado completo (SSH)
# - Autenticación por llave (sin password en script)
# - Cumple PCI-DSS
# - Auditable (logs SSH)
```

**Configuración del servidor SFTP:**

```bash
# En servidor de backups

# 1. Crear usuario dedicado para backups
sudo useradd -m -d /home/backup -s /bin/bash backup

# 2. Crear directorio de backups
sudo mkdir -p /backups
sudo chown backup:backup /backups
sudo chmod 750 /backups

# 3. Configurar SSH para solo SFTP (sin shell)
sudo nano /etc/ssh/sshd_config

# Al final del archivo:
Match User backup
    ChrootDirectory /backups
    ForceCommand internal-sftp
    AllowTcpForwarding no
    X11Forwarding no

sudo systemctl restart sshd

# 4. En cliente, copiar llave pública
ssh-copy-id -i ~/.ssh/id_backup.pub backup@sftp.empresa.com

# 5. Probar conexión
sftp -i ~/.ssh/id_backup backup@sftp.empresa.com
```

## Casos Excepcionales: Cuándo FTP/TFTP AÚN Se Usan

### TFTP para PXE Boot (Aceptable en Red Interna)

```
ESCENARIO: Instalación masiva de sistemas operativos

┌─────────────┐                    ┌─────────────┐
│  Cliente    │  PXE Boot Request  │  DHCP       │
│  (Sin SO)   │───────────────────>│  Server     │
│             │                    │  (Opción 67)│
│             │<───────────────────│             │
└─────────────┘  "Boot desde TFTP" └─────────────┘
       │
       │  TFTP RRQ pxelinux.0
       ↓
┌─────────────┐
│  TFTP       │
│  Server     │  Envía bootloader + kernel
│  (Puerto 69)│  ⚠️ Red INTERNA AISLADA
└─────────────┘

ACEPTABLE SI:
✓ Red interna aislada (no Internet)
✓ VLAN dedicada para PXE
✓ Firewall bloquea puerto 69 desde otras VLANs
✓ Solo para instalación inicial (datos no sensibles)

ALTERNATIVA MODERNA:
→ HTTP Boot (UEFI HTTP Boot, RFC 9110)
  - Usa HTTPS en lugar de TFTP
  - Cifrado TLS
  - Puerto 443
```

### FTP en Sistemas Legacy (Migración Planificada)

```
EMPRESA CON SISTEMA LEGACY:

Aplicación de 1995 (código fuente perdido):
  - Hardcoded: FTP para recibir órdenes de compra
  - No puede modificarse (sin código fuente)
  - Retiro del sistema planificado en 12 meses

MITIGACIÓN TEMPORAL:
1. Aislar FTP en VLAN separada (DMZ)
2. Firewall strict: Solo IPs autorizadas → FTP server
3. FTP server NO tiene acceso directo a BD producción
4. Proxy/Gateway que:
   - Recibe archivos vía FTP
   - Valida contenido (malware scan)
   - Reenvía a sistema moderno vía HTTPS API
5. Logging agresivo + monitoreo SIEM
6. Roadmap claro para migración completa

⚠️ ESTO ES UN PARCHE, NO SOLUCIÓN PERMANENTE
```

## Aspectos de Seguridad: Migrando de FTP/TFTP

### Checklist de Migración Segura

```
PRE-MIGRACIÓN:
☐ Inventario completo de usos de FTP/TFTP
  - Usuarios (quién accede)
  - Aplicaciones (scripts, integraciones)
  - Datos transferidos (sensibilidad)
  - Frecuencia de uso

☐ Análisis de riesgo
  - ¿Datos PCI/HIPAA/GDPR siendo transferidos?
  - ¿Exposición a Internet o solo interna?
  - ¿Qué sucede si datos son interceptados?

☐ Seleccionar alternativa apropiada
  - SFTP: Mayoría de casos
  - Rsync: Backups/sincronización
  - Cloud Storage: Apps cloud-native
  - MFT: Compliance estricto

MIGRACIÓN:
☐ Configurar servicio alternativo (SFTP/HTTPS)
☐ Generar llaves SSH (no passwords)
☐ Actualizar scripts/aplicaciones
☐ Testing exhaustivo en staging
☐ Documentar procedimientos
☐ Capacitar usuarios
☐ Migración gradual (dual-run FTP+SFTP)
☐ Monitoreo de uso de FTP (debe disminuir)

POST-MIGRACIÓN:
☐ Deshabilitar FTP/TFTP después de 30 días sin uso
☐ Remover del firewall
☐ Desinstalar software FTP
☐ Auditoría de cumplimiento
☐ Documentar lecciones aprendidas
```

### Monitoreo de Seguridad

```bash
# Detectar uso de FTP/TFTP en red (para identificar sistemas legacy)

# Con tcpdump
sudo tcpdump -i any 'port 21 or port 20 or port 69' -w ftp-traffic.pcap

# Con nmap (escanear red por servidores FTP/TFTP)
nmap -p 21,69 192.168.1.0/24

# Alertar si FTP/TFTP es usado (SIEM rule)
# Splunk:
source="firewall" dest_port IN (20,21,69) | stats count by src_ip dest_ip
# Alerta si count > 0 (no debería haber tráfico FTP después de migración)

# Grep logs por intentos de conexión FTP
sudo grep -i "ftp" /var/log/auth.log
sudo grep -i "vsftpd" /var/log/syslog
```

### Política de Transferencia de Archivos Empresarial

```markdown
# Política de Transferencia de Archivos v2.0
## Empresa XYZ - Vigencia: 2024-2026

### 1. PROTOCOLOS PROHIBIDOS
❌ FTP (File Transfer Protocol) - Puerto 21
❌ TFTP (Trivial FTP) - Puerto 69
❌ HTTP sin TLS - Puerto 80 (excepto redirect a HTTPS)
❌ SMB v1 (WannaCry vulnerability)

### 2. PROTOCOLOS APROBADOS

#### Para Transferencias Usuario ↔ Servidor
✅ SFTP (SSH File Transfer Protocol) - Puerto 22
  - Autenticación: SSH keys obligatorio (no passwords)
  - Cifrado: AES-256
  - Logging: Obligatorio en SIEM

✅ HTTPS/WebDAV - Puerto 443
  - Autenticación: OAuth 2.0 + MFA
  - Certificado: Let's Encrypt o CA interna
  - Logging: Access logs + WAF logs

#### Para Backups Automatizados
✅ Rsync sobre SSH
  - Autenticación: SSH keys con passphrase
  - Encriptación adicional: GPG para datos sensibles
  - Retention: 30 días on-site, 1 año off-site

#### Para Aplicaciones Cloud-Native
✅ AWS S3 / Azure Blob Storage / GCP Cloud Storage
  - Autenticación: IAM roles (no access keys hardcoded)
  - Cifrado en tránsito: TLS 1.3
  - Cifrado en reposo: AES-256
  - Versionado: Habilitado

#### Para Código Fuente
✅ Git (GitHub Enterprise / GitLab)
  - Autenticación: SSH keys + GPG signing
  - Branch protection: Obligatorio en main
  - Code review: Requerido para merge

### 3. CLASIFICACIÓN DE DATOS

| Clasificación | Ejemplos | Protocolo Mínimo | Cifrado Adicional |
|---------------|----------|------------------|-------------------|
| **Pública** | Marketing materials | HTTPS | Opcional |
| **Interna** | Documentos corporativos | SFTP, HTTPS | Recomendado |
| **Confidencial** | Contratos, financiera | SFTP | GPG obligatorio |
| **Regulada** | PCI, HIPAA, GDPR | SFTP + MFT | GPG + Audit trail |

### 4. EXCEPCIONES

Excepciones a esta política requieren:
1. Justificación de negocio escrita (VP+ aprobación)
2. Análisis de riesgo (InfoSec team)
3. Plan de mitigación (controles compensatorios)
4. Fecha de expiración (máx. 6 meses, renovable)
5. Revisión trimestral

### 5. CONSECUENCIAS DE INCUMPLIMIENTO

Primera violación: Advertencia escrita + capacitación
Segunda violación: Suspensión de acceso (1 semana)
Tercera violación: Terminación de empleo

### 6. REVISIÓN DE POLÍTICA

Esta política será revisada anualmente o cuando:
- Cambios regulatorios (PCI-DSS, HIPAA)
- Incidentes de seguridad
- Nuevas tecnologías disponibles
```

## Conclusión

**FTP y TFTP cumplieron su propósito histórico pero son INSEGUROS para uso moderno.** La transmisión de credenciales y datos en texto plano es inaceptable en 2026, violando estándares de compliance (PCI-DSS, HIPAA, GDPR) y exponiendo a organizaciones a riesgos de seguridad graves.

### Resumen de Alternativas por Caso de Uso

| Necesidad | Recomendación | Razón |
|-----------|---------------|-------|
| **Transferencia general de archivos** | SFTP | Reemplazo directo de FTP, compatible con Linux/Windows |
| **Copias rápidas entre servidores** | SCP | Simple, rápido, scriptable |
| **Backups/sincronización** | Rsync sobre SSH | Incremental, eficiente, compresión |
| **Legacy FTP requerido** | FTPS (transición a SFTP) | Cifrado TLS, compatible con clientes FTP |
| **Descarga pública de archivos** | HTTPS (Nginx) | Universal, firewall-friendly (puerto 443) |
| **Compartir archivos estilo Dropbox** | WebDAV sobre HTTPS | Montable como unidad de red, gestión completa |
| **Aplicaciones cloud** | S3/Azure Blob/GCP Storage | Escalable, HA, versionado, cifrado nativo |
| **Código fuente** | Git (GitHub/GitLab) | Control de versiones, CI/CD integration |
| **Compliance estricto** | MFT (GoAnywhere, MOVEit) | Auditoría completa, workflows, reporting |
| **PXE boot interno** | TFTP (red aislada) + HTTP Boot | Solo en VLAN aislada, migrar a HTTP Boot |

### Puntos Clave

```
❌ FTP/TFTP Transmiten:
  - Credenciales en texto plano
  - Datos sin cifrado
  - Sin integridad verificable
  
❌ Violan:
  - PCI-DSS (datos de tarjetas)
  - HIPAA (información médica)
  - GDPR (datos personales)
  - SOX (controles financieros)
  
✅ SFTP Proporciona:
  - Cifrado completo (SSH/TLS)
  - Autenticación robusta (keys)
  - Integridad (HMAC)
  - Un solo puerto (firewall-friendly)
  - Cumplimiento normativo
  
✅ Para Casos Específicos:
  - Backups → Rsync
  - Cloud → S3/Blob Storage
  - Código → Git
  - Public → HTTPS
  - Enterprise → MFT
```

**Acción Recomendada:** Si tu organización aún usa FTP/TFTP, **inicia migración a SFTP inmediatamente.** El riesgo de exposición de datos no justifica la "comodidad" de protocolos legacy.
