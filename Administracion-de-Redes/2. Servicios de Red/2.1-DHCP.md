# 2.1 DHCP - Dynamic Host Configuration Protocol

## Descripción

**DHCP (Dynamic Host Configuration Protocol)** es un protocolo de red cliente-servidor que asigna automáticamente direcciones IP y otros parámetros de configuración de red a dispositivos (hosts) que se conectan a una red. Sin DHCP, cada dispositivo requeriría configuración manual de IP, máscara de subred, gateway predeterminado, servidores DNS y otros parámetros, lo cual es inviable e ineficiente en redes modernas.

### ¿Cómo Funciona DHCP?

DHCP opera mediante un proceso de **4 pasos** conocido como **DORA**:

```
CLIENTE                                    SERVIDOR DHCP

  │                                              │
  │  1. DHCP DISCOVER (broadcast)               │
  │───────────────────────────────────────────→ │
  │      "¿Hay algún servidor DHCP? Necesito IP" │
  │                                              │
  │  2. DHCP OFFER (unicast o broadcast)        │
  │ ←───────────────────────────────────────────│
  │      "Tengo IP 192.168.1.100 disponible"    │
  │                                              │
  │  3. DHCP REQUEST (broadcast)                │
  │───────────────────────────────────────────→ │
  │      "Acepto 192.168.1.100 de servidor X"   │
  │                                              │
  │  4. DHCP ACK (unicast)                      │
  │ ←───────────────────────────────────────────│
  │      "Confirmado, aquí está tu config"      │
  │                                              │
  ▼                                              ▼
 Cliente configurado con IP                   Registro en lease table
```

**Detalles de cada paso:**

1. **DISCOVER:** Cliente envía broadcast (255.255.255.255) desde 0.0.0.0 buscando servidores DHCP
2. **OFFER:** Servidor(es) responde(n) ofreciendo una dirección IP disponible de su pool
3. **REQUEST:** Cliente selecciona una oferta (si hay múltiples servidores) y solicita formalmente
4. **ACKNOWLEDGE:** Servidor confirma y envía configuración completa (IP, máscara, gateway, DNS, etc.)

### Renovación de Lease

Las direcciones IP asignadas por DHCP tienen un **tiempo de lease (arrendamiento)** definido.

```
TIMELINE DE LEASE (Ejemplo: 24 horas)

Hora 0: Cliente recibe IP con lease de 24h
  │
  ▼
Hora 12 (50% del lease): Cliente intenta renovar automáticamente
  │                       (DHCP REQUEST directo al servidor)
  ├─→ Éxito: Lease renovado por 24h más
  └─→ Fallo: Continúa intentando
  
Hora 18 (75% del lease): Si aún no renovó, intenta con broadcast
  │                       (cualquier servidor DHCP puede responder)
  └─→ Fallo: Continúa usando IP hasta expiración

Hora 24: Lease expira
  └─→ Cliente debe iniciar proceso DORA completo
```

## RFCs de Referencia

DHCP está definido por múltiples RFCs (Request for Comments) que especifican su funcionamiento:

### RFCs Principales

```
RFC 2131 - "Dynamic Host Configuration Protocol" (1997)
  • RFC fundamental que define DHCP
  • Reemplaza a BOOTP (Bootstrap Protocol)
  • Define proceso DORA, formato de mensajes, leases
  • Estado: ESTÁNDAR INTERNET

RFC 2132 - "DHCP Options and BOOTP Vendor Extensions" (1997)
  • Define opciones de DHCP (DHCP Options)
  • Parámetros adicionales más allá de IP básica
  • Gateway, DNS, dominio, NTP, etc.
  • Estado: ESTÁNDAR INTERNET

RFC 3046 - "DHCP Relay Agent Information Option" (2001)
  • Define option 82 (relay agent information)
  • Permite a switches/routers agregar información
  • Usado en DHCP snooping
  
RFC 3942 - "Reclassifying DHCP Options" (2004)
  • Reorganización de opciones
  • Códigos 128-254 redefinidos

RFC 4361 - "Node-specific Client Identifiers" (2006)
  • Identificadores de cliente únicos
  • Importante para dual-stack (IPv4/IPv6)

RFC 6842 - "Client Identifier Option in DHCP Server Replies" (2013)
  • Servidor debe incluir client identifier en respuestas
```

### RFCs para DHCPv6 (IPv6)

```
RFC 8415 - "Dynamic Host Configuration Protocol for IPv6 (DHCPv6)" (2018)
  • Reemplaza RFC 3315
  • DHCP para IPv6
  • Proceso similar pero con diferencias (SLAAC vs DHCPv6)
```

## DHCP Options (Opciones de Configuración)

Las **DHCP Options** son parámetros adicionales que el servidor puede enviar al cliente más allá de la dirección IP básica. Están definidas en RFC 2132 y ampliadas en RFCs subsecuentes.

### Formato de DHCP Option

```
┌──────────┬──────────┬──────────────────────────┐
│  Code    │  Length  │  Data                    │
│ (1 byte) │ (1 byte) │  (variable, 0-255 bytes) │
└──────────┴──────────┴──────────────────────────┘

Ejemplo: Option 3 (Router/Gateway)
  Code: 3
  Length: 4 (4 bytes = 1 dirección IPv4)
  Data: 192.168.1.1
```

### DHCP Options Más Comunes

| Option Code | Nombre | Descripción | Ejemplo de Valor |
|-------------|--------|-------------|------------------|
| **1** | Subnet Mask | Máscara de subred | 255.255.255.0 |
| **3** | Router | Gateway predeterminado | 192.168.1.1 |
| **6** | DNS Servers | Servidores DNS (puede ser lista) | 8.8.8.8, 8.8.4.4 |
| **15** | Domain Name | Nombre de dominio | empresa.com |
| **28** | Broadcast Address | Dirección de broadcast | 192.168.1.255 |
| **42** | NTP Servers | Servidores de tiempo (NTP) | 129.6.15.28 |
| **51** | IP Address Lease Time | Duración del lease (segundos) | 86400 (24 horas) |
| **53** | DHCP Message Type | Tipo de mensaje DHCP | 1=Discover, 2=Offer, 3=Request, 5=ACK |
| **54** | DHCP Server Identifier | IP del servidor DHCP | 192.168.1.254 |
| **58** | Renewal (T1) Time | Tiempo de renovación (50% lease) | 43200 (12 horas) |
| **59** | Rebinding (T2) Time | Tiempo de rebinding (87.5% lease) | 75600 (21 horas) |
| **66** | TFTP Server Name | Servidor TFTP para PXE boot | tftp.empresa.com |
| **67** | Bootfile Name | Archivo de boot para PXE | pxelinux.0 |
| **69** | SMTP Servers | Servidores de correo | mail.empresa.com |
| **82** | Relay Agent Information | Info agregada por relay agent | VLAN ID, Circuit ID |
| **119** | Domain Search List | Lista de dominios para búsqueda | empresa.com, corp.empresa.com |
| **121** | Classless Static Routes | Rutas estáticas | 10.20.0.0/16 via 192.168.1.10 |
| **150** | TFTP Server Address | IP del servidor TFTP (Cisco) | 10.10.10.50 |
| **252** | WPAD (Web Proxy Autodiscovery) | URL del archivo PAC de proxy | http://proxy.empresa.com/wpad.dat |

### Opciones Críticas vs Opcionales

```
CRÍTICAS (casi siempre configuradas):
✓ Option 1: Subnet Mask
✓ Option 3: Router (Gateway)
✓ Option 6: DNS Servers
✓ Option 51: Lease Time

COMUNES (depende del entorno):
• Option 15: Domain Name
• Option 42: NTP Servers
• Option 119: Domain Search List

ESPECIALIZADAS (casos de uso específicos):
• Option 66/67: PXE Boot (thin clients, instalaciones de red)
• Option 82: DHCP Snooping (seguridad en switches)
• Option 121: Rutas estáticas (subredes no directamente conectadas)
• Option 150: Teléfonos IP Cisco
• Option 252: Proxy autodiscovery
```

## Objetivo

### Propósitos Principales de DHCP

1. **Automatización de Configuración de Red**
   - Eliminar configuración manual de cada dispositivo
   - Reducir errores humanos (IPs duplicadas, gateway incorrecto)
   - Facilitar movilidad de dispositivos (laptops, móviles)

2. **Gestión Centralizada de Direcciones IP**
   - Pool de IPs dinámicas asignadas según demanda
   - Reservas estáticas para servidores/impresoras
   - Optimizar uso de espacio de direcciones

3. **Distribución de Parámetros de Red**
   - DNS, gateway, dominio, NTP, etc.
   - Cambios centralizados afectan a todos los clientes
   - Configuración consistente en toda la red

4. **Facilitación de Troubleshooting**
   - Logs centralizados de asignaciones
   - Rastreo de qué dispositivo tuvo qué IP y cuándo
   - Identificación de problemas de red (IPs agotadas, rogue DHCP)

### Casos de Uso Reales

```
OFICINA CORPORATIVA:
- 500 empleados con laptops
- DHCP asigna IPs dinámicas
- Reservas para impresoras, AP WiFi
- Options: DNS corporativo, dominio interno, NTP

DATACENTER:
- Servidores con IPs estáticas asignadas manualmente
- DHCP solo para VMs temporales o containers
- Reservas DHCP para IPs "fijas" con flexibilidad

RED DOMÉSTICA:
- Router ISP con DHCP integrado
- Asigna IPs a dispositivos (PCs, móviles, Smart TV, IoT)
- Configuración mínima: IP, máscara, gateway, DNS

NETWORK PXE BOOT:
- Thin clients booting desde red
- DHCP proporciona IP + Option 66/67 (TFTP server y bootfile)
- Cliente descarga SO desde servidor

HOSPITALES/GUEST NETWORKS:
- Dispositivos temporales (visitantes, equipos médicos portátiles)
- Leases cortos (1-2 horas)
- Segmentación por VLANs con DHCP relay
```

#### Configuración Básica

**Archivo de configuración:** `/etc/dhcp/dhcpd.conf`

```bash
# Editar configuración principal
sudo nano /etc/dhcp/dhcpd.conf
```

**Configuración Simple (Red 192.168.1.0/24):**

```
# /etc/dhcp/dhcpd.conf
# Configuración global

# Tiempo de lease predeterminado (segundos)
default-lease-time 86400;  # 24 horas
max-lease-time 172800;     # 48 horas (máximo que un cliente puede solicitar)

# Servidor autoritativo (responde authoritatively)
authoritative;

# DNS dinámico deshabilitado (por ahora)
ddns-update-style none;

# Subnet declaration (red a servir)
subnet 192.168.1.0 netmask 255.255.255.0 {
    # Rango de IPs dinámicas a asignar
    range 192.168.1.100 192.168.1.200;
    
    # Option 3: Gateway predeterminado
    option routers 192.168.1.1;
    
    # Option 6: Servidores DNS
    option domain-name-servers 8.8.8.8, 8.8.4.4;
    
    # Option 15: Nombre de dominio
    option domain-name "empresa.local";
    
    # Option 28: Dirección de broadcast
    option broadcast-address 192.168.1.255;
}
```

**Configuración Avanzada con Múltiples Opciones:**

```
# /etc/dhcp/dhcpd.conf
# Configuración completa para red empresarial

# Configuración global
default-lease-time 43200;  # 12 horas
max-lease-time 86400;      # 24 horas
authoritative;
ddns-update-style none;

# Log facility
log-facility local7;

# Subnet principal - Empleados
subnet 192.168.10.0 netmask 255.255.255.0 {
    range 192.168.10.50 192.168.10.200;
    
    option routers 192.168.10.1;
    option domain-name-servers 192.168.10.10, 8.8.8.8;
    option domain-name "corp.empresa.com";
    option broadcast-address 192.168.10.255;
    
    # Option 42: Servidor NTP
    option ntp-servers 192.168.10.10;
    
    # Option 119: Domain search list
    option domain-search "corp.empresa.com", "empresa.com";
}

# Subnet para servidores (mayormente reservas estáticas)
subnet 192.168.20.0 netmask 255.255.255.0 {
    # Pool pequeño para VMs temporales
    range 192.168.20.230 192.168.20.250;
    
    option routers 192.168.20.1;
    option domain-name-servers 192.168.20.10, 192.168.20.11;
    option domain-name "servers.empresa.com";
}

# Subnet para invitados (leases cortos)
subnet 192.168.100.0 netmask 255.255.255.0 {
    range 192.168.100.10 192.168.100.250;
    
    default-lease-time 3600;   # 1 hora
    max-lease-time 7200;       # 2 horas
    
    option routers 192.168.100.1;
    option domain-name-servers 8.8.8.8, 8.8.4.4;  # DNS público solo
    option domain-name "guest.empresa.com";
}

# Reserva estática (IP fija asignada por DHCP)
# Útil para impresoras, APs, servidores que necesitan IP conocida
host printer-hp-laserjet {
    # MAC address del dispositivo
    hardware ethernet 00:11:22:33:44:55;
    # IP fija a asignar
    fixed-address 192.168.10.10;
    # Opciones específicas para este host
    option host-name "printer-01";
}

host server-web-prod {
    hardware ethernet AA:BB:CC:DD:EE:FF;
    fixed-address 192.168.20.100;
    option host-name "web-prod-01";
}

# Configuración para PXE Boot (instalación de SO por red)
host pxe-client-01 {
    hardware ethernet 11:22:33:44:55:66;
    fixed-address 192.168.10.25;
    # Option 66: TFTP server
    next-server 192.168.10.5;
    # Option 67: Boot file
    filename "pxelinux.0";
}
```

#### Especificar Interfaz de Red

```bash

# Ubuntu/Debian

# Rocky/RHEL - archivo diferente

```

## DHCP Relay (Helper Address)

En redes segmentadas por VLANs, un servidor DHCP no puede responder broadcasts de otras subredes. Se requiere un **DHCP Relay Agent** (típicamente el router/switch de capa 3).

### Escenario

```
VLAN 10 (192.168.10.0/24) ──┐
                            │
VLAN 20 (192.168.20.0/24) ──┼── Router/Switch L3 ──→ DHCP Server
                            │                         192.168.1.254
VLAN 30 (192.168.30.0/24) ──┘
```

### Configuración en Cisco Router/Switch

```cisco
interface Vlan10
 ip address 192.168.10.1 255.255.255.0
 ip helper-address 192.168.1.254
 ! El router reenviará broadcasts DHCP a 192.168.1.254

interface Vlan20
 ip address 192.168.20.1 255.255.255.0
 ip helper-address 192.168.1.254

interface Vlan30
 ip address 192.168.30.1 255.255.255.0
 ip helper-address 192.168.1.254
```

**Funcionamiento:**
1. Cliente en VLAN 10 envía DHCP Discover (broadcast)
2. Router recibe broadcast en su interfaz Vlan10
3. Router convierte a unicast y lo envía a 192.168.1.254
4. Servidor DHCP responde al router
5. Router reenvía respuesta al cliente

### Configuración del Servidor DHCP para Múltiples Subredes

```
# /etc/dhcp/dhcpd.conf

subnet 192.168.10.0 netmask 255.255.255.0 {
    range 192.168.10.50 192.168.10.200;
    option routers 192.168.10.1;
    option domain-name-servers 192.168.1.10;
}

subnet 192.168.20.0 netmask 255.255.255.0 {
    range 192.168.20.50 192.168.20.200;
    option routers 192.168.20.1;
    option domain-name-servers 192.168.1.10;
}

subnet 192.168.30.0 netmask 255.255.255.0 {
    range 192.168.30.50 192.168.30.200;
    option routers 192.168.30.1;
    option domain-name-servers 192.168.1.10;
}

# Subnet donde reside el servidor DHCP (debe estar declarado)
subnet 192.168.1.0 netmask 255.255.255.0 {
    # Vacío o con su propia configuración
}
```

```bash

# Abrir en Wireshark y filtrar:
# Display filter: bootp
# Verás los 4 mensajes DORA con todas las opciones
```

**Análisis en Wireshark:**
- Discover: Broadcast a 255.255.255.255, source 0.0.0.0
- Offer: Server ofrece IP, incluye Options 53 (tipo=2), 54 (server ID), etc.
- Request: Cliente solicita IP ofrecida, broadcast para informar a otros servidores
- Ack: Server confirma, envía Options 1, 3, 6, 51, etc.

## Aspectos de Seguridad

### Vulnerabilidades Comunes de DHCP

#### 1. Rogue DHCP Server (Servidor DHCP No Autorizado)

**Problema:**
- Atacante conecta dispositivo con servidor DHCP a la red
- Clientes legítimos reciben configuración maliciosa:
  - Gateway falso (man-in-the-middle)
  - DNS malicioso (phishing, malware)
  - IP en subred incorrecta (pérdida de conectividad)

**Consecuencias:**
```
Cliente → DHCP Request
  ↓
Rogue DHCP responde primero
  ↓
Gateway: 192.168.1.99 (atacante)
DNS: 10.0.0.50 (DNS malicioso)
  ↓
Todo el tráfico pasa por atacante
→ Interceptación, inyección de malware, robo de credenciales
```

**Mitigación: DHCP Snooping**

---

#### 2. DHCP Starvation Attack

**Problema:**
- Atacante envía miles de DHCP Requests con MACs falsas
- Agota el pool de IPs disponibles
- Usuarios legítimos no pueden obtener IP (DoS)

**Ataque:**
```bash
# Herramienta de ataque (Yersinia, DHCPig)
sudo yersinia dhcp -attack 1
# Envía DHCP Discovers con MACs aleatorias rápidamente
# Pool: 192.168.1.100-200 (100 IPs) agotado en segundos
```

**Mitigación:**
- DHCP Snooping con rate limiting
- Port security en switches

---

### DHCP Snooping (Protección en Switch)

**DHCP Snooping** es una característica de switches que actúa como firewall para DHCP.

#### Concepto

```
PUERTOS TRUSTED:
- Conectados a servidores DHCP legítimos
- Conectados a routers/switches upstream
- Permiten mensajes DHCP Server (Offer, Ack)

PUERTOS UNTRUSTED:
- Conectados a usuarios finales
- Solo permiten mensajes DHCP Client (Discover, Request)
- Bloquean mensajes DHCP Server (Rogue DHCP)
```

#### Configuración en Cisco Switch

```cisco
! Habilitar DHCP snooping globalmente
ip dhcp snooping

! Habilitar en VLANs específicas
ip dhcp snooping vlan 10,20,30

! Marcar puertos como trusted (hacia servidor DHCP)
interface GigabitEthernet0/1
 description Uplink hacia DHCP Server
 ip dhcp snooping trust

interface GigabitEthernet0/24
 description Uplink hacia router
 ip dhcp snooping trust

! Puertos de usuario (untrusted por defecto)
interface range GigabitEthernet0/2-23
 description Puertos de usuario
 ip dhcp snooping limit rate 10
 ! Máximo 10 mensajes DHCP por segundo (previene starvation)

! Habilitar Option 82 (Relay Agent Information)
ip dhcp snooping information option

! Verificar configuración
show ip dhcp snooping
show ip dhcp snooping binding
```

**Resultado:**
- Rogue DHCP en puerto untrusted → DHCP Offers bloqueados
- DHCP Starvation → Rate limit previene flood
- Base de datos de bindings: IP-MAC-Puerto (útil para Dynamic ARP Inspection)

---

### IP Source Guard

Complemento de DHCP Snooping que previene IP spoofing.

```cisco
! Habilitar IP Source Guard en puertos de usuario
interface range GigabitEthernet0/2-23
 ip verify source
 ! Solo permite tráfico con IP asignada por DHCP
 ! Bloquea IPs estáticas no autorizadas
```

**Funcionamiento:**
1. Cliente obtiene 192.168.1.105 vía DHCP
2. Switch crea binding: 192.168.1.105 ↔ MAC ↔ Puerto Gi0/5
3. Cliente intenta enviar paquetes con IP 192.168.1.200 (spoofed)
4. Switch verifica binding: 192.168.1.200 no asignado a ese puerto
5. Switch bloquea paquetes

---

### Dynamic ARP Inspection (DAI)

Usa base de datos de DHCP Snooping para validar ARP.

```cisco
! Habilitar DAI en VLANs
ip arp inspection vlan 10,20,30

! Puertos trusted (hacia routers/switches)
interface GigabitEthernet0/1
 ip arp inspection trust

! Verificar
show ip arp inspection
```

### Hardening del Servidor DHCP

#### 1. Firewall - Permitir Solo Clientes Legítimos

```bash
# iptables (Linux)
# Permitir DHCP solo desde red local
sudo iptables -A INPUT -p udp --dport 67 -s 192.168.1.0/24 -j ACCEPT
sudo iptables -A INPUT -p udp --dport 67 -j DROP

# Guardar reglas
sudo iptables-save > /etc/iptables/rules.v4
```

#### 2. Logging Detallado

```bash
# ISC DHCP - aumentar nivel de log
# /etc/dhcp/dhcpd.conf
log-facility local7;

# Configurar rsyslog para separar logs
sudo nano /etc/rsyslog.d/dhcpd.conf

local7.*    /var/log/dhcpd.log

sudo systemctl restart rsyslog
```

#### 3. Autenticación DHCP (Poco Usado)

RFC 3118 define autenticación DHCP con shared secret, pero es raramente implementado debido a complejidad y overhead.

### Mejores Prácticas de Seguridad

```
✓ DHCP Snooping en todos los switches de acceso
✓ Rate limiting en puertos de usuario (10-15 paquetes/segundo)
✓ Reservas estáticas para dispositivos críticos (servidores, impresoras)
✓ Segmentación por VLANs con scopes DHCP separados
✓ Logs centralizados en SIEM para auditoría
✓ Monitoreo de agotamiento de pools (alertar a 80% utilización)
✓ Backups de configuración y base de datos de reservas
✓ Redundancia con servidor DHCP secundario (failover)
✓ Firewall en servidor DHCP (solo red interna)
✓ Deshabilitar DHCP en interfaces no necesarias

✗ NO exponer servidor DHCP a Internet
✗ NO usar leases excesivamente largos (dificulta troubleshooting)
✗ NO usar leases excesivamente cortos (genera tráfico innecesario)
✗ NO permitir DHCP sin snooping en producción
```

## Alta Disponibilidad: DHCP Failover

En producción, un solo servidor DHCP es **single point of failure**. DHCP Failover proporciona redundancia.

### Opción 1: ISC DHCP Failover (Peers)

```
# Servidor DHCP Primario - /etc/dhcp/dhcpd.conf

failover peer "dhcp-failover" {
    primary;
    address 192.168.1.10;
    port 647;
    peer address 192.168.1.11;
    peer port 647;
    max-response-delay 60;
    max-unacked-updates 10;
    load balance max seconds 3;
    mclt 3600;
    split 128;
}

subnet 192.168.10.0 netmask 255.255.255.0 {
    pool {
        failover peer "dhcp-failover";
        range 192.168.10.50 192.168.10.200;
    }
    option routers 192.168.10.1;
    option domain-name-servers 192.168.10.10;
}
```

```
# Servidor DHCP Secundario - /etc/dhcp/dhcpd.conf

failover peer "dhcp-failover" {
    secondary;
    address 192.168.1.11;
    port 647;
    peer address 192.168.1.10;
    peer port 647;
    max-response-delay 60;
    max-unacked-updates 10;
    load balance max seconds 3;
}

# Misma subnet declaration que primario
subnet 192.168.10.0 netmask 255.255.255.0 {
    pool {
        failover peer "dhcp-failover";
        range 192.168.10.50 192.168.10.200;
    }
    option routers 192.168.10.1;
    option domain-name-servers 192.168.10.10;
}
```

**Funcionamiento:**
- Ambos servidores activos (load balancing)
- Si uno cae, el otro asume todas las IPs
- Sincronización automática de leases

---

### Opción 2: Método Split Scope (Simple)

Dividir el pool entre dos servidores sin sincronización activa.

```
SERVIDOR 1:
subnet 192.168.10.0 netmask 255.255.255.0 {
    range 192.168.10.50 192.168.10.150;  # 80% del pool
    option routers 192.168.10.1;
}

SERVIDOR 2:
subnet 192.168.10.0 netmask 255.255.255.0 {
    range 192.168.10.151 192.168.10.200;  # 20% del pool
    option routers 192.168.10.1;
}
```

**Ventajas:**
- Simple, sin configuración compleja
- Sin dependencias entre servidores

**Desventajas:**
- No hay sincronización de leases
- Si servidor 1 cae, solo 20% de pool disponible

## Monitoreo y Troubleshooting

### Comandos de Diagnóstico

```bash
# Ver estado del servicio
sudo systemctl status isc-dhcp-server

# Ver logs en tiempo real
sudo journalctl -u isc-dhcp-server -f

# Verificar puerto escuchando
sudo netstat -uln | grep :67
sudo ss -uln | grep :67

# Leases activos
cat /var/lib/dhcp/dhcpd.leases | grep "binding state active"

# Contar leases
grep -c "binding state active" /var/lib/dhcp/dhcpd.leases

# Test de configuración
sudo dhcpd -t -cf /etc/dhcp/dhcpd.conf
```

### Métricas de Monitoreo (Zabbix/Nagios)

```
- Disponibilidad del servicio (process running)
- Puerto UDP 67 accesible
- Uso del pool (% de IPs asignadas)
- Tasa de DHCP Discovers (paquetes/segundo)
- Tiempo de respuesta (latencia)
- Errores en logs
```

### Problemas Comunes y Soluciones

| Problema | Síntoma | Causa Probable | Solución |
|----------|---------|----------------|----------|
| **Cliente no obtiene IP** | Timeout en DHCP Request | Servidor caído, firewall, subnet incorrecta | Verificar servicio, ping al servidor, revisar config |
| **IP duplicada** | "IP address conflict" | Reserva estática fuera del pool no configurada | Agregar exclusion o mover pool |
| **Opciones no recibidas** | Gateway/DNS incorrectos | Config errónea de options | Verificar opciones en subnet {} |
| **Lease no se renueva** | Cliente pierde IP al 50% | Servidor inalcanzable durante renovación | Verificar conectividad, redundancia |
| **Pool agotado** | "No free leases" en logs | Lease time muy largo, muchos dispositivos | Aumentar pool, reducir lease time |
| **DHCP Relay no funciona** | Clientes en VLAN remota sin IP | Helper address incorrecto | Verificar ip helper-address en router |

## Conclusión

DHCP es un servicio fundamental que automatiza la configuración de red, reduciendo errores humanos y facilitando la administración de infraestructuras grandes. Su correcta implementación, incluyendo redundancia y medidas de seguridad como DHCP Snooping, es crítica para operaciones de red estables y seguras.

**Puntos Clave:**
- Proceso DORA (Discover, Offer, Request, Acknowledge)
- DHCP Options permiten distribuir configuración completa (DNS, Gateway, NTP, etc.)
- DHCP Relay permite centralizar servidor para múltiples VLANs
- DHCP Snooping protege contra Rogue DHCP y DHCP Starvation
- Alta disponibilidad mediante Failover o Split Scope
- Monitoreo de uso de pool y logs es esencial
