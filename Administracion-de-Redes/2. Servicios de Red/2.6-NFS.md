# 2.6 NFS (Network File System) - Sistema de Archivos en Red

> **⚠️ ADVERTENCIA DE SEGURIDAD**: NFSv2 y NFSv3 **NO deben utilizarse** en redes no confiables o para datos sensibles. Carecen de autenticación fuerte y cifrado. **NFSv4 con Kerberos** es el mínimo aceptable, pero considere **alternativas modernas** como SSHFS, SMB 3.x, o soluciones cloud para mayor seguridad.

## Descripción

### Network File System (NFS)

NFS es un protocolo de sistema de archivos distribuido desarrollado por Sun Microsystems en 1984 que permite a clientes acceder a archivos remotos como si fueran locales. Es ampliamente utilizado en entornos Unix/Linux para compartir directorios entre servidores.

**Características fundamentales:**
- **Transparencia**: Los archivos remotos aparecen como directorios locales
- **Stateless protocol** (NFSv2/v3): El servidor no mantiene estado de conexiones
- **RPC-based**: Utiliza Remote Procedure Call sobre UDP o TCP
- **Cross-platform**: Clientes Linux, BSD, macOS, Solaris, Windows (con servicios adicionales)

### Evolución de NFS

#### NFSv2 (RFC 1094, 1989)
- **Stateless**: Sin seguimiento de archivos abiertos
- **UDP solamente**: No confiable en redes inestables
- **32-bit file sizes**: Límite de 2GB por archivo
- **Sin autenticación fuerte**: Basado en UID/GID del cliente (fácil de falsificar)
- **❌ OBSOLETO**: No usar en producción

#### NFSv3 (RFC 1813, 1995)
- **64-bit file sizes**: Soporte para archivos >2GB
- **TCP support**: Mayor confiabilidad
- **Mejor rendimiento**: Escrituras asíncronas, mejor caching
- **Sin cambios de seguridad**: Aún basado en UID/GID sin autenticación
- **Problema principal**: Sin cifrado, sin integridad de datos
- **⚠️ USO LIMITADO**: Solo en redes internas confiables

```
NFSv3 - Flujo de montaje y acceso:

Cliente                    Portmapper       NFS Server        Mountd
   │                           │                │                │
   │ 1. Portmap Query (111)    │                │                │
   ├──────────────────────────>│                │                │
   │    "¿Puerto de mountd?"   │                │                │
   │                           │                │                │
   │ 2. Respuesta: Puerto 2049 │                │                │
   │<──────────────────────────┤                │                │
   │                           │                │                │
   │ 3. MOUNT Request                           │                │
   │    (exportar /datos)      │                │                │
   ├───────────────────────────────────────────────────────────>│
   │                           │                │                │
   │ 4. File Handle                             │                │
   │<────────────────────────────────────────────────────────────┤
   │                           │                │                │
   │ 5. NFS READ/WRITE         │                │                │
   │    (usando file handle)   │                │                │
   ├──────────────────────────────────────────>│                │
   │                           │                │                │
   │ 6. Datos (SIN CIFRAR)     │                │                │
   │<───────────────────────────────────────────┤                │
   │                           │                │                │

⚠️ Problema: UID/GID del cliente se confía sin verificación
⚠️ Problema: Tráfico sin cifrar (sniffing posible)
⚠️ Problema: Sin autenticación del servidor (MITM posible)
```

#### NFSv4 (RFC 3530, 2003 → RFC 7530, 2015)
- **Stateful protocol**: Seguimiento de archivos abiertos y locks
- **Puerto único (2049)**: No requiere portmapper, mejor para firewalls
- **ACLs granulares**: Permisos más finos que POSIX
- **Kerberos integration**: Autenticación fuerte (RPCSEC_GSS)
- **Cifrado opcional**: Con Kerberos krb5p
- **Mejor rendimiento**: Operaciones compuestas, delegación de archivos
- **✅ RECOMENDADO**: Con Kerberos para seguridad

#### NFSv4.1 (RFC 5661, 2010) y NFSv4.2 (RFC 7862, 2016)
- **pNFS (Parallel NFS)**: Acceso paralelo para HPC
- **Sessions**: Mejor recuperación ante fallos
- **Server-side copy**: Copia eficiente entre archivos
- **Sparse files**: Soporte para archivos dispersos
- **Application Data Block (ADB)**: Para bases de datos
- **SELinux labeling**: Integración con políticas de seguridad

## Instalación y Configuración

### 1. NFS Server (Linux - Ubuntu/Debian)

#### NFSv3/v4 básico (servidor)

```bash
# Instalar servidor NFS
sudo apt update
sudo apt install nfs-kernel-server -y

# Verificar instalación
dpkg -l | grep nfs

# Servicios NFS
sudo systemctl status nfs-server
sudo systemctl status nfs-kernel-server
```

**Configuración de exports (`/etc/exports`):**

```bash
# Formato básico:
# /directorio    cliente(opciones)

# Sintaxis de clientes:
# - IP única: 192.168.1.100
# - Subred: 192.168.1.0/24
# - Hostname: cliente.ejemplo.com
# - Wildcard: *.ejemplo.com

# Ejemplos de opciones:
# rw       - Lectura/escritura
# ro       - Solo lectura
# sync     - Escrituras síncronas (más seguro, menos rendimiento)
# async    - Escrituras asíncronas (más rápido, menos seguro)
# no_subtree_check - Desactiva verificación de subdirectorios (recomendado)
# root_squash - Mapear root remoto a nobody (SEGURIDAD)
# no_root_squash - No mapear root (PELIGROSO)
# all_squash - Mapear todos los usuarios a nobody
```

**Ejemplo de `/etc/exports` básico:**

```bash
# /etc/exports

# Directorio compartido con toda la subred (lectura/escritura)
/datos/compartidos    192.168.1.0/24(rw,sync,no_subtree_check,root_squash)

# Solo lectura para clientes específicos
/datos/publicos       192.168.1.100(ro,sync,no_subtree_check)
/datos/publicos       192.168.1.101(ro,sync,no_subtree_check)

# Escritura solo para un servidor específico
/datos/backups        192.168.1.50(rw,sync,no_subtree_check,root_squash)

# Múltiples clientes en una línea
/var/www              192.168.1.0/24(ro,sync,no_subtree_check) 10.0.0.0/8(ro,sync)
```

**Aplicar configuración:**

```bash
# Crear directorios
sudo mkdir -p /datos/compartidos /datos/publicos /datos/backups

# Permisos
sudo chown -R nobody:nogroup /datos/compartidos
sudo chmod 755 /datos/compartidos

# Exportar configuración
sudo exportfs -a

# Verificar exports actuales
sudo exportfs -v

# Reiniciar servidor NFS
sudo systemctl restart nfs-kernel-server

# Verificar puertos (NFSv4 usa solo 2049)
sudo ss -tulnp | grep -E '(nfs|2049)'
```

#### NFSv4 con ID Mapping

NFSv4 usa ID mapping en lugar de confiar en UID/GID directamente.

```bash
# Configurar dominio NFSv4
sudo nano /etc/idmapd.conf
```

```ini
[General]
Verbosity = 0
Domain = ejemplo.com

[Mapping]
Nobody-User = nobody
Nobody-Group = nogroup
```

```bash
# Reiniciar servicio
sudo systemctl restart nfs-idmapd
```

**Export NFSv4 (usando bind mounts):**

```bash
# Crear raíz de exports NFSv4
sudo mkdir -p /export/compartidos

# Bind mount del directorio real
sudo mount --bind /datos/compartidos /export/compartidos

# Hacer permanente en /etc/fstab
echo "/datos/compartidos /export/compartidos none bind 0 0" | sudo tee -a /etc/fstab

# /etc/exports para NFSv4
sudo nano /etc/exports
```

```
# NFSv4 exports
/export                192.168.1.0/24(rw,sync,fsid=0,crossmnt,no_subtree_check)
/export/compartidos    192.168.1.0/24(rw,sync,no_subtree_check,root_squash)
```

```bash
# Aplicar
sudo exportfs -ra
```

#### Firewall configuration

```bash
# Ubuntu/Debian con ufw
sudo ufw allow from 192.168.1.0/24 to any port nfs
sudo ufw allow 2049/tcp

# Rocky Linux/RHEL con firewalld
sudo firewall-cmd --permanent --add-service=nfs
sudo firewall-cmd --permanent --add-service=mountd

```

### 3. NFS con Kerberos (Seguro)

**⚠️ IMPORTANTE**: Kerberos requiere infraestructura compleja (KDC, DNS correcto, sincronización de tiempo NTP). Solo para entornos empresariales.

#### Requisitos previos:
1. **KDC (Key Distribution Center)** configurado
2. **DNS funcional** con resolución forward y reverse correcta
3. **NTP sincronizado** en todos los hosts (diferencia <5 minutos = fallo Kerberos)
4. **Firewall**: Permitir Kerberos (88 TCP/UDP), kadmin (749), kpasswd (464)

#### Configuración básica (resumen):

```bash
# Servidor NFS - Instalar Kerberos
sudo apt install krb5-user nfs-kernel-server -y

# Crear principal para NFS en KDC
kadmin.local
  addprinc -randkey nfs/nfsserver.ejemplo.com
  ktadd nfs/nfsserver.ejemplo.com
  quit

# Configurar /etc/exports con Kerberos
# sec=krb5   - Solo autenticación
# sec=krb5i  - Autenticación + integridad
# sec=krb5p  - Autenticación + integridad + CIFRADO (recomendado)
```

```bash
# /etc/exports
/datos/seguros    192.168.1.0/24(rw,sync,sec=krb5p,no_subtree_check)
```

```bash
# Cliente NFS - Obtener ticket Kerberos
kinit usuario@EJEMPLO.COM

# Montar con Kerberos
sudo mount -t nfs4 -o sec=krb5p nfsserver.ejemplo.com:/datos/seguros /mnt/seguros

# Verificar ticket
klist
```

**⚠️ NOTA**: La configuración completa de Kerberos está fuera del alcance de este documento. Para producción, considere alternativas más simples (SSHFS, SMB 3.x) si no tiene experiencia con Kerberos.

### 4. SSHFS (Alternativa segura y simple)

SSHFS monta directorios remotos sobre SSH, proporcionando cifrado y autenticación robusta sin complejidad de Kerberos.

**Ventajas sobre NFS:**
- ✅ Cifrado automático (SSH)
- ✅ Autenticación con claves SSH (sin passwords)
- ✅ Firewall-friendly (solo puerto 22)
- ✅ No requiere configuración de servidor adicional (solo SSH)
- ✅ Funciona sobre WAN/Internet

**Instalación:**

```bash
# Ubuntu/Debian
sudo apt install sshfs -y

# Rocky Linux/RHEL
sudo dnf install fuse-sshfs -y
```

**Uso básico:**

```bash
# Montar directorio remoto
sshfs usuario@servidor.ejemplo.com:/datos/remotos /mnt/sshfs

# Con opciones
sshfs usuario@servidor.ejemplo.com:/datos/remotos /mnt/sshfs \
  -o reconnect,ServerAliveInterval=15,ServerAliveCountMax=3

# Con clave SSH específica
sshfs -o IdentityFile=~/.ssh/id_rsa usuario@servidor:/datos /mnt/sshfs

# Desmontar
fusermount -u /mnt/sshfs
# O
umount /mnt/sshfs
```

**Montaje automático con `/etc/fstab`:**

```bash
# /etc/fstab
usuario@servidor.ejemplo.com:/datos/remotos /mnt/sshfs fuse.sshfs defaults,_netdev,user,idmap=user,allow_other,reconnect,ServerAliveInterval=15 0 0

# Opciones:
# _netdev            - Esperar red
# user               - Permitir montaje por usuarios no-root
# idmap=user         - Mapear UID remoto al usuario local
# allow_other        - Permitir acceso a otros usuarios
# reconnect          - Reconectar automáticamente
# ServerAliveInterval - Keepalive SSH cada 15 segundos
```

**Script de montaje automático:**

```bash
#!/bin/bash
# mount_sshfs.sh - Montar SSHFS con autenticación por clave

REMOTE_HOST="servidor.ejemplo.com"
REMOTE_DIR="/datos/compartidos"
LOCAL_MOUNT="/mnt/sshfs"
SSH_KEY="$HOME/.ssh/id_rsa"
REMOTE_USER="usuario"

# Verificar que el punto de montaje existe
if [ ! -d "$LOCAL_MOUNT" ]; then
    sudo mkdir -p "$LOCAL_MOUNT"
fi

# Verificar si ya está montado
if mountpoint -q "$LOCAL_MOUNT"; then
    echo "⚠️  Ya está montado en $LOCAL_MOUNT"
    exit 0
fi

# Montar
echo "📁 Montando $REMOTE_HOST:$REMOTE_DIR en $LOCAL_MOUNT..."
sshfs "${REMOTE_USER}@${REMOTE_HOST}:${REMOTE_DIR}" "$LOCAL_MOUNT" \
    -o IdentityFile="$SSH_KEY" \
    -o reconnect \
    -o ServerAliveInterval=15 \
    -o ServerAliveCountMax=3 \
    -o idmap=user \
    -o allow_other

if [ $? -eq 0 ]; then
    echo "✅ Montaje exitoso"
else
    echo "❌ Error al montar"
    exit 1
fi
```

### 5. SMB/CIFS 3.x (Windows interoperability + seguridad)

**Ventajas de SMB 3.x:**
- ✅ Cifrado end-to-end (SMB 3.0+)
- ✅ Soporte nativo en Windows y Linux
- ✅ Autenticación robusta (Active Directory, NTLM, Kerberos)
- ✅ Mejor rendimiento en WAN que NFS
- ✅ Transparencia de failover (SMB 3.0+)

**Servidor Samba (Linux):**

```bash
# Instalar Samba
sudo apt install samba -y

# Configurar compartido seguro
sudo nano /etc/samba/smb.conf
```

```ini
[global]
   workgroup = EJEMPLO
   server string = Servidor Samba
   security = user
   encrypt passwords = yes
   
   # Seguridad: Solo SMB3 con cifrado
   server min protocol = SMB3
   server max protocol = SMB3
   smb encrypt = required

[datos]
   path = /datos/compartidos
   browseable = yes
   writable = yes
   valid users = @usuarios
   create mask = 0664
   directory mask = 0775
   # Requerir cifrado para este share
   smb encrypt = required
```

```bash
# Crear usuario Samba
sudo smbpasswd -a usuario

# Reiniciar Samba
sudo systemctl restart smbd

# Firewall
sudo ufw allow samba
```

**Cliente Linux (cifs-utils):**

```bash
# Instalar cliente
sudo apt install cifs-utils -y

# Montar con cifrado SMB3
sudo mount -t cifs //servidor/datos /mnt/smb \
    -o username=usuario,password=secreto,vers=3.0,seal

# Montaje con credenciales en archivo (más seguro)
echo "username=usuario" | sudo tee /root/.smbcredentials
echo "password=secreto" | sudo tee -a /root/.smbcredentials
sudo chmod 600 /root/.smbcredentials

# /etc/fstab
//servidor/datos /mnt/smb cifs credentials=/root/.smbcredentials,vers=3.0,seal,_netdev 0 0
```

### 6. Cloud Storage (AWS EFS, Azure Files)

#### AWS EFS (Elastic File System)

```bash
# Instalar utilidades EFS
sudo apt install nfs-common amazon-efs-utils -y

# Montar EFS usando mount helper (cifrado en tránsito automático)
sudo mount -t efs -o tls fs-12345678:/ /mnt/efs

# /etc/fstab
fs-12345678:/ /mnt/efs efs _netdev,tls,accesspoint=fsap-abcdef123456 0 0
```

**Ventajas de EFS:**
- ✅ Cifrado en tránsito (TLS) y en reposo (KMS)
- ✅ Escalabilidad automática (petabytes)
- ✅ Alta disponibilidad multi-AZ
- ✅ Integración con IAM
- ✅ Sin gestión de servidores

#### Azure Files

```bash
# Montar Azure Files via SMB 3.0 con cifrado
# Obtener comando de montaje desde Azure Portal

sudo mount -t cifs //storageaccount.file.core.windows.net/share /mnt/azure \
    -o username=storageaccount,password=STORAGE_KEY,vers=3.0,dir_mode=0777,file_mode=0777,serverino,seal
```

### 4. Demostración de vulnerabilidad NFSv3

**Escenario**: Atacante puede falsificar UID/GID para acceder a archivos.

```bash
# Servidor NFSv3 con root_squash deshabilitado (INSEGURO)
# /etc/exports
# /datos/inseguro 192.168.1.0/24(rw,sync,no_subtree_check,no_root_squash)

# Cliente legítimo (UID 1000)
mkdir /mnt/nfs/archivos_usuario1000
touch /mnt/nfs/archivos_usuario1000/secreto.txt
ls -ln /mnt/nfs/archivos_usuario1000/
# -rw-r--r-- 1 1000 1000 0 Mar 30 10:00 secreto.txt

# Cliente atacante: Crear usuario con UID 1000
sudo useradd -u 1000 fake_user

# Atacante puede acceder al archivo
su - fake_user
cat /mnt/nfs/archivos_usuario1000/secreto.txt
# ✅ Acceso exitoso sin autenticación real

# SOLUCIÓN: Usar Kerberos, SSHFS, o SMB con autenticación robusta
```

**Demostración de sniffing NFSv3:**

```bash
# Terminal 1: Cliente escribe archivo sensible
echo "password=secreto123" > /mnt/nfs/config.txt

# Terminal 2: Atacante captura tráfico
sudo tcpdump -i any -A 'port 2049' | grep -i password

# Resultado: ¡Password visible en tráfico!
# password=secreto123

# SOLUCIÓN: NFSv4 con krb5p, SSHFS, o SMB3 con cifrado
```

## Aspectos de Seguridad

### 1. Vulnerabilidades de NFSv2/v3

#### Problema 1: Autenticación basada en UID/GID (fácil de falsificar)

```
Servidor NFS confía en:
- UID del cliente (no verificado)
- Dirección IP del cliente (spoofing posible)

Cliente malicioso:
1. Obtiene UID de víctima (observando ls -ln)
2. Crea usuario local con mismo UID
3. Accede a archivos de la víctima sin credenciales

NO HAY VERIFICACIÓN DE IDENTIDAD REAL
```

#### Problema 2: Sin cifrado (sniffing)

Todo el contenido de archivos viaja en texto plano:

```bash
# Captura en red
sudo tcpdump -i any -A 'port 2049'

# Archivos visibles:
# - Nombres de archivos
# - Contenido completo (passwords, datos sensibles)
# - Metadata (propietario, permisos)
```

#### Problema 3: Sin integridad de datos

Atacante Man-in-the-Middle puede:
- Modificar contenido de archivos en tránsito
- Cambiar permisos
- Inyectar malware en archivos

**NO hay firma criptográfica para detectar modificaciones**

#### Problema 4: Múltiples puertos (firewall complejo)

NFSv3 requiere:
- **2049**: nfsd
- **111**: portmapper/rpcbind
- **Dinámicos**: mountd, statd, lockd

Dificulta configuración de firewall y aumenta superficie de ataque.

### 2. Mejoras de seguridad en NFSv4

#### Con Kerberos (sec=krb5p):
- ✅ **Autenticación mutua**: Cliente y servidor verifican identidad
- ✅ **Cifrado**: Datos protegidos con AES (krb5p)
- ✅ **Integridad**: Detección de modificaciones (HMAC)
- ✅ **Puerto único (2049)**: Mejor para firewall
- ✅ **ACLs granulares**: Permisos más finos que POSIX

**Niveles de seguridad en NFSv4:**
- `sec=sys` - Default, basado en UID/GID (⚠️ inseguro, igual que NFSv3)
- `sec=krb5` - Solo autenticación Kerberos
- `sec=krb5i` - Autenticación + **integridad** de datos
- `sec=krb5p` - Autenticación + integridad + **cifrado** (RECOMENDADO)

#### Limitaciones de NFSv4 + Kerberos:
- ❌ **Complejidad**: Requiere KDC, DNS correcto, NTP sincronizado
- ❌ **Curva de aprendizaje**: Administración Kerberos no trivial
- ❌ **Single point of failure**: KDC caído = no acceso
- ❌ **Renovación de tickets**: Gestión de keytabs y principales

### 3. Comparación de seguridad: NFS vs Alternativas

| Aspecto | NFSv3 | NFSv4+Kerberos | SSHFS | SMB 3.x |
|---------|-------|----------------|-------|---------|
| **Autenticación** | ❌ UID/GID | ✅ Kerberos | ✅ SSH keys/password | ✅ AD/NTLM |
| **Cifrado** | ❌ | ✅ krb5p | ✅ AES (SSH) | ✅ AES-128-GCM |
| **Integridad** | ❌ | ✅ HMAC | ✅ HMAC | ✅ HMAC-SHA256 |
| **Complejidad setup** | Baja | **Muy alta** | Baja | Media |
| **Resistencia MITM** | ❌ | ✅ | ✅ | ✅ |
| **Compliance-ready** | ❌ | ⚠️ (configurado) | ✅ | ✅ |
| **Firewall-friendly** | ❌ (v3) | ✅ | ✅ | ✅ |

### 4. Best practices de seguridad NFS

#### Si debe usar NFS:

**Configuración mínima aceptable:**

```bash
# /etc/exports - Configuración segura

# ✅ Especificar subred exacta (no wildcards amplios)
/datos/compartidos    192.168.1.0/24(rw,sync,no_subtree_check,root_squash)

# ❌ NUNCA hacer:
# /datos  *(rw,no_root_squash,insecure)
# Problemas: acceso desde cualquier IP, root sin mapear, puertos inseguros

# ✅ Solo lectura cuando sea posible
/datos/publicos    192.168.1.0/24(ro,sync,no_subtree_check,all_squash)

# ✅ Usar NFSv4 con Kerberos para datos sensibles
/datos/confidenciales    192.168.1.0/24(rw,sync,sec=krb5p,no_subtree_check)
```

**Firewall estricto:**

```bash
# Solo permitir IPs específicas
sudo ufw allow from 192.168.1.100 to any port 2049 proto tcp
sudo ufw allow from 192.168.1.101 to any port 2049 proto tcp

# Denegar todo lo demás
sudo ufw default deny incoming
```

**Monitoreo:**

```bash
# Logs de acceso NFS
sudo journalctl -u nfs-server -f

# Alertar en accesos sospechosos
# Ejemplo con fail2ban (filtro personalizado)
# Detectar intentos de acceso desde IPs no autorizadas
```

#### Opciones seguras recomendadas:

| Escenario | Solución recomendada | Razón |
|-----------|----------------------|-------|
| **Desarrollo local** | NFS básico sin Kerberos | Simplicidad, red confiable |
| **Producción interna** | SSHFS o SMB 3.x | Balance seguridad/simplicidad |
| **Producción alta seguridad** | SSHFS, SMB 3.x + cifrado, o cloud storage | Cifrado sin complejidad Kerberos |
| **HPC / Alto rendimiento** | NFSv4.1/4.2 con Kerberos | pNFS para paralelismo |
| **Windows interop** | SMB 3.x nativo | Integración nativa Windows |
| **Cloud/híbrido** | AWS EFS, Azure Files, GCP Filestore | Escalabilidad, seguridad managed |

### 5. Alternativas Seguras Detalladas

#### SSHFS - La alternativa más simple

**Cuándo usar:**
- ✅ Equipos técnicos que ya usan SSH
- ✅ Acceso ocasional a archivos remotos
- ✅ Entornos donde NFS/Kerberos es overkill
- ✅ Acceso sobre Internet (con VPN o SSH hardening)

**Desventajas:**
- ❌ Rendimiento menor que NFS en LAN pura
- ❌ No es ideal para cargas I/O intensivas (databases)
- ❌ Sin soporte nativo en Windows (requiere WinFsp + SSHFS-Win)

**Setup completo con autenticación por clave:**

```bash
# Generar clave SSH (cliente)
ssh-keygen -t ed25519 -C "nfs-replacement"

# Copiar clave pública al servidor
ssh-copy-id usuario@servidor.ejemplo.com

# Probar conexión sin password
ssh usuario@servidor.ejemplo.com "echo Conexión exitosa"

# Montar con opciones de rendimiento
sshfs usuario@servidor.ejemplo.com:/datos /mnt/sshfs \
  -o compression=yes \
  -o cache=yes \
  -o kernel_cache \
  -o Ciphers=aes128-gcm@openssh.com \
  -o reconnect \
  -o ServerAliveInterval=15

# Script de montaje automático al login
echo "sshfs usuario@servidor.ejemplo.com:/datos $HOME/remotos -o reconnect,compression=yes,cache=yes" >> ~/.bashrc
```

#### SMB 3.x - Mejor Windows interoperability

**Cuándo usar:**
- ✅ Entornos mixtos Windows/Linux
- ✅ Integración con Active Directory
- ✅ Mejor rendimiento WAN que NFS
- ✅ Failover automático (SMB Multichannel)

**Configuración de Samba con cifrado forzado:**

```ini
# /etc/samba/smb.conf

[global]
   # Seguridad
   server min protocol = SMB3_00
   server max protocol = SMB3_11
   smb encrypt = required
   
   # Auditoría
   log level = 2
   log file = /var/log/samba/%m.log
   max log size = 5000
   
   # Autenticación
   security = user
   passdb backend = tdbsam
   
[datos_cifrados]
   path = /srv/samba/datos
   valid users = @datagroup
   writable = yes
   browseable = yes
   create mask = 0660
   directory mask = 0770
   # Forzar cifrado en este share
   smb encrypt = required
```

**Cliente Windows:**

```powershell
# PowerShell - Montar con cifrado
New-SmbMapping -LocalPath Z: -RemotePath \\servidor\datos_cifrados `
  -Username "usuario" -Password "password" `
  -RequireIntegrity $true -RequirePrivacy $true

# Verificar cifrado habilitado
Get-SmbConnection | Select-Object -Property ServerName, ShareName, Encrypted
```

#### Cloud Storage - Solución managed

**AWS EFS con cifrado:**

```bash
# mount-efs.sh con cifrado en tránsito
#!/bin/bash

EFS_ID="fs-0123456789abcdef0"
MOUNT_POINT="/mnt/efs"
REGION="us-east-1"

sudo mkdir -p "$MOUNT_POINT"

# Montar con TLS (cifrado en tránsito)
sudo mount -t efs -o tls,accesspoint=fsap-123456 "$EFS_ID":/ "$MOUNT_POINT"

if [ $? -eq 0 ]; then
    echo "✅ EFS montado con cifrado TLS"
else
    echo "❌ Error al montar EFS"
    exit 1
fi

# Verificar montaje
df -h | grep efs
```

**Azure Files con SMB 3.0:**

```bash
# Montar Azure Files con cifrado SMB 3.0
STORAGE_ACCOUNT="mystorageaccount"
SHARE_NAME="myshare"
STORAGE_KEY="XXXXX"

sudo mount -t cifs //"$STORAGE_ACCOUNT".file.core.windows.net/"$SHARE_NAME" /mnt/azure \
  -o username="$STORAGE_ACCOUNT",password="$STORAGE_KEY",vers=3.0,seal,dir_mode=0777,file_mode=0777,serverino

# seal = cifrado SMB
# vers=3.0 = SMB 3.0 mínimo
```

### 6. Compliance y regulaciones

**PCI-DSS (Payment Card Industry):**
- ❌ NFSv3 sin cifrado **viola PCI-DSS 4.1** (cifrado de datos en tránsito)
- ✅ NFSv4 con krb5p, SSHFS, SMB 3.x con cifrado **cumplen**

**HIPAA (Healthcare):**
- ❌ NFSv3 **no cumple** con HIPAA Security Rule (164.312(e)(1))
- ✅ Requerido: Cifrado end-to-end para PHI (Protected Health Information)

**GDPR (General Data Protection Regulation):**
- ❌ NFSv3 para datos personales **incumple** Artículo 32 (seguridad del tratamiento)
- ✅ Requerido: Cifrado de datos personales en tránsito

**ISO 27001:**
- ❌ NFSv3 **no cumple** A.10.1.1 (política de uso de controles criptográficos)
- ✅ Requerido: Cifrado para información clasificada

**Caso de uso: Directorio compartido para uploads en cluster web**

# Servidor NFS dedicado para uploads
# /etc/exports
/var/www/uploads  10.0.1.0/24(rw,sync,no_subtree_check,root_squash)

# /etc/fstab en cada app server
nfs-server.local:/var/www/uploads  /var/www/uploads  nfs4  defaults,_netdev  0  0

# Ventajas:
# ✅ Uploads visibles inmediatamente en todos los servidores
# ✅ Sin duplicación de almacenamiento

# ❌ Latencia adicional vs disco local

**Alternativa con SSHFS para mayor seguridad:**

```bash
# Cada app server monta vía SSHFS
sshfs webapp@storage-server:/var/www/uploads /var/www/uploads \
  -o IdentityFile=/root/.ssh/webapp_key,reconnect,ServerAliveInterval=15

# Ventajas adicionales:
# ✅ Cifrado automático
# ✅ Autenticación por clave SSH
# ✅ No requiere configurar servidor NFS
```

### 5. Migración de NFS a alternativas

**Estrategia de migración NFSv3 → SSHFS:**

```bash
#!/bin/bash
# migrate_nfs_to_sshfs.sh

# Paso 1: Backup de /etc/exports
sudo cp /etc/exports /etc/exports.backup

# Paso 2: Desmontar clientes NFS
for client in server1 server2 server3; do
    echo "Desmontando NFS en $client..."
    ssh root@$client "umount /mnt/nfs-old; sed -i '/nfs-old/d' /etc/fstab"
done

# Paso 3: Configurar SSH keys en todos los clientes
for client in server1 server2 server3; do
    echo "Configurando SSHFS en $client..."
    ssh root@$client << 'EOF'
        # Instalar SSHFS
        apt install sshfs -y
        
        # Generar clave SSH
        ssh-keygen -t ed25519 -f /root/.ssh/storage_key -N ""
        
        # Copiar clave a storage server
        ssh-copy-id -i /root/.ssh/storage_key.pub storage-user@storage-server
        
        # Montar vía SSHFS
        mkdir -p /mnt/sshfs-new
        sshfs storage-user@storage-server:/datos /mnt/sshfs-new \
            -o IdentityFile=/root/.ssh/storage_key,reconnect
        
        # Agregar a fstab
        echo "storage-user@storage-server:/datos /mnt/sshfs-new fuse.sshfs defaults,_netdev,IdentityFile=/root/.ssh/storage_key,reconnect 0 0" >> /etc/fstab
EOF
done

# Paso 4: Verificar montajes
for client in server1 server2 server3; do
    echo "Verificando $client..."
    ssh root@$client "df -h | grep sshfs"
done

# Paso 5: Desactivar NFS server (después de validación)
echo "⚠️  Validar que todo funciona antes de ejecutar:"
echo "sudo systemctl stop nfs-server"
echo "sudo systemctl disable nfs-server"
```

### 6. Monitoreo y alertas

**Script de monitoreo de montajes NFS/SSHFS:**

```bash
#!/bin/bash
# monitor_mounts.sh

MOUNTS=("/mnt/nfs/compartidos" "/mnt/sshfs" "/mnt/smb")
EMAIL="admin@ejemplo.com"

for mount in "${MOUNTS[@]}"; do
    if ! mountpoint -q "$mount"; then
        echo "❌ ALERTA: $mount no está montado" | mail -s "Montaje caído: $mount" "$EMAIL"
        
        # Intentar remontar automáticamente
        mount "$mount" 2>&1 | logger -t mount-check
    else
        # Verificar acceso de escritura
        if ! touch "$mount/.health_check" 2>/dev/null; then
            echo "❌ ALERTA: $mount montado pero sin acceso de escritura" | mail -s "Montaje read-only: $mount" "$EMAIL"
        else
            rm -f "$mount/.health_check"
        fi
    fi
done
```

- [ ] Plan de backup del storage server
- [ ] Alta disponibilidad (DRBD + Pacemaker o cloud)

- [ ] Autenticación por claves SSH (no passwords)

- [ ] Script de montaje automático con reconnect
- [ ] Monitoreo de conexiones SSH

- [ ] Configurar auditoría de accesos

- [ ] Cifrado en tránsito (TLS) y en reposo (KMS)

## Resumen Ejecutivo

**NFS es útil en LAN confiable, pero tiene serias limitaciones de seguridad en versiones antiguas.**

**Problemas críticos de NFSv2/v3:**
- ❌ Sin autenticación real (basado en UID/GID falsificable)
- ❌ Sin cifrado (sniffing posible)
- ❌ Sin integridad de datos (MITM posible)
- ❌ No cumple compliance (PCI-DSS, HIPAA, GDPR)

**NFSv4 con Kerberos mejora significativamente**, pero:
- ⚠️ Complejidad alta (KDC, DNS, NTP)
- ⚠️ Curva de aprendizaje pronunciada
- ⚠️ Gestión de tickets y keytabs no trivial

**Alternativas recomendadas:**

1. **SSHFS** - Mejor para:
   - ✅ Equipos técnicos que ya usan SSH
   - ✅ Simplicidad (sin KDC)
   - ✅ Cifrado automático
   - ✅ Acceso sobre Internet (con VPN)

2. **SMB 3.x** - Mejor para:
   - ✅ Entornos Windows/Linux mixtos
   - ✅ Integración Active Directory
   - ✅ Cifrado sin complejidad Kerberos
   - ✅ Mejor rendimiento WAN

3. **Cloud Storage** - Mejor para:
   - ✅ Escalabilidad automática
   - ✅ Alta disponibilidad managed
   - ✅ Sin gestión de servidores
   - ✅ Backup y replication integrados

**Conclusión**: Salvo que tenga infraestructura Kerberos existente o requiera alto rendimiento en HPC, **considere SSHFS o SMB 3.x** como alternativas más simples y seguras a NFS para la mayoría de casos de uso empresariales.
