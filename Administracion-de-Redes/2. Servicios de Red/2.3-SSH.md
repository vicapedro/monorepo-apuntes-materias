# 2.3 SSH - Secure Shell

## Descripción

**SSH (Secure Shell)** es un protocolo criptográfico de red que permite acceso remoto seguro a sistemas, ejecución de comandos, transferencia de archivos y tunneling de tráfico de red. SSH reemplaza a protocolos inseguros como **Telnet, rlogin y rsh**, proporcionando autenticación robusta y cifrado de toda la comunicación.

### Telnet: El Antecedente Inseguro

Antes de SSH, **Telnet (RFC 854, 1983)** era el protocolo estándar para acceso remoto a servidores.

```
TELNET - Problemas Críticos de Seguridad:

┌─────────────┐                                    ┌─────────────┐
│   Cliente   │                                    │   Servidor  │
│   (Admin)   │                                    │   (Linux)   │
└──────┬──────┘                                    └──────┬──────┘
       │                                                   │
       │  1. Conexión a puerto 23 (Telnet)               │
       │──────────────────────────────────────────────────>│
       │                                                   │
       │  2. Login: admin (TEXTO PLANO) ❌                │
       │──────────────────────────────────────────────────>│
       │                                                   │
       │  3. Password: P@ssw0rd (TEXTO PLANO) ❌          │
       │──────────────────────────────────────────────────>│
       │                                                   │
       │  4. Comando: cat /etc/shadow (TEXTO PLANO) ❌    │
       │──────────────────────────────────────────────────>│
       │                                                   │
       │  5. Respuesta (TEXTO PLANO) ❌                   │
       │<──────────────────────────────────────────────────│
       │                                                   │

ATACANTE en la red puede:
  • Capturar credenciales con Wireshark/tcpdump
  • Ver todos los comandos ejecutados
  • Ver todas las respuestas (datos sensibles)
```

### ¿Por Qué Ya NO Usar Telnet?

| Característica | Telnet | SSH |
|---------------|--------|-----|
| **Cifrado** | ❌ Ninguno (texto plano) | ✅ Cifrado AES-256, ChaCha20 |
| **Autenticación** | ❌ Password en claro | ✅ Password cifrado + llaves públicas |
| **Integridad** | ❌ Sin verificación | ✅ HMAC (SHA-256, SHA-512) |
| **Confidencialidad** | ❌ Todo visible | ✅ Todo cifrado extremo a extremo |
| **Autenticación servidor** | ❌ Sin verificar identidad | ✅ Host key verification |
| **Protección MITM** | ❌ Vulnerable | ✅ Protegido |
| **Transferencia archivos** | ❌ No integrado | ✅ SCP/SFTP integrado |
| **Port forwarding** | ❌ No | ✅ Sí (tunneling) |
| **Auditoría** | ⚠️ Limitada | ✅ Logs detallados |
| **Cumplimiento** | ❌ No cumple PCI-DSS, SOX | ✅ Cumple estándares |

### Casos Donde Telnet AÚN Existe (NO RECOMENDADO)

```
1. EQUIPOS LEGACY:
   - Switches/routers viejos sin soporte SSH
   - Sistemas embebidos antiguos
   - ⚠️ SOLUCIÓN: Upgrade firmware o reemplazo

2. ENTORNOS DE LABORATORIO AISLADOS:
   - Redes internas sin acceso a Internet
   - VMs de prueba desechables
   - ⚠️ AUN ASÍ: Usar SSH para formar buenos hábitos

3. CONSOLAS DE ADMINISTRACIÓN (No es realmente Telnet):
   - Puerto serial/consola de equipos
   - Acceso físico directo
   - Comunicación local, no por red

4. TESTING DE SERVICIOS (Telnet como cliente):
   - Probar puertos TCP manualmente
   - Ejemplo: telnet mail.servidor.com 25 (SMTP)
   - ⚠️ USO VÁLIDO: Solo como herramienta de diagnóstico
```

**Ejemplo de uso legítimo de Telnet como cliente de testing:**

```bash
# Probar si puerto SMTP está abierto (NO es acceso remoto)
telnet mail.empresa.com 25

# Output:
Trying 192.168.1.120...
Connected to mail.empresa.com.
220 mail.empresa.com ESMTP Postfix

# Enviar comandos SMTP manualmente para debugging
EHLO test.com
QUIT

# Esto es DIFERENTE de usar Telnet para acceso remoto
```

### SSH: La Solución Segura

SSH fue desarrollado en 1995 por Tatu Ylönen (Universidad de Tecnología de Helsinki) como respuesta directa a ataques de sniffing de passwords que comprometieron su red universitaria.

```
SSH - Comunicación Segura:

┌─────────────┐                                    ┌─────────────┐
│   Cliente   │                                    │   Servidor  │
│   (Admin)   │                                    │   (Linux)   │
└──────┬──────┘                                    └──────┬──────┘
       │                                                   │
       │  1. Conexión a puerto 22 (SSH)                   │
       │──────────────────────────────────────────────────>│
       │                                                   │
       │  2. Intercambio de llaves (Diffie-Hellman)       │
       │<─────────────────────────────────────────────────>│
       │     Establecen clave de sesión simétrica          │
       │                                                   │
       │  3. Verificación host key (prevenir MITM)        │
       │<──────────────────────────────────────────────────│
       │                                                   │
       │  4. Login: admin (CIFRADO AES-256) ✅            │
       │═══════════════════════════════════════════════════>│
       │                                                   │
       │  5. Password: P@ssw0rd (CIFRADO) ✅              │
       │═══════════════════════════════════════════════════>│
       │                                                   │
       │  6. Comando: cat /etc/shadow (CIFRADO) ✅        │
       │═══════════════════════════════════════════════════>│
       │                                                   │
       │  7. Respuesta (CIFRADA) ✅                       │
       │<═══════════════════════════════════════════════════│
       │                                                   │
       ▼                                                   ▼

ATACANTE ve solo:
  • Tráfico cifrado incomprensible
  • Longitudes de paquetes (pero no contenido)
  • No puede descifrar sin la clave de sesión
```

### Arquitectura de SSH

SSH utiliza un modelo **cliente-servidor** con tres capas:

```
CAPA DE TRANSPORTE (SSH-TRANS, RFC 4253)
  • Establecimiento de conexión segura
  • Intercambio de llaves (key exchange)
  • Cifrado de datos (AES, ChaCha20)
  • Integridad de datos (HMAC)
  • Compresión (opcional)
  
CAPA DE AUTENTICACIÓN (SSH-AUTH, RFC 4252)
  • Autenticación de usuario
  • Métodos: password, public key, keyboard-interactive, GSSAPI
  
CAPA DE CONEXIÓN (SSH-CONN, RFC 4254)
  • Multiplexación de canales
  • Sesiones interactivas (shell)
  • Ejecución de comandos remotos
  • Transferencia de archivos (SFTP)
  • Port forwarding (tunneling)
  • X11 forwarding
```

### Flujo de Conexión SSH

```
PASO 1 - Negociación de Versión:
Cliente → "SSH-2.0-OpenSSH_8.9"
Servidor → "SSH-2.0-OpenSSH_8.9"

PASO 2 - Intercambio de Algoritmos:
Cliente → Lista de algoritmos soportados (cifrado, MAC, compresión)
Servidor → Selecciona algoritmos compatibles

PASO 3 - Intercambio de Llaves (Diffie-Hellman):
Cliente y Servidor generan clave de sesión compartida
  • Sin transmitir la clave por la red
  • Clave única por sesión (forward secrecy)

PASO 4 - Verificación del Servidor (Host Key):
Servidor → Envía su clave pública (host key)
Cliente → Verifica contra ~/.ssh/known_hosts
  • Primera conexión: Pide confirmación al usuario
  • Conexiones subsecuentes: Verifica automáticamente
  • Si cambia: ⚠️ WARNING: POSSIBLE MAN-IN-THE-MIDDLE ATTACK!

PASO 5 - Autenticación del Cliente:
Opción A: Password
  Cliente → Envía password (cifrado)
  Servidor → Verifica contra /etc/shadow

Opción B: Public Key (más seguro)
  Cliente → "Quiero autenticarme con clave pública"
  Servidor → Envía challenge (datos aleatorios)
  Cliente → Firma challenge con clave privada
  Servidor → Verifica firma con clave pública (~/.ssh/authorized_keys)

PASO 6 - Sesión Establecida:
  • Canal cifrado establecido
  • Cliente puede ejecutar comandos
  • Transferir archivos
  • Crear tunnels
```

## RFCs de Referencia

SSH está definido por múltiples RFCs que especifican su arquitectura, seguridad y operación.

### RFCs Fundamentales (SSH Protocol Suite)

```
RFC 4250 - "The Secure Shell (SSH) Protocol Assigned Numbers" (2006)
  • Registro de números asignados para SSH
  • Tipos de mensajes, algoritmos, códigos
  • Estado: ESTÁNDAR PROPUESTO

RFC 4251 - "The Secure Shell (SSH) Protocol Architecture" (2006)
  • Arquitectura general de SSH
  • Modelo de capas (Transport, Authentication, Connection)
  • Conceptos de seguridad
  • Estado: ESTÁNDAR PROPUESTO

RFC 4252 - "The Secure Shell (SSH) Authentication Protocol" (2006)
  • Protocolo de autenticación
  • Métodos: publickey, password, hostbased, none
  • Flujo de autenticación
  • Estado: ESTÁNDAR PROPUESTO

RFC 4253 - "The Secure Shell (SSH) Transport Layer Protocol" (2006)
  • Capa de transporte
  • Intercambio de llaves (Diffie-Hellman)
  • Cifrado y MAC
  • Host key verification
  • Estado: ESTÁNDAR PROPUESTO

RFC 4254 - "The Secure Shell (SSH) Connection Protocol" (2006)
  • Protocolo de conexión
  • Canales (channels)
  • Port forwarding (local, remote, dynamic)
  • X11 forwarding
  • Estado: ESTÁNDAR PROPUESTO
```

### RFCs de Extensiones y Mejoras

```
RFC 4255 - "Using DNS to Securely Publish SSH Key Fingerprints" (2006)
  • SSHFP records en DNS
  • Verificación de host keys vía DNSSEC
  • Prevención MITM

RFC 4256 - "Generic Message Exchange Authentication for SSH" (2006)
  • Autenticación interactiva (keyboard-interactive)
  • Soporte para múltiples prompts
  • Usado por 2FA, OTP

RFC 4335 - "The SSH Session Channel Break Extension" (2006)
  • Envío de señal BREAK
  • Útil para consolas seriales sobre SSH

RFC 4344 - "The SSH Transport Layer Encryption Modes" (2006)
  • Modos de cifrado adicionales
  • AES en modo CTR (Counter)

RFC 4345 - "Improved Arcfour Modes for SSH" (2006)
  • Variantes mejoradas de cifrado Arcfour
  • (Nota: Arcfour/RC4 ya no recomendado)

RFC 4419 - "Diffie-Hellman Group Exchange for SSH" (2006)
  • Negociación dinámica de grupo DH
  • Permite tamaños de grupo variables

RFC 4432 - "RSA Key Exchange for SSH" (2006)
  • Intercambio de llaves basado en RSA
  • Alternativa a Diffie-Hellman

RFC 4462 - "Generic Security Service Application Program Interface (GSS-API)
           Authentication and Key Exchange for SSH" (2006)
  • Autenticación GSSAPI
  • Integración con Kerberos
  • Single Sign-On (SSO)

RFC 4716 - "The Secure Shell (SSH) Public Key File Format" (2006)
  • Formato estándar de archivos de clave pública
  • Diferente de formato OpenSSH
```

### RFCs de Seguridad y Algoritmos

```
RFC 4819 - "Secure Shell Public Key Subsystem" (2006)
  • Subsistema para gestión de claves públicas
  • Permite administración remota de authorized_keys

RFC 5656 - "Elliptic Curve Algorithm Integration in SSH" (2009)
  • Algoritmos de curva elíptica (ECDSA, ECDH)
  • Mayor seguridad con claves más cortas
  • Mejor rendimiento

RFC 6187 - "X.509v3 Certificates for SSH Authentication" (2011)
  • Uso de certificados X.509 en SSH
  • Integración con PKI empresarial

RFC 6668 - "SHA-2 Data Integrity Verification for SSH" (2012)
  • Algoritmos HMAC con SHA-256 y SHA-512
  • Reemplaza SHA-1 (más débil)

RFC 8268 - "More Modular Exponentiation (MODP) Diffie-Hellman (DH)
           Key Exchange (KEX) Groups for SSH" (2017)
  • Grupos DH adicionales (3072, 4096, 6144, 8192 bits)
  • Mayor seguridad contra ataques

RFC 8308 - "Extension Negotiation in the Secure Shell (SSH) Protocol" (2018)
  • Negociación de extensiones
  • Permite nuevas capacidades sin romper compatibilidad

RFC 8332 - "Use of RSA Keys with SHA-256 and SHA-512 in SSH" (2018)
  • RSA con hashes SHA-2
  • Reemplaza RSA-SHA1

RFC 8709 - "Ed25519 and Ed448 Public Key Algorithms for SSH" (2020)
  • Algoritmos EdDSA (curvas Edwards)
  • Más seguro y rápido que RSA/ECDSA
  • Resistente a timing attacks
```

### Resumen de RFCs por Categoría

| Categoría | RFCs Principales | Propósito |
|-----------|------------------|-----------|
| **Fundamentos** | 4250, 4251, 4252, 4253, 4254 | Arquitectura base SSH-2 |
| **Autenticación** | 4252, 4256, 4462 | Métodos de autenticación |
| **Cifrado** | 4344, 5656, 8709 | Algoritmos modernos (AES, ECC, Ed25519) |
| **Integridad** | 6668, 8332 | HMAC-SHA2, RSA-SHA2 |
| **Extensiones** | 4255, 4716, 4819, 8308 | Funcionalidades adicionales |
| **Seguridad** | 4419, 8268 | DH groups, key exchange |

## Objetivo

### Propósitos Principales de SSH

1. **Acceso Remoto Seguro**
   - Reemplazar Telnet, rlogin, rsh
   - Shell interactivo cifrado
   - Ejecución de comandos remotos

2. **Transferencia Segura de Archivos**
   - SCP (Secure Copy Protocol)
   - SFTP (SSH File Transfer Protocol)
   - Reemplazar FTP inseguro

3. **Tunneling y Port Forwarding**
   - Local port forwarding (acceso a servicios remotos)
   - Remote port forwarding (exponer servicios locales)
   - Dynamic port forwarding (SOCKS proxy)
   - VPN-like functionality

4. **Automatización Segura**
   - Scripts de administración
   - Backups remotos
   - Deployment de aplicaciones (Ansible, Fabric)
   - Integración CI/CD

5. **X11 Forwarding**
   - Ejecutar aplicaciones gráficas remotas
   - Display redirigido a cliente

### Casos de Uso Reales

```
ADMINISTRACIÓN DE SERVIDORES:
- Acceso a servidores Linux/Unix/BSD remotos
- Ejecutar comandos de mantenimiento
- Monitoreo en tiempo real (top, htop)
- Revisión de logs

TRANSFERENCIA DE ARCHIVOS:
- Backups de bases de datos a servidor remoto
- Subir/descargar archivos de configuración
- Sincronización de directorios (rsync sobre SSH)

DESARROLLO:
- Git push/pull sobre SSH
- Edición remota de código (VSCode Remote-SSH)
- Debugging de aplicaciones remotas

TUNNELING:
- Acceso a bases de datos remotas (MySQL, PostgreSQL)
- Acceso a paneles web internos (VNC, Proxmox, ESXi)
- Bypass de firewalls corporativos (SOCKS proxy)

AUTOMATIZACIÓN:
- Ansible: Gestión de configuración
- Fabric/Paramiko: Scripts Python para deployment
- Capistrano: Deployment Ruby on Rails
- CI/CD: Jenkins, GitLab CI ejecutando comandos remotos
```

#### Archivo de Configuración Principal

**Ubicación:** `/etc/ssh/sshd_config`

```bash
# Ver configuración actual (sin comentarios)
grep -v '^#' /etc/ssh/sshd_config | grep -v '^$'
```

**Configuración Básica Segura:**

```bash
sudo nano /etc/ssh/sshd_config
```

```
# /etc/ssh/sshd_config - Configuración recomendada

# Puerto SSH (cambiar de 22 reduce bots automatizados)
Port 22
# Port 2222  # Opcional: cambiar puerto

# Direcciones IP en las que escuchar
ListenAddress 0.0.0.0  # IPv4 todas las interfaces
# ListenAddress 192.168.1.10  # Específica

# Protocolo SSH (solo SSH-2, SSH-1 es inseguro)
Protocol 2

# Host Keys (llaves del servidor)
HostKey /etc/ssh/ssh_host_rsa_key
HostKey /etc/ssh/ssh_host_ecdsa_key
HostKey /etc/ssh/ssh_host_ed25519_key

# Logging
SyslogFacility AUTH
LogLevel INFO

# Autenticación
PermitRootLogin no  # ⚠️ CRÍTICO: Nunca permitir login root directo
MaxAuthTries 3      # Máximo 3 intentos de password
MaxSessions 10      # Máximo 10 sesiones simultáneas

PubkeyAuthentication yes  # Autenticación por llave pública
PasswordAuthentication yes  # Password permitido (cambiar a no después de configurar llaves)
PermitEmptyPasswords no  # Nunca permitir passwords vacíos

# Challenge-Response (para 2FA)
ChallengeResponseAuthentication no

# Autenticación Kerberos/GSSAPI
GSSAPIAuthentication no
GSSAPICleanupCredentials yes

# Autenticación basada en host (rara vez usada)
HostbasedAuthentication no
IgnoreRhosts yes

# X11 Forwarding
X11Forwarding yes  # Permitir aplicaciones gráficas
X11DisplayOffset 10
X11UseLocalhost yes

# Port Forwarding / Tunneling
AllowTcpForwarding yes
GatewayPorts no  # No permitir binds externos
PermitTunnel no  # VPN-like tunnel (normalmente no necesario)

# Configuración de sesión
PrintMotd no  # Message of the day (manejado por PAM)
PrintLastLog yes
TCPKeepAlive yes
Compression delayed  # Comprimir después de autenticación

# Variables de entorno permitidas
AcceptEnv LANG LC_*

# Subsistema SFTP
Subsystem sftp /usr/lib/openssh/sftp-server

# Permitir/denegar usuarios específicos
# AllowUsers admin usuario1 usuario2
# DenyUsers hacker malicioso
# AllowGroups ssh-users
# DenyGroups no-ssh

# Timeout de sesiones inactivas
ClientAliveInterval 300  # Ping cada 5 minutos
ClientAliveCountMax 2    # Desconectar después de 2 pings sin respuesta

# Banner de advertencia
# Banner /etc/ssh/banner.txt

# Deshabilitar forwarding de agente (si no se necesita)
AllowAgentForwarding yes

# Limitar conexiones concurrentes por IP
MaxStartups 10:30:60
# 10 conexiones concurrentes, rechazar 30% adicionales, máximo 60 total
```

**Aplicar configuración:**

```bash
# Verificar sintaxis
sudo sshd -t

# Si no hay errores, reiniciar
sudo systemctl restart ssh  # Ubuntu/Debian
sudo systemctl restart sshd  # Rocky/RHEL

# Verificar puerto escuchando
sudo ss -tlnp | grep ssh
# LISTEN 0      128          0.0.0.0:22        0.0.0.0:*    users:(("sshd",pid=1234,fd=3))
```

#### Hardening Avanzado

##### 1. Deshabilitar Algoritmos Débiles

```bash
sudo nano /etc/ssh/sshd_config
```

```
# Cifrados modernos (AES-GCM, ChaCha20)
Ciphers chacha20-poly1305@openssh.com,aes256-gcm@openssh.com,aes128-gcm@openssh.com,aes256-ctr,aes192-ctr,aes128-ctr

# MACs fuertes (SHA-256, SHA-512)
MACs hmac-sha2-512-etm@openssh.com,hmac-sha2-256-etm@openssh.com,hmac-sha2-512,hmac-sha2-256

# Key Exchange Algorithms (DH moderno, curvas elípticas)
KexAlgorithms curve25519-sha256,curve25519-sha256@libssh.org,diffie-hellman-group-exchange-sha256,diffie-hellman-group16-sha512,diffie-hellman-group18-sha512

# Host Key Algorithms (Ed25519, ECDSA, RSA-SHA2)
HostKeyAlgorithms ssh-ed25519,ecdsa-sha2-nistp521,ecdsa-sha2-nistp384,ecdsa-sha2-nistp256,rsa-sha2-512,rsa-sha2-256
```

##### 2. Cambiar Puerto SSH (Security by Obscurity)

```bash
# Editar sshd_config
Port 2222

# Actualizar firewall
sudo ufw allow 2222/tcp
sudo ufw delete allow 22/tcp

# Reiniciar SSH
sudo systemctl restart ssh

# Conectar en nuevo puerto
ssh -p 2222 usuario@servidor
```

##### 3. Autenticación Solo por Llaves (Deshabilitar Password)

```bash
# Después de configurar llaves públicas (ver sección siguiente)
sudo nano /etc/ssh/sshd_config

PasswordAuthentication no
ChallengeResponseAuthentication no
UsePAM yes  # Mantener para otras funcionalidades

sudo systemctl restart ssh
```

##### 4. Fail2Ban (Protección Contra Fuerza Bruta)

```bash
# Instalar Fail2Ban
sudo apt install fail2ban -y

# Configurar
sudo nano /etc/fail2ban/jail.local

[sshd]
enabled = true
port = ssh
filter = sshd
logpath = /var/log/auth.log
maxretry = 3
bantime = 3600  # 1 hora
findtime = 600  # Ventana de 10 minutos

# Iniciar
sudo systemctl enable --now fail2ban

# Ver IPs baneadas
sudo fail2ban-client status sshd
```

### Configuración de Llaves SSH (Autenticación Sin Password)

#### 1. Generar Par de Llaves (Cliente)

```bash
# Ed25519 (recomendado, más seguro y rápido)
```

### Port Forwarding (Tunneling)

#### Local Port Forwarding

**Caso de uso:** Acceder a base de datos remota (MySQL) que solo escucha en localhost del servidor.

```
ESCENARIO:
Servidor remoto (192.168.1.50):
  - MySQL escucha en 127.0.0.1:3306 (solo localhost)
  - SSH escucha en 0.0.0.0:22

Cliente local:
  - Quiere conectar a MySQL desde laptop
```

```bash
# Crear tunnel: puerto local 3307 → servidor:localhost:3306
ssh -L 3307:localhost:3306 usuario@192.168.1.50

# En otra terminal, conectar a MySQL local
mysql -h 127.0.0.1 -P 3307 -u dbuser -p
# Conecta realmente a 192.168.1.50:3306

# Mantener en background
ssh -fNL 3307:localhost:3306 usuario@192.168.1.50
# -f: background
# -N: no ejecutar comando remoto (solo tunnel)
```

**Sintaxis:**
```
ssh -L [local_addr:]local_port:remote_addr:remote_port servidor
```

#### Remote Port Forwarding

**Caso de uso:** Exponer servicio local (web dev server) a servidor remoto.

```
ESCENARIO:
Laptop local (detrás de NAT):
  - Web server en localhost:8080
  
Servidor público (203.0.113.50):
  - Quiere acceder al web server local
```

```bash
# Crear tunnel: servidor:8080 → local:localhost:8080
ssh -R 8080:localhost:8080 usuario@203.0.113.50

# Desde el servidor, acceder
curl http://localhost:8080
# Ve el web server del laptop local
```

**Sintaxis:**
```
ssh -R [remote_addr:]remote_port:local_addr:local_port servidor
```

#### Dynamic Port Forwarding (SOCKS Proxy)

**Caso de uso:** Usar servidor SSH como proxy SOCKS para navegar como si estuvieras en esa red.

```bash
# Crear SOCKS proxy en puerto local 1080
ssh -D 1080 usuario@servidor

# Configurar navegador para usar SOCKS proxy:
# Firefox → Settings → Network Settings → Manual proxy
# SOCKS Host: localhost
# Port: 1080
# SOCKS v5

# O con curl
curl --socks5 localhost:1080 http://internal-website.com
```

#### Script Python - Ejecución Remota (Paramiko)

```python
#!/usr/bin/env python3
# remote-exec.py - Ejecutar comandos en múltiples servidores

import paramiko

servers = [
    {'host': '192.168.1.50', 'user': 'admin', 'key': '/home/admin/.ssh/id_rsa'},
    {'host': '192.168.1.51', 'user': 'admin', 'key': '/home/admin/.ssh/id_rsa'},
    {'host': '192.168.1.52', 'user': 'admin', 'key': '/home/admin/.ssh/id_rsa'},
]

comando = 'df -h'

for server in servers:
    try:
        # Conectar
        ssh = paramiko.SSHClient()
        ssh.set_missing_host_key_policy(paramiko.AutoAddPolicy())
        ssh.connect(server['host'], username=server['user'], key_filename=server['key'])
        
        # Ejecutar comando
        stdin, stdout, stderr = ssh.exec_command(comando)
        
        # Output
        print(f"\n=== {server['host']} ===")
        print(stdout.read().decode())
        
        # Cerrar
        ssh.close()
        
    except Exception as e:
        print(f"Error en {server['host']}: {e}")
```

### Vulnerabilidades Comunes y Mitigaciones

#### 1. Weak Ciphers/MACs

**Problema:** Algoritmos criptográficos débiles (DES, RC4, MD5) permiten ataques.

**Mitigación:**

```bash
# Auditar configuración actual
ssh -Q cipher
ssh -Q mac
ssh -Q kex

# Deshabilitar débiles en sshd_config
Ciphers chacha20-poly1305@openssh.com,aes256-gcm@openssh.com,aes128-gcm@openssh.com
MACs hmac-sha2-512-etm@openssh.com,hmac-sha2-256-etm@openssh.com
KexAlgorithms curve25519-sha256,diffie-hellman-group-exchange-sha256
```

#### 2. Key Management

**Problema:** Llaves privadas sin passphrase, compartidas, o no rotadas.

**Mitigación:**

```
✓ SIEMPRE usar passphrase en llaves privadas
✓ Una llave por usuario/dispositivo (no compartir)
✓ Rotar llaves cada 6-12 meses
✓ Eliminar llaves de empleados que se van
✓ Usar ssh-agent para no escribir passphrase constantemente
✓ Backups cifrados de llaves privadas
```

#### 3. Exposed SSH Service

**Problema:** SSH expuesto a Internet es objetivo de bots de fuerza bruta.

**Mitigación:**

```
1. VPN: Acceso SSH solo vía VPN
2. Bastion Host: SSH solo desde jump server
3. Port Knocking: Puerto SSH cerrado hasta secuencia especial
4. Firewall: Whitelist de IPs permitidas
5. Fail2Ban: Ban automático después de intentos fallidos
6. Cambiar puerto: De 22 a otro (reduce bots básicos)
```

#### 4. Root Login

**Problema:** Login directo como root = escalación inmediata si se compromete.

**Mitigación:**

```bash
# sshd_config
PermitRootLogin no

# Usar sudo en su lugar
ssh usuario@servidor
sudo su -
```

#### 5. Outdated OpenSSH

**Problema:** Vulnerabilidades conocidas en versiones antiguas.

**Mitigación:**

```bash
# Verificar versión
ssh -V

# Actualizar regularmente
sudo apt update && sudo apt upgrade openssh-server -y

# Suscribirse a avisos de seguridad
# https://www.openssh.com/security.html
```

```
✓ Deshabilitar root login (PermitRootLogin no)
✓ Autenticación por llaves (deshabilitar passwords)
✓ Usar passphrases fuertes en llaves privadas
✓ Fail2Ban o rate limiting activo
✓ Cambiar puerto SSH (security by obscurity)
```

```yaml
        - { regexp: '^PermitRootLogin', line: 'PermitRootLogin no' }
        - { regexp: '^PasswordAuthentication', line: 'PasswordAuthentication no' }
        - { regexp: '^PubkeyAuthentication', line: 'PubkeyAuthentication yes' }
        - { regexp: '^Port', line: 'Port 22' }
      notify: Restart SSH

    - name: Instalar Fail2Ban
      apt:
        name: fail2ban
        state: present
        update_cache: yes

    - name: Configurar Fail2Ban
      copy:
        src: files/jail.local
        dest: /etc/fail2ban/jail.local
      notify: Restart Fail2Ban

  handlers:
    - name: Restart SSH
      systemd:
        name: ssh
        state: restarted

    - name: Restart Fail2Ban
      systemd:
        name: fail2ban
        state: restarted
```

---

## Conclusión

SSH es el protocolo estándar para acceso remoto seguro, reemplazando completamente a Telnet y otros protocolos inseguros de texto plano. Su correcta implementación, con autenticación por llaves públicas, hardening adecuado y monitoreo constante, es fundamental para la seguridad de cualquier infraestructura moderna.

**Puntos Clave:**
- **Telnet transmite todo en texto plano** (credenciales, comandos, datos) - **NUNCA USAR**
- SSH cifra toda la comunicación extremo a extremo
- Autenticación por llaves públicas > passwords
- SIEMPRE deshabilitar root login directo
- Fail2Ban protege contra fuerza bruta
- Bastion hosts para acceso a redes internas
- Port forwarding permite tunneling seguro
- Auditoría y logging detallado esencial
- Hardening: deshabilitar algoritmos débiles, cambiar puerto, limitar usuarios
