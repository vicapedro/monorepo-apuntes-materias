# 1.2 Gestión de Configuración (Configuration Management)

## 📋 Introducción

La **Gestión de Configuración** es el proceso sistemático de identificar, controlar, rastrear y auditar los elementos de configuración (CIs - Configuration Items) de una infraestructura de red a lo largo de todo su ciclo de vida. Esta área funcional de FCAPS es fundamental para mantener la **consistencia, estabilidad y trazabilidad** de los cambios en el entorno de red.

### **¿Por qué es crítica la Gestión de Configuración?**

En entornos de red modernos, con cientos o miles de dispositivos (routers, switches, firewalls, balanceadores, servidores), la gestión manual de configuraciones se convierte rápidamente en un problema de escala que genera:

```
❌ Sin Gestión de Configuración:
  • Configuraciones inconsistentes entre dispositivos similares
  • Cambios no documentados ("configuración tribal")
  • Imposibilidad de rollback ante fallas
  • Pérdida de configuraciones críticas
  • Auditorías imposibles de realizar
  • Tiempo de recuperación ante desastres prolongado
  • Incumplimiento de normativas (ISO, SOX, PCI-DSS)

✅ Con Gestión de Configuración:
  • Configuraciones estandarizadas y versionadas
  • Cambios rastreables con aprobación formal
  • Rollback inmediato (segundos vs horas)
  • Backups automatizados diarios/por evento
  • Auditoría completa de quién-qué-cuándo
  • Recuperación ante desastres en minutos
  • Compliance demostrable con evidencia
```

---

## 🎯 Objetivos de la Gestión de Configuración

### **1. Control de Cambios (Change Management)**

**Objetivo:** Garantizar que todos los cambios en la red se implementen de manera **controlada, documentada y reversible**.

**Beneficio:** Reducción de incidentes causados por cambios (70% de fallas son por cambios no controlados según ITIL).

**Ejemplo práctico:**
```
Sin control:
  Técnico modifica ACL en firewall directamente → 
  Bloquea tráfico legítimo → 
  Falla no documentada → 
  Sin forma de revertir rápidamente

Con control:
  Técnico solicita cambio vía RFC (Request for Change) → 
  CAB (Change Advisory Board) evalúa impacto → 
  Se aprueba con plan de rollback → 
  Backup pre-cambio automático → 
  Cambio implementado y documentado → 
  Si falla: rollback en 30 segundos
```

---

### **2. Inventario de Activos (Asset Inventory)**

**Objetivo:** Mantener un registro **preciso y actualizado** de todos los elementos de configuración en la infraestructura.

**Componentes del inventario:**
- **Hardware:** Modelos, números de serie, ubicación física, garantías
- **Software:** Versiones de firmware/OS, licencias, fechas de EOL
- **Conexiones:** Topología física y lógica, puertos utilizados
- **Responsabilidades:** Propietario, equipo de soporte, criticidad

**Beneficio:** Conocimiento completo del entorno para tomar decisiones informadas.

**Ejemplo práctico:**
```
Pregunta: "¿Cuántos switches tenemos afectados por CVE-2025-XXXXX?"

Con inventario actualizado:
  → Query en CMDB: "IOS version = 15.2(4)E1"
  → Resultado: 23 switches identificados en 2 minutos
  → Acción: Plan de parcheo priorizado por criticidad

Sin inventario:
  → Buscar manualmente en documentación desactualizada
  → Conectarse switch por switch (horas de trabajo)
  → Riesgo de omitir dispositivos vulnerables
```

---

### **3. Versionamiento y Auditoría (Version Control & Audit)**

**Objetivo:** Rastrear **quién hizo qué cambio, cuándo y por qué**, con capacidad de restaurar versiones anteriores.

**Beneficio:** Trazabilidad completa para troubleshooting, compliance y mejora continua.

**Flujo de versionamiento:**
```
Configuración actual (v1.0) → 
Cambio aprobado → 
Nueva versión (v1.1) con metadata:
  ├─ Timestamp: 2026-03-25 14:30:00
  ├─ Usuario: jperez
  ├─ Ticket: CHG-2026-0234
  ├─ Descripción: "Agregar VLAN 50 para IoT"
  ├─ Diff: +3 líneas, -0 líneas
  └─ Validación: Config tested OK
```

**Ejemplo de auditoría:**
```
Auditor: "¿Quién modificó la política de firewall el 15 de marzo?"

Con versionamiento:
  Git log:
    commit a3f2b1c
    Author: mgarcia <mgarcia@empresa.com>
    Date: 2026-03-15 09:45:22
    Ticket: CHG-2026-0198
    
    Permitir tráfico HTTPS desde VLAN 10 a servidor DMZ
    
    - ACL 100: permit tcp 192.168.10.0/24 host 10.20.1.50 eq 443
    
  ✅ Respuesta inmediata con evidencia completa

Sin versionamiento:
  ❌ "No lo sé, buscaré en correos y tickets manualmente"
```

---

### **4. Estandarización y Cumplimiento (Standardization & Compliance)**

**Objetivo:** Asegurar que las configuraciones cumplan con **estándares corporativos, mejores prácticas y requisitos regulatorios**.

**Elementos a estandarizar:**
- **Naming conventions:** Hostnames, interfaces, VLANs, ACLs
- **Security baselines:** Passwords, SSH, SNMP, logging
- **Configuraciones base:** Templates por tipo de dispositivo
- **Documentación:** Formato, detalle, actualización

**Beneficio:** Reducción de errores, facilita troubleshooting, cumple normativas.

**Ejemplo de estándar de hostname:**
```
Convención corporativa:
  [SITIO]-[TIPO]-[FUNCIÓN]-[NÚMERO]
  
Ejemplos válidos:
  ✅ MTY-SW-ACCESS-01    (Monterrey, Switch, Acceso, #1)
  ✅ GDL-RTR-CORE-02     (Guadalajara, Router, Core, #2)
  ✅ CDMX-FW-BORDER-01   (Ciudad de México, Firewall, Borde, #1)

Ejemplos NO conformes:
  ❌ Switch1              (No indica ubicación ni función)
  ❌ Router_Nuevo         (Naming no estándar)
  ❌ FIREWALL             (Sin identificación única)

Validación automatizada:
  Script audita compliance → Reporta desviaciones → 
  Genera alerta para corrección
```

**Compliance regulatorio:**
```
ISO 27001 requiere:
  ✅ Control de cambios documentado
  ✅ Backups periódicos
  ✅ Segregación de funciones (quien aprueba ≠ quien ejecuta)
  ✅ Auditoría de accesos

PCI-DSS requiere:
  ✅ Configuraciones de seguridad baseline
  ✅ Revisión trimestral de reglas de firewall
  ✅ Logs de cambios por 1 año mínimo
  ✅ Validación de configuraciones

Gestión de Configuración proporciona evidencia de cumplimiento
```

---

### **5. Recuperación ante Desastres (Disaster Recovery)**

**Objetivo:** Permitir la **restauración rápida** de servicios de red ante fallas catastróficas.

**Beneficio:** Reducción de RTO (Recovery Time Objective) de horas/días a minutos.

**Escenario sin gestión:**
```
Falla catastrófica:
  Core switch sufre falla de hardware irreparable
  
Proceso de recuperación:
  1. Conseguir switch de reemplazo (horas/días)
  2. Buscar última configuración conocida (¿dónde está?)
  3. Reconstruir configuración de memoria (error-prone)
  4. Probar y ajustar (múltiples iteraciones)
  5. Poner en producción (validación extensa)
  
  RTO estimado: 8-48 horas ❌
  Pérdida de negocio: Significativa
```

**Escenario con gestión:**
```
Falla catastrófica:
  Core switch sufre falla de hardware irreparable
  
Proceso de recuperación:
  1. Conseguir switch de reemplazo (horas/días) ← mismo
  2. Cargar configuración desde repositorio Git/RANCID ← 2 minutos
  3. Validar que versión es la actual ← automático
  4. Aplicar configuración al nuevo switch ← 5 minutos
  5. Verificación funcional ← 10 minutos
  
  RTO estimado: 30 minutos (después de tener hardware) ✅
  Pérdida de negocio: Mínima
```

## 🔑 Conceptos Fundamentales

### **Configuration Item (CI) - Elemento de Configuración**

**Definición:** Cualquier componente de la infraestructura que debe ser gestionado para entregar un servicio de TI.

**Tipos de CIs en redes:**

| **Categoría** | **Ejemplos** | **Atributos Clave** |
|---------------|--------------|---------------------|
| **Hardware** | Routers, switches, firewalls, APs | Modelo, S/N, ubicación, garantía |
| **Software** | IOS, firmware, aplicaciones | Versión, licencia, fecha EOL |
| **Configuraciones** | Running-config, startup-config | Versión, hash MD5, fecha |
| **Conexiones** | Cables, enlaces WAN, fibra | Origen, destino, capacidad, estado |
| **Documentación** | Diagramas, runbooks, políticas | Versión, aprobador, vigencia |
| **Servicios** | DHCP, DNS, VPN | SLA, dependencias, responsable |

**Relaciones entre CIs:**
```
Servicio: "Internet Corporativo"
  ├─ Depende de → Router WAN (RTR-WAN-01)
  │   ├─ Configuración → running-config v2.3
  │   ├─ Hardware → Cisco ISR 4331 (S/N: FDO12345678)
  │   └─ Enlace → Fibra Telmex 1Gbps (ID: WAN-001)
  ├─ Depende de → Firewall (FW-BORDER-01)
  │   ├─ Configuración → policy.conf v1.8
  │   └─ Software → FortiOS 7.0.5
  └─ Monitoreado por → Zabbix Server (MON-SRV-01)
```

---

**Definición:** Base de datos centralizada que almacena información sobre todos los CIs y sus relaciones.

**Función principal:** Fuente única de verdad (Single Source of Truth - SSOT) para el inventario de TI.

**Información almacenada:**

```

│ ├─ Serial Number: FOC2345A1BC                          │
│ ├─ Ubicación: Datacenter - Rack A05 - RU 20-22        │
│ ├─ IP Management: 192.168.1.10                         │
│ ├─ Firmware: IOS-XE 17.3.4                             │
│ ├─ Config Version: v3.2 (2026-03-20)                   │
│ ├─ Última modificación: 2026-03-20 14:30 (mgarcia)    │
│ ├─ Propietario: Depto. de Redes                        │
│ ├─ Criticidad: ALTA                                    │
│ ├─ Estado: En Producción                               │
│ ├─ Fecha de compra: 2023-05-15                         │
│ ├─ Garantía: 2028-05-14 (SmartNet)                    │
│ ├─ Costo: $8,500 USD                                   │
│ └─ Relaciones:                                          │
│     ├─ Conectado a: SW-CORE-02 (trunk)                 │
```

**Beneficios de CMDB:**
- ✅ **Impact Analysis:** "Si SW-CORE-01 falla, ¿qué servicios se afectan?"
- ✅ **Change Planning:** "¿Qué cambios requieren ventana de mantenimiento?"
- ✅ **Capacity Planning:** "¿Cuántos puertos disponibles tenemos?"
- ✅ **Compliance:** "¿Todos los switches tienen firmware actualizado?"
- ✅ **Asset Management:** "¿Qué equipos tienen garantía vencida?"

### **Baseline Configuration (Configuración Base)**

**Definición:** Configuración estándar aprobada que sirve como punto de referencia para dispositivos del mismo tipo.

**Propósito:**
- Garantizar consistencia entre dispositivos similares
- Facilitar despliegues rápidos (ZTP - Zero Touch Provisioning)
- Reducir errores de configuración manual
- Simplificar auditorías de compliance

**Ejemplo de baseline para switches de acceso:**

```cisco
! ============================================
! BASELINE: Switch de Acceso - Versión 2.1
! Última actualización: 2026-03-01
! Aprobado por: CAB-2026-001
! Aplicable a: Catalyst 2960-X, 3650, 9200
! ============================================

! --- CONFIGURACIÓN BASE ---
hostname ${HOSTNAME}  ! Formato: [SITIO]-SW-ACCESS-[NN]
!
service timestamps debug datetime msec localtime show-timezone
service timestamps log datetime msec localtime show-timezone
service password-encryption
!
no ip domain-lookup
ip domain-name empresa.local
!
! --- USUARIOS Y AUTENTICACIÓN ---
username admin privilege 15 secret ${ADMIN_PASSWORD}
!
aaa new-model
aaa authentication login default group tacacs+ local
aaa authorization exec default group tacacs+ local
!
tacacs-server host 192.168.1.5 key ${TACACS_KEY}
!
! --- ACCESO REMOTO ---
ip ssh version 2
ip ssh time-out 60
ip ssh authentication-retries 2
!
line vty 0 15
 transport input ssh
 exec-timeout 15 0
 logging synchronous
!
! --- SNMP ---
snmp-server community ${SNMP_RO_COMMUNITY} RO
snmp-server community ${SNMP_RW_COMMUNITY} RW
snmp-server location ${LOCATION}
snmp-server contact helpdesk@empresa.com
snmp-server host 192.168.1.20 version 2c ${SNMP_COMMUNITY}
!
! --- LOGGING ---
logging buffered 16384
logging host 192.168.1.30
logging trap informational
!
! --- NTP ---
ntp server 192.168.1.2
clock timezone CST -6
!
! --- SEGURIDAD BÁSICA ---
no ip http server
no ip http secure-server
!
! --- VLANs ESTÁNDAR ---
vlan 10
 name USUARIOS
vlan 20
 name SERVIDORES
vlan 30
 name INVITADOS
vlan 99
 name MANAGEMENT
!
! --- INTERFACES DE ACCESO (TEMPLATE) ---
interface range GigabitEthernet1/0/1-48
 switchport mode access
 switchport access vlan 10
 spanning-tree portfast
 spanning-tree bpduguard enable
!
! --- INTERFACE DE MANAGEMENT ---
interface Vlan99
 ip address ${MGMT_IP} 255.255.255.0
 no shutdown
!
ip default-gateway ${DEFAULT_GW}
!
! --- BANNER ---
banner motd ^
=========================================
   ACCESO AUTORIZADO ÚNICAMENTE
   Propiedad de: Empresa S.A. de C.V.
   Todos los accesos son monitoreados
=========================================
^
!
end
```

**Variables a reemplazar en despliegue:**
- `${HOSTNAME}`: Nombre único del switch
- `${ADMIN_PASSWORD}`: Password hasheado
- `${TACACS_KEY}`: Llave compartida TACACS+
- `${SNMP_RO_COMMUNITY}`: Community read-only
- `${SNMP_RW_COMMUNITY}`: Community read-write
- `${LOCATION}`: Ubicación física
- `${MGMT_IP}`: IP de gestión
- `${DEFAULT_GW}`: Gateway de gestión

### **Change Management Process (Proceso de Gestión de Cambios)**

**Definición:** Proceso formal para controlar el ciclo de vida de todos los cambios en la infraestructura.

**Objetivos:**
- Minimizar riesgo de interrupciones por cambios
- Garantizar que cambios sean necesarios y beneficiosos
- Documentar cambios para auditoría y troubleshooting
- Permitir rollback rápido en caso de problemas

**Tipos de cambios:**

| **Tipo** | **Descripción** | **Aprobación** | **Ventana** | **Ejemplo** |
|----------|----------------|----------------|-------------|-------------|
| **Estándar** | Cambios pre-aprobados, bajo riesgo, repetitivos | Pre-autorizado (CAB) | Flexible | Agregar usuario a VLAN, crear backup manual |
| **Normal** | Cambios que requieren evaluación y aprobación | CAB | Planificada | Actualizar firmware, modificar ACL importante |
| **Emergencia** | Cambios urgentes para resolver incidente crítico | Gerente TI | Inmediata | Bloquear tráfico de ataque, failover manual |

**Flujo del proceso:**

```
┌────────────────────────────────────────────────────────┐
│ 1. SOLICITUD (Request for Change - RFC)               │
│    Usuario/Técnico identifica necesidad de cambio     │
│    Crea ticket con: Qué, Por qué, Cuándo, Impacto     │
└──────────────────┬─────────────────────────────────────┘
                   │
                   ▼
┌────────────────────────────────────────────────────────┐
│ 2. EVALUACIÓN (Assessment)                            │
│    ├─ Análisis de impacto (¿qué se afecta?)          │
│    ├─ Análisis de riesgo (¿qué puede salir mal?)     │
│    ├─ Revisión de recursos (¿quién, cuándo?)         │
│    └─ Plan de rollback (¿cómo revertir?)             │
└──────────────────┬─────────────────────────────────────┘
                   │
                   ▼
┌────────────────────────────────────────────────────────┐
│ 3. APROBACIÓN (Approval)                              │
│    CAB (Change Advisory Board) evalúa:                │
│    ├─ ¿Cambio justificado?                           │
│    ├─ ¿Riesgos aceptables?                           │
│    ├─ ¿Recursos disponibles?                         │
│    └─ Decisión: Aprobar / Rechazar / Diferir         │
└──────────────────┬─────────────────────────────────────┘
                   │
                   ▼
┌────────────────────────────────────────────────────────┐
│ 4. PLANIFICACIÓN (Planning)                           │
│    ├─ Asignar responsables                            │
│    ├─ Definir ventana de mantenimiento                │
│    ├─ Preparar configuraciones/scripts                │
│    ├─ Notificar a stakeholders                        │
│    └─ Validar plan de rollback                        │
└──────────────────┬─────────────────────────────────────┘
                   │
                   ▼
┌────────────────────────────────────────────────────────┐
│ 5. IMPLEMENTACIÓN (Implementation)                    │
│    ├─ Backup pre-cambio (CRÍTICO)                    │
│    ├─ Ejecutar cambio según plan                      │
│    ├─ Documentar acciones realizadas                  │
│    └─ Validar funcionamiento (testing)                │
└──────────────────┬─────────────────────────────────────┘
                   │
                   ▼
┌────────────────────────────────────────────────────────┐
│ 6. VALIDACIÓN POST-CAMBIO (Post-Implementation Review)│
│    ├─ ¿Cambio exitoso? ✅ → Cerrar ticket            │
│    ├─ ¿Problemas? ❌ → Ejecutar rollback              │
│    ├─ Actualizar CMDB con nueva configuración         │
│    └─ Generar reporte de cambio                       │
└────────────────────────────────────────────────────────┘
```

## 🌟 Importancia Estratégica

### **Impacto en Disponibilidad**

```
Estudio de caso real:
  Empresa sin gestión de configuración:
    - Cambios mensuales: 150
    - Incidentes causados por cambios: 45 (30%)
    - Tiempo promedio de rollback: 4 horas
    - Downtime mensual por cambios: 180 horas
    
  Misma empresa después de implementar gestión:
    - Cambios mensuales: 150 (mismos)
    - Incidentes causados por cambios: 8 (5%)  ← Reducción 83%
    - Tiempo promedio de rollback: 15 minutos  ← Reducción 93%
    - Downtime mensual por cambios: 2 horas    ← Reducción 98%
    
  ROI: Inversión en herramientas amortizada en 3 meses
```

### **Cumplimiento Regulatorio**

**Normativas que requieren gestión de configuración:**

- **ISO 27001 (Seguridad de la Información):**
  - Control A.12.1.2: Gestión de cambios
  - Control A.12.3.1: Respaldo de información
  
- **PCI-DSS (Payment Card Industry):**
  - Requisito 2.4: Mantener inventario de componentes
  - Requisito 6.4: Seguir procesos de control de cambios
  - Requisito 10.5.5: Proteger logs de alteración (configs = logs)

- **SOX (Sarbanes-Oxley):**
  - Sección 404: Control de TI sobre reportes financieros
  - Requiere segregación de funciones (quien hace ≠ quien aprueba)

- **HIPAA (Health Insurance Portability):**
  - Mantener inventario de sistemas con información de salud
  - Documentar cambios en controles de seguridad

**Evidencia que proporciona gestión de configuración:**
- ✅ Logs completos de cambios (audit trail)
- ✅ Aprobaciones formales registradas
- ✅ Segregación de funciones (requester ≠ approver ≠ implementer)
- ✅ Versionamiento de configuraciones críticas
- ✅ Backups regulares y verificados

## 🔄 Relación con Otras Áreas de FCAPS

La Gestión de Configuración no opera en aislamiento; se integra estrechamente con las demás áreas funcionales:

### **Configuración ↔ Fallas (Fault Management)**

```
Fallas detecta:
  "Switch SW-ACCESS-15 tiene 50% packet loss"

Configuración proporciona:
  ├─ Última configuración conocida buena (baseline)
  ├─ Cambios recientes en el switch (últimos 7 días)
  ├─ Relación de dependencias (qué servicios afecta)
  └─ Plan de rollback si cambio reciente es la causa

Resultado: Troubleshooting 70% más rápido
```

### **Configuración ↔ Contabilidad (Accounting)**

```
Contabilidad necesita:
  "Costo total de propiedad (TCO) de infraestructura de red"

Configuración proporciona:
  ├─ Inventario completo (CMDB)
  ├─ Costos de adquisición por dispositivo
  ├─ Fechas de garantía (costos de soporte)
  ├─ Licencias de software activas
  └─ Proyección de renovaciones (EOL/EOS)

Resultado: Budget planning preciso
```

### **Configuración ↔ Desempeño (Performance)**

```
Desempeño detecta:
  "Latencia en VLAN 20 aumentó 200% en última semana"

Configuración proporciona:
  ├─ ¿Hubo cambios en routing/switching? (Git log)
  ├─ ¿Se agregó nueva VLAN? (CMDB diff)
  ├─ ¿Cambió QoS policy? (Config diff)
  └─ Posibilidad de revertir a configuración anterior

Resultado: Correlación cambio → degradación de desempeño
```

### **Configuración ↔ Seguridad (Security)**

```
Seguridad requiere:
  "Auditoría de compliance con baseline de seguridad"

Configuración proporciona:
  ├─ Baseline de seguridad definido
  ├─ Scripts de validación automática
  ├─ Reporte de desviaciones por dispositivo
  ├─ Plan de remediación (aplicar baseline)
  └─ Evidencia de cumplimiento para auditoría

Resultado: Postura de seguridad consistente y auditable
```

### **Configuración ↔ SLA (Niveles de Servicio)**

```
SLA define:
  "Cambios estándar: implementar en <30 minutos"
  "Cambios normales: ventana máxima 2 horas"
  "Rollback: completar en <15 minutos"

Configuración garantiza cumplimiento:
  ├─ Templates pre-configurados (cambios rápidos)
  ├─ Automatización vía Ansible/scripts
  ├─ Backups automáticos pre-cambio
  ├─ Procedimientos de rollback documentados
  └─ Métricas de tiempo de implementación

Resultado: SLOs de cambios cumplidos consistentemente
```

## 📊 Métricas Clave de Gestión de Configuración

Para evaluar la efectividad de la gestión de configuración, se monitorean las siguientes métricas:

| **Métrica** | **Objetivo Típico** | **Fórmula / Medición** | **Impacto en Negocio** |
|-------------|---------------------|------------------------|------------------------|
| **Tasa de éxito de cambios** | ≥ 95% | (Cambios exitosos / Total cambios) × 100 | Alta tasa = Menos incidentes |
| **Tiempo de implementación** | < 30 min (estándar) | Timestamp fin - Timestamp inicio | Menor ventana de cambio |
| **Tiempo de rollback** | < 15 minutos | Detección problema → Config restaurada | Menor downtime |
| **Cobertura de backup** | 100% dispositivos críticos | (Devices con backup / Total devices) × 100 | Capacidad de recuperación |
| **Frecuencia de backup** | Diario + por cambio | Última fecha de backup por device | Pérdida de datos mínima |
| **Desviación de baseline** | < 5% de devices | Devices no conformes / Total devices | Consistencia de seguridad |
| **Precisión de CMDB** | ≥ 98% | Auditoría física vs CMDB | Confianza en decisiones |
| **Cambios de emergencia** | < 10% del total | (Cambios emergencia / Total cambios) × 100 | Indicador de planificación |

**Dashboard de métricas (ejemplo):**

```
┌─────────────────────────────────────────────────────────┐
│ GESTIÓN DE CONFIGURACIÓN - Dashboard Mensual           │
│ Periodo: Marzo 2026                                    │
├─────────────────────────────────────────────────────────┤
│                                                         │
│ 📊 CAMBIOS                                             │
```
