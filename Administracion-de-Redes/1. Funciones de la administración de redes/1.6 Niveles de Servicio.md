# 1.6 Niveles de Servicio (SLA/SLO/SLI)

## 📋 Introducción

Los **Niveles de Servicio** son el puente fundamental entre la **gestión técnica de redes** y las **necesidades del negocio**. Definen **qué se espera** del servicio de red, mientras que FCAPS define **cómo se logra**.

### **¿Por qué son importantes?**

```
Sin SLA definido:                  Con SLA definido:
❌ Expectativas ambiguas          ✅ Compromisos claros y medibles
❌ Conflictos técnico-negocio     ✅ Alineación de objetivos
❌ Inversión sin justificación    ✅ Decisiones basadas en impacto
❌ Gestión reactiva               ✅ Gestión proactiva con métricas
```

**Ejemplo del impacto:**
```
Empresa sin SLA:
  Usuario: "La red está lenta"
  TI: "Funciona normal, es tu percepción"
  ➜ Conflicto sin resolución

Empresa con SLA:
  SLA: Latencia < 50ms, Disponibilidad 99.9%
  Medición: Latencia actual 120ms ⚠️
  TI: "Incumplimiento detectado, iniciando troubleshooting"
  ➜ Acción correctiva inmediata
```

## 🎯 Conceptos Fundamentales: SLA vs SLO vs SLI

### **Definiciones**

Estos tres conceptos frecuentemente se confunden, pero tienen roles distintos:

| **Concepto** | **Definición** | **Responsable** | **Ejemplo** |
|--------------|----------------|-----------------|-------------|
| **SLA** (Service Level Agreement) | **Acuerdo formal** entre proveedor y cliente sobre el nivel de servicio esperado. Incluye métricas, responsabilidades y consecuencias. | Legal/Comercial + TI | "Garantizamos 99.9% de disponibilidad en internet corporativo. Penalización: 5% del costo mensual por cada 0.1% de incumplimiento" |
| **SLO** (Service Level Objective) | **Objetivo específico** dentro de un SLA. Meta técnica cuantificable que se debe cumplir. | Operaciones TI | "Objetivo: Disponibilidad ≥ 99.9%" |
| **SLI** (Service Level Indicator) | **Métrica real** que se mide para verificar cumplimiento del SLO. Es el dato observable. | Sistemas de monitoreo | "Medición: Uptime = 99.85% en marzo" |

### **Relación jerárquica**

```
┌────────────────────────────────────────────────────────────┐
│ SLA (Acuerdo de Nivel de Servicio)                        │
│ "Contrato entre TI y Negocio"                             │
│                                                            │
│  ┌──────────────────────────────────────────────────────┐ │
│  │ SLO 1: Disponibilidad ≥ 99.9%                        │ │
│  │  └─ SLI: Uptime medido = 99.92% ✅                   │ │
│  └──────────────────────────────────────────────────────┘ │
│                                                            │
│  ┌──────────────────────────────────────────────────────┐ │
│  │ SLO 2: Latencia promedio < 50ms                      │ │
│  │  └─ SLI: Latencia medida = 42ms ✅                   │ │
│  └──────────────────────────────────────────────────────┘ │
│                                                            │
│  ┌──────────────────────────────────────────────────────┐ │
│  │ SLO 3: MTTR < 2 horas para incidentes P1             │ │
│  │  └─ SLI: MTTR promedio = 1.8h ✅                     │ │
│  └──────────────────────────────────────────────────────┘ │
│                                                            │
│ Penalización si SLO no se cumple: Crédito del 5%         │
└────────────────────────────────────────────────────────────┘
```

**Contexto:** Servicio de internet corporativo

## 📐 Componentes de un SLA

Un SLA completo debe contener los siguientes elementos:

### **1. Identificación del Servicio**

```markdown
### SLA-2026-001: Servicio de Internet Corporativo

**Descripción:** Acceso a internet para usuarios corporativos en 
sede principal y 5 sucursales.

**Alcance:**
  ✅ Incluye: Conectividad WAN, gateway, DNS, firewall
  ❌ Excluye: WiFi interno, dispositivos de usuario, aplicaciones cloud

**Horas de cobertura:**
  - Lunes a Viernes: 07:00 - 22:00 (15 horas)
  - Sábados: 08:00 - 14:00 (6 horas)
  - Domingos: NO cubierto
  - Total: 96 horas/semana
```

### **2. Partes Involucradas**

```markdown
**Proveedor del Servicio:**
  - Departamento: TI - Infraestructura de Redes
  - Responsable: Ing. Carlos Méndez
  - Contacto: cmendez@empresa.com | Ext. 1234

**Cliente del Servicio:**
  - Departamento: Ventas
  - Responsable: Lic. Ana Rodríguez
  - Contacto: arodriguez@empresa.com | Ext. 5678

**Escalamiento:**
  - L1: Mesa de ayuda (ext. 9999)
  - L2: Técnico de redes (ext. 1234)
  - L3: Gerente de TI (ext. 1100)
```

### **3. Objetivos de Nivel de Servicio (SLOs)**

Los SLOs deben ser **SMART** (Specific, Measurable, Achievable, Relevant, Time-bound):

| **SLO** | **Métrica** | **Objetivo** | **Método de medición** | **Frecuencia** |
|---------|-------------|--------------|------------------------|----------------|
| Disponibilidad | Uptime | ≥ 99.9% | Monitoreo ICMP + puerto 443 | Continuo (5 min) |
| Latencia | RTT promedio | < 50 ms | Ping a 8.8.8.8 | Cada 5 minutos |
| Throughput | Velocidad descarga | ≥ 950 Mbps | Speedtest automatizado | Cada hora |
| Packet Loss | % paquetes perdidos | < 0.1% | SNMP en router WAN | Cada 5 minutos |
| MTTR | Tiempo resolución | < 2 horas | Sistema de tickets | Por incidente |
| Jitter | Variación latencia | < 10 ms | Monitoreo VoIP (SIP) | Continuo |

**Cálculo de Disponibilidad:**
```
Disponibilidad (%) = (Tiempo total - Tiempo caído) / Tiempo total × 100

99.9% anual = 8.76 horas de downtime permitido/año
99.9% mensual = 43.2 minutos de downtime permitido/mes
```

### **4. Responsabilidades**

```markdown
**Responsabilidades del Proveedor (TI):**
  ✅ Monitorear proactivamente 24/7
  ✅ Responder incidentes en < 15 minutos
  ✅ Mantener configuraciones respaldadas
  ✅ Generar reporte mensual de cumplimiento
  ✅ Notificar mantenimientos con 48h de anticipación

**Responsabilidades del Cliente (Ventas):**
  ✅ Reportar incidentes via sistema de tickets
  ✅ Proporcionar acceso para troubleshooting
  ✅ No modificar equipos de red sin autorización
  ✅ Validar ventanas de mantenimiento propuestas

**Exclusiones (No responsabilidad de TI):**
  ❌ Problemas en dispositivos del usuario (PCs, laptops)
  ❌ Fallas en servicios cloud (Office 365, Salesforce)
  ❌ Problemas en WiFi local (administrado por Ventas)
  ❌ Ancho de banda insuficiente por uso no autorizado
```

### **5. Penalizaciones y Créditos**

```markdown
**Esquema de Penalizaciones:**

| Disponibilidad Mensual | Crédito Aplicable | Ejemplo (costo $10,000) |
|------------------------|-------------------|-------------------------|
| ≥ 99.9% | 0% | $0 |
| 99.0% - 99.89% | 5% | $500 de descuento |
| 98.0% - 98.99% | 10% | $1,000 de descuento |
| 95.0% - 97.99% | 25% | $2,500 de descuento |
| < 95.0% | 50% | $5,000 de descuento |

**Cálculo de crédito:**
  Crédito ($) = Costo mensual del servicio × % penalización

**Exclusiones de penalización:**
  ⚠️ NO aplica penalización en caso de:
    - Mantenimiento planificado (notificado 48h antes)
    - Fallas del proveedor de internet (ISP) fuera de control de TI
    - Desastres naturales (terremotos, inundaciones)
    - Ataques DDoS dirigidos a la empresa
    - Cambios solicitados por el cliente con menos de 24h
```

**Ejemplo de cálculo real:**
```
Mes: Abril 2026
Costo del servicio: $10,000
Total minutos: 43,200 (30 días × 24h × 60min)

Incidentes:
  1. [02-Abr] Falla en router principal: 120 minutos
  2. [15-Abr] Actualización de firewall (planificada): 30 minutos
  3. [22-Abr] Corte de ISP (Telmex): 45 minutos

Tiempo caído contable:
  - 120 min (router) ✅ CUENTA
  - 30 min (mantenimiento) ❌ NO CUENTA (planificado)
  - 45 min (ISP) ❌ NO CUENTA (fuera de control)
  
Disponibilidad:
  (43,200 - 120) / 43,200 × 100 = 99.72%

Resultado:
  99.72% cae en rango 99.0% - 99.89% → Penalización 5%
  Crédito = $10,000 × 5% = $500
  
Factura final: $10,000 - $500 = $9,500
```

### **6. Procedimientos de Reporte**

```markdown
**Reportes Automáticos:**
  📧 Alerta inmediata por incumplimiento de SLO (email + SMS)
  📊 Dashboard en tiempo real (Grafana): https://monitoring.empresa.com
  📈 Reporte semanal automatizado (lunes 08:00 AM)

**Reporte Mensual Formal:**
  📅 Entrega: Primer día hábil del mes siguiente
  📄 Formato: PDF + datos crudos (CSV)
  📊 Contenido:
    - Resumen ejecutivo (cumplimiento general)
    - Métricas detalladas por SLO
    - Gráficas de tendencias
    - Incidentes relevantes (P1, P2)
    - Acciones correctivas implementadas
    - Plan de mejora para próximo mes
```

### **7. Proceso de Revisión y Ajuste**

```markdown
**Revisión Trimestral:**
  📅 Agenda: Última semana de cada trimestre
  👥 Asistentes: Responsables de TI y Ventas
  📋 Temas:
    - Análisis de tendencias (¿SLOs realistas?)
    - Cambios en necesidades del negocio
    - Propuestas de ajuste a métricas
    - Inversiones necesarias para mejorar

**Proceso de cambio al SLA:**
  1. Propuesta formal por escrito
  2. Análisis de impacto técnico/financiero
  3. Negociación de nuevos objetivos
  4. Aprobación por ambas partes
  5. Actualización del documento SLA
  6. Implementación con 30 días de notice
```

## 📊 Métricas Comunes por Área FCAPS

Los SLOs deben alinearse con las 5 áreas funcionales de FCAPS:

### **F - Fallas (Fault Management)**

| **Métrica SLO** | **Objetivo Típico** | **SLI (Cómo se mide)** | **Herramienta** |
|-----------------|---------------------|------------------------|-----------------|
| **Disponibilidad** | 99.9% - 99.99% | `(Total time - Downtime) / Total time × 100` | Zabbix, Nagios |
| **MTBF** (Mean Time Between Failures) | > 720 horas (30 días) | Tiempo promedio entre incidentes | Sistema de tickets |
| **MTTR** (Mean Time To Repair) | < 2 horas | Tiempo promedio de resolución | Sistema de tickets |
| **Tasa de Incidentes** | < 5 incidentes/mes | Cantidad de incidentes P1+P2 | Dashboard ITSM |

**Ejemplo de medición de Disponibilidad:**
```bash
# Script para calcular uptime mensual desde logs de Zabbix

#!/bin/bash
# calculate_uptime.sh

MONTH="2026-03"
TOTAL_MINUTES=$(date -d "$MONTH-01 + 1 month - 1 day" +%s | awk '{print $1/60}')

# Sumar minutos caídos desde base de datos de Zabbix
DOWNTIME_MINUTES=$(mysql -u zabbix -p'password' zabbix -e "
  SELECT SUM(TIMESTAMPDIFF(MINUTE, clock_start, clock_end)) 
  FROM alerts 
  WHERE hostname='gateway-principal' 
    AND severity >= 4 
    AND DATE_FORMAT(FROM_UNIXTIME(clock_start), '%Y-%m') = '$MONTH';
" | tail -1)

# Calcular disponibilidad
UPTIME=$(echo "scale=4; (($TOTAL_MINUTES - $DOWNTIME_MINUTES) / $TOTAL_MINUTES) * 100" | bc)

echo "Mes: $MONTH"
echo "Total minutos: $TOTAL_MINUTES"
echo "Minutos caídos: $DOWNTIME_MINUTES"
echo "Disponibilidad: $UPTIME%"

# Comparar con SLO
SLO=99.9
if (( $(echo "$UPTIME >= $SLO" | bc -l) )); then
  echo "✅ SLO CUMPLIDO (objetivo: $SLO%)"
else
  echo "❌ SLO INCUMPLIDO (objetivo: $SLO%)"
  PENALTY=$(echo "scale=2; ($SLO - $UPTIME) * 50" | bc)
  echo "⚠️ Penalización aproximada: $PENALTY%"
fi
```

**Cálculo de Downtime Permitido por Nivel de Disponibilidad:**

| **Disponibilidad** | **Downtime Anual** | **Downtime Mensual** | **Downtime Semanal** | **Downtime Diario** |
|--------------------|--------------------|----------------------|----------------------|---------------------|
| 90% (un nueve) | 36.5 días | 72 horas | 16.8 horas | 2.4 horas |
| 99% (dos nueves) | 3.65 días | 7.2 horas | 1.68 horas | 14.4 minutos |
| 99.9% (tres nueves) | 8.76 horas | 43.2 minutos | 10.1 minutos | 1.44 minutos |
| 99.99% (cuatro nueves) | 52.6 minutos | 4.32 minutos | 1.01 minutos | 8.64 segundos |
| 99.999% (cinco nueves) | 5.26 minutos | 25.9 segundos | 6.05 segundos | 0.86 segundos |

**⚠️ Importante:** Cada "nueve" adicional incrementa costos exponencialmente (redundancia, personal 24/7, etc.)

### **C - Configuración (Configuration Management)**

| **Métrica SLO** | **Objetivo Típico** | **SLI (Cómo se mide)** | **Herramienta** |
|-----------------|---------------------|------------------------|-----------------|
| **Tasa de éxito de cambios** | ≥ 95% | `(Cambios exitosos / Total cambios) × 100` | Sistema de cambios |
| **Tiempo de implementación** | < 30 min (cambio estándar) | Duración promedio de cambios | Tickets + Git logs |
| **Backups exitosos** | 100% | `(Backups OK / Total backups) × 100` | RANCID, Oxidized |
| **Configuraciones auditadas** | 100% de dispositivos | `(Devices con backup / Total devices) × 100` | NetBox, RANCID |

**Ejemplo de medición de tasa de éxito de cambios:**
```python
# analyze_changes.py - Analiza éxito de cambios desde GitLab

import requests
import json
from datetime import datetime, timedelta

GITLAB_URL = "https://gitlab.empresa.com"
PROJECT_ID = 123
TOKEN = "glpat-xxxxxxxxxxxx"

headers = {"PRIVATE-TOKEN": TOKEN}

# Obtener cambios del último mes
since_date = (datetime.now() - timedelta(days=30)).isoformat()
url = f"{GITLAB_URL}/api/v4/projects/{PROJECT_ID}/merge_requests"
params = {"state": "merged", "created_after": since_date}

response = requests.get(url, headers=headers, params=params)
merge_requests = response.json()

total_changes = len(merge_requests)
successful_changes = 0

for mr in merge_requests:
    # Verificar si tuvo rollback en las siguientes 24h
    labels = mr.get("labels", [])
    if "rollback" not in labels:
        successful_changes += 1

success_rate = (successful_changes / total_changes) * 100

print(f"📊 Reporte de Cambios - Último mes")
print(f"Total cambios: {total_changes}")
print(f"Cambios exitosos: {successful_changes}")
print(f"Tasa de éxito: {success_rate:.2f}%")

if success_rate >= 95:
    print("✅ SLO CUMPLIDO (objetivo: ≥95%)")
else:
    print(f"❌ SLO INCUMPLIDO (objetivo: ≥95%)")
    print(f"⚠️ Mejora necesaria: {95 - success_rate:.2f}%")
```

### **A - Contabilidad (Accounting Management)**

| **Métrica SLO** | **Objetivo Típico** | **SLI (Cómo se mide)** | **Herramienta** |
|-----------------|---------------------|------------------------|-----------------|
| **Uso de ancho de banda** | 60-80% de capacidad | `(Tráfico promedio / Capacidad total) × 100` | NetFlow, sFlow |
| **Costo por usuario** | < $50/mes | `Costo total / Número de usuarios` | Sistema financiero |
| **Precisión de facturación** | ≥ 99% | `(Facturas correctas / Total facturas) × 100` | ERP + monitoreo |
| **Utilización de recursos** | 70-85% (óptimo) | `(Recursos usados / Recursos disponibles) × 100` | SNMP, Zabbix |

**Ejemplo de medición de uso de ancho de banda:**
```bash
# bandwidth_usage.sh - Mide uso de ancho de banda desde NetFlow

#!/bin/bash

INTERFACE="GigabitEthernet0/0"
CAPACITY_MBPS=1000  # 1 Gbps

# Consultar tráfico promedio del último mes usando nfdump
TRAFFIC_MBPS=$(nfdump -R /var/nfsen/profiles-data/live/router1 \
  -n 1 \
  -s srcip/bytes \
  -t $(date -d '30 days ago' +%Y/%m/%d.%H:%M) - $(date +%Y/%m/%d.%H:%M) \
  | awk '/Total/ {print $3/1000000/2592000*8}')  # Convertir a Mbps

USAGE_PERCENT=$(echo "scale=2; ($TRAFFIC_MBPS / $CAPACITY_MBPS) * 100" | bc)

echo "📊 Uso de Ancho de Banda - Último mes"
echo "Interfaz: $INTERFACE"
echo "Capacidad: $CAPACITY_MBPS Mbps"
echo "Tráfico promedio: $TRAFFIC_MBPS Mbps"
echo "Uso: $USAGE_PERCENT%"

if (( $(echo "$USAGE_PERCENT >= 60 && $USAGE_PERCENT <= 80" | bc -l) )); then
  echo "✅ SLO CUMPLIDO (rango óptimo: 60-80%)"
elif (( $(echo "$USAGE_PERCENT > 80" | bc -l) )); then
  echo "⚠️ ALERTA: Uso excesivo, considerar upgrade"
else
  echo "ℹ️ Uso bajo capacidad, recursos subutilizados"
fi
```

### **P - Desempeño (Performance Management)**

| **Métrica SLO** | **Objetivo Típico** | **SLI (Cómo se mide)** | **Herramienta** |
|-----------------|---------------------|------------------------|-----------------|
| **Latencia** | < 50 ms (promedio) | Tiempo de RTT (Round Trip Time) | Smokeping, PRTG |
| **Jitter** | < 10 ms | Variación en latencia | Monitoreo VoIP |
| **Packet Loss** | < 0.1% | `(Paquetes perdidos / Total paquetes) × 100` | SNMP, Zabbix |
| **Throughput** | ≥ 95% de capacidad | Velocidad real vs teórica | Speedtest, iPerf |
| **Tiempo de respuesta** | < 200 ms (aplicaciones web) | Tiempo desde request hasta response | APM tools |

**Ejemplo de medición de latencia:**
```python
#!/usr/bin/env python3
# latency_monitor.py - Monitorea latencia a múltiples destinos

import subprocess
import re
import time
from datetime import datetime

TARGETS = {
    "Google DNS": "8.8.8.8",
    "Cloudflare DNS": "1.1.1.1",
    "Gateway Sucursal 1": "10.20.1.1",
    "Gateway Sucursal 2": "10.20.2.1"
}

SLO_LATENCY = 50  # ms

def ping_host(ip):
    """Hace ping y retorna latencia promedio"""
    try:
        output = subprocess.check_output(
            f"ping -c 10 {ip}", 
            shell=True, 
            stderr=subprocess.STDOUT,
            timeout=15
        ).decode()
        
        # Extraer latencia promedio
        match = re.search(r'avg = ([\d.]+)', output)
        if match:
            return float(match.group(1))
    except:
        return None
    
print(f"📊 Reporte de Latencia - {datetime.now().strftime('%Y-%m-%d %H:%M')}")
print(f"SLO objetivo: < {SLO_LATENCY} ms\n")

violations = 0

for name, ip in TARGETS.items():
    latency = ping_host(ip)
    if latency:
        status = "✅" if latency < SLO_LATENCY else "❌"
        print(f"{status} {name:20} ({ip:15}): {latency:6.2f} ms")
        if latency >= SLO_LATENCY:
            violations += 1
    else:
        print(f"❌ {name:20} ({ip:15}): UNREACHABLE")
        violations += 1

print(f"\n{'='*60}")
if violations == 0:
    print("✅ Todos los destinos dentro del SLO")
else:
    print(f"⚠️ {violations}/{len(TARGETS)} destinos fuera del SLO")
```

**Percentiles en SLOs (concepto avanzado):**

En lugar de usar promedios (que pueden ocultar problemas), usar **percentiles**:

```
Latencia promedio: 45ms ✅ Cumple SLO <50ms

Pero al analizar percentiles:
  P50 (mediana): 40ms ✅
  P95: 120ms ❌ (5% de usuarios experimentan latencia alta)
  P99: 280ms ❌ (1% con latencia inaceptable)

SLO mejorado:
  ✅ Latencia promedio < 50ms
  ✅ Latencia P95 < 100ms
  ✅ Latencia P99 < 200ms
```

### **S - Seguridad (Security Management)**

| **Métrica SLO** | **Objetivo Típico** | **SLI (Cómo se mide)** | **Herramienta** |
|-----------------|---------------------|------------------------|-----------------|
| **Tiempo de respuesta a incidentes** | < 30 min (críticos) | Tiempo desde detección hasta respuesta | SIEM, SOC |
| **Vulnerabilidades críticas** | 0 abiertas > 7 días | Cantidad sin parche/mitigación | Nessus, Qualys |
| **Intentos de intrusión bloqueados** | ≥ 99.9% | `(Intentos bloqueados / Total intentos) × 100` | Firewall, IPS |
| **Cumplimiento de políticas** | 100% | % de dispositivos con políticas aplicadas | NAC, 802.1X |
| **Backups encriptados** | 100% | % de backups con encriptación | Backup software |

**Ejemplo de medición de tiempo de respuesta a incidentes:**
```sql
-- Query para calcular MTTR de incidentes de seguridad desde sistema SIEM

SELECT 
    DATE_FORMAT(detected_at, '%Y-%m') AS month,
    COUNT(*) AS total_incidents,
    AVG(TIMESTAMPDIFF(MINUTE, detected_at, responded_at)) AS avg_response_time_minutes,
    MAX(TIMESTAMPDIFF(MINUTE, detected_at, responded_at)) AS max_response_time_minutes,
    CASE 
        WHEN AVG(TIMESTAMPDIFF(MINUTE, detected_at, responded_at)) < 30 
        THEN '✅ SLO Cumplido' 
        ELSE '❌ SLO Incumplido' 
    END AS slo_status
FROM 
    security_incidents
WHERE 
    severity = 'CRITICAL'
    AND detected_at >= DATE_SUB(NOW(), INTERVAL 3 MONTH)
GROUP BY 
    DATE_FORMAT(detected_at, '%Y-%m')
ORDER BY 
    month DESC;

-- Resultado ejemplo:
-- +----------+-----------------+-------------------------+-------------------------+-----------------+
-- | month    | total_incidents | avg_response_time_min   | max_response_time_min   | slo_status      |
-- +----------+-----------------+-------------------------+-------------------------+-----------------+
```

## 📋 Tipos de SLA

Existen diferentes enfoques para estructurar SLAs según la organización:

### **1. SLA Basado en Cliente (Customer-Based SLA)**

Un acuerdo único que cubre **todos los servicios** para un cliente específico.

```
📄 SLA: Departamento de Ventas

Cliente: Departamento de Ventas
Servicios incluidos:
  ✅ Internet corporativo
  ✅ VPN para vendedores remotos
  ✅ Acceso a CRM (Salesforce)
  ✅ Telefonía IP (extensiones 5XXX)
  ✅ Correo electrónico corporativo

SLOs generales:
  - Disponibilidad: 99.9% en horario laboral
  - Soporte: 24/7 para P1, L-V 8-18h para P2-P4
  - MTTR: < 2h para P1, < 8h para P2

Ventajas:
  ✅ Relación simplificada (un solo documento)
  ✅ Negociación más fácil (interlocutor único)
  ✅ Visión holística del servicio al departamento

Desventajas:
  ❌ SLOs genéricos pueden no ajustarse a cada servicio
  ❌ Difícil optimizar por servicio individual
```

### **2. SLA Basado en Servicio (Service-Based SLA)**

Un acuerdo específico para **un solo servicio**, aplicable a **todos los clientes**.

```
📄 SLA: Servicio de VPN Corporativa

Servicio: Acceso VPN SSL (Cisco AnyConnect)
Clientes: Todos los departamentos con usuarios remotos

SLOs específicos:
  - Disponibilidad de servidores VPN: 99.95%
  - Capacidad mínima: 500 usuarios simultáneos
  - Latencia adicional por VPN: < 20ms
  - Throughput mínimo por usuario: 50 Mbps
  - Tiempo de autenticación: < 5 segundos
  - Soporte: 24/7 para incidentes de conectividad

Exclusiones:
  ❌ Velocidad de internet en ubicación del usuario
  ❌ Problemas de firewall local del usuario
  ❌ Aplicaciones lentas (problema de la app, no VPN)

Ventajas:
  ✅ SLOs optimizados para el servicio específico
  ✅ Métricas técnicas precisas y medibles
  ✅ Más fácil gestionar cambios (un solo servicio)

Desventajas:
  ❌ Múltiples SLAs por cliente (complejidad administrativa)
  ❌ Posible fragmentación de responsabilidades
```

### **3. SLA Multinivel (Multi-Level SLA)**

Combinación de SLAs a nivel **corporativo**, **cliente** y **servicio**.

```
┌─────────────────────────────────────────────────────────────┐
│ NIVEL 1: SLA Corporativo                                    │
│ Aplica a TODA la organización                               │
│                                                              │
│ SLOs generales:                                             │
│   - Disponibilidad mínima de infraestructura crítica: 99.9% │
│   - Horario de soporte: 24/7 para servicios críticos        │
│   - Reporte mensual de cumplimiento obligatorio             │
└──────────────┬──────────────────────────────────────────────┘
               │
               ├── 📄 NIVEL 2: SLA por Cliente (Ventas)
               │   │
               │   ├── Disponibilidad: 99.9% en horario 7-22h
               │   ├── MTTR: < 2h para P1
               │   └── Contacto: Ana Rodríguez (ext. 5678)
               │
               ├── 📄 NIVEL 2: SLA por Cliente (Finanzas)
               │   │
               │   ├── Disponibilidad: 99.99% (más crítico)
               │   ├── MTTR: < 1h para P1
               │   └── Contacto: Luis Gómez (ext. 7890)
               │
               └── 📄 NIVEL 3: SLA por Servicio
                   │
                   ├── SLA-VPN: 99.95% uptime, latencia <20ms
                   ├── SLA-Internet: 99.9% uptime, throughput ≥950Mbps
                   └── SLA-VoIP: Jitter <10ms, packet loss <0.05%

Ventajas:
  ✅ Flexibilidad máxima (ajustar a diferentes necesidades)
  ✅ Cobertura completa (corporativo + específico)
  ✅ Escalabilidad (fácil agregar servicios/clientes)

Desventajas:
  ❌ Complejidad administrativa (múltiples documentos)
  ❌ Riesgo de conflictos entre niveles
  ❌ Requiere gobernanza clara
```

**Ejemplo de jerarquía en caso de conflicto:**

```
Conflicto: Usuario de Ventas reporta lentitud en VPN

SLA Nivel 1 (Corporativo): MTTR < 4h para P2
SLA Nivel 2 (Cliente Ventas): MTTR < 2h para P2
SLA Nivel 3 (Servicio VPN): MTTR < 3h para P2

Resolución: Aplica el SLO MÁS RESTRICTIVO
  ➜ MTTR < 2h (del SLA de Cliente)

Regla general: El nivel más bajo/específico prevalece
```

## 🎯 Diseño de SLOs Efectivos

### **Principios SMART para SLOs**

| **Característica** | **Descripción** | **Ejemplo Malo ❌** | **Ejemplo Bueno ✅** |
|--------------------|-----------------|---------------------|----------------------|
| **S**pecific (Específico) | Debe ser claro y sin ambigüedades | "Red rápida" | "Latencia promedio < 50ms" |
| **M**easurable (Medible) | Debe poder cuantificarse | "Buena disponibilidad" | "Disponibilidad ≥ 99.9%" |
| **A**chievable (Alcanzable) | Realista con recursos actuales | "100% uptime" (imposible) | "99.95% uptime" |
| **R**elevant (Relevante) | Alineado con necesidades del negocio | "Latencia a la Luna" | "Latencia a servidores Office 365" |
| **T**ime-bound (Temporal) | Con periodo de medición definido | "Siempre rápido" | "Latencia < 50ms mensual" |

### **Error Budgets (Presupuesto de Errores)**

Concepto popularizado por Google SRE: **Cantidad de downtime permitido** sin incumplir SLO.

```
Cálculo de Error Budget:

SLO: 99.9% de disponibilidad mensual
Total minutos en mes (30 días): 43,200

Error Budget = 43,200 × (100% - 99.9%) / 100
             = 43,200 × 0.1%
             = 43.2 minutos/mes

Uso del Error Budget:

Semana 1: Incidente de 15 minutos → Budget restante: 28.2 min
Semana 2: Sin incidentes → Budget restante: 28.2 min
Semana 3: Incidente de 20 minutos → Budget restante: 8.2 min
Semana 4: Incidente de 10 minutos → ❌ BUDGET AGOTADO (-1.8 min)
  ➜ SLO INCUMPLIDO

Decisiones basadas en Error Budget:
  ✅ Budget > 50%: OK para cambios no urgentes
  ⚠️ Budget 20-50%: Solo cambios importantes
  ❌ Budget < 20%: FREEZE, solo urgencias críticas
```

### **SLOs Aspiracionales vs Contractuales**

```
SLO Contractual (en SLA formal):
  - Disponibilidad ≥ 99.9%
  - Con penalización si se incumple
  - Conservador (alcanzable con recursos actuales)

SLO Aspiracional (objetivo interno):
  - Disponibilidad ≥ 99.95%
  - Sin penalización (meta de mejora continua)
  - Ambicioso (requiere inversión/optimización)

Ejemplo:
  SLA dice: "99.9% mensual" (contractual)
  Equipo busca: "99.95% mensual" (aspiracional)
  
  Si logra 99.92%:
    ✅ Cumple con cliente (no penalización)
    ❌ No alcanza meta interna (oportunidad de mejora)
```

```javascript
// Business Rule en ServiceNow para auto-calcular cumplimiento SLA

(function executeRule(current, previous /*null when async*/) {
    
    // Obtener SLA definido para esta categoría de incidente
    var slaGR = new GlideRecord('sla_definition');
    slaGR.addQuery('name', 'MTTR - Incidentes P1');
    slaGR.query();
    
    if (slaGR.next()) {
        var sloMinutes = slaGR.getValue('duration'); // 120 minutos (2 horas)
        
        // Calcular tiempo real de resolución
        var createdTime = new GlideDateTime(current.opened_at);
        var resolvedTime = new GlideDateTime(current.resolved_at);
        var actualMinutes = gs.dateDiff(createdTime, resolvedTime, true) / 60;
        
        // Determinar cumplimiento
        if (actualMinutes <= sloMinutes) {
            current.slo_compliance = 'Met';
            current.slo_status = '✅ Cumplido (' + actualMinutes + ' min)';
        } else {
            current.slo_compliance = 'Violated';
            current.slo_status = '❌ Incumplido (' + actualMinutes + ' min vs ' + sloMinutes + ' objetivo)';
            
            // Crear tarea de análisis post-mortem
            var pmGR = new GlideRecord('post_mortem');
            pmGR.initialize();
            pmGR.incident = current.sys_id;
            pmGR.reason = 'SLO violation - MTTR exceeded by ' + (actualMinutes - sloMinutes) + ' minutes';
            pmGR.insert();
        }
        
        current.update();
    }
    
})(current, previous);
```

**Script para throughput con Speedtest:**

```bash
#!/bin/bash
# /usr/local/bin/speedtest_sla.sh
# Mide throughput y envía a Zabbix

# Instalar speedtest-cli si no existe
if ! command -v speedtest-cli &> /dev/null; then
    pip3 install speedtest-cli
fi

# Ejecutar test
RESULT=$(speedtest-cli --simple)

PING=$(echo "$RESULT" | grep Ping | awk '{print $2}')
DOWNLOAD=$(echo "$RESULT" | grep Download | awk '{print $2}')
UPLOAD=$(echo "$RESULT" | grep Upload | awk '{print $2}')

# Enviar a Zabbix
zabbix_sender -z zabbix-server -s "Internet Gateway" -k speedtest.ping -o "$PING"
zabbix_sender -z zabbix-server -s "Internet Gateway" -k speedtest.download -o "$DOWNLOAD"
zabbix_sender -z zabbix-server -s "Internet Gateway" -k speedtest.upload -o "$UPLOAD"

# Verificar cumplimiento de SLO
SLO_DOWNLOAD=950

if (( $(echo "$DOWNLOAD < $SLO_DOWNLOAD" | bc -l) )); then
    echo "❌ SLO VIOLATION: Throughput $DOWNLOAD Mbps < $SLO_DOWNLOAD Mbps"
    # Enviar alerta crítica
    zabbix_sender -z zabbix-server -s "Internet Gateway" -k slo.throughput.violation -o "1"
else
    echo "✅ SLO OK: Throughput $DOWNLOAD Mbps ≥ $SLO_DOWNLOAD Mbps"
    zabbix_sender -z zabbix-server -s "Internet Gateway" -k slo.throughput.violation -o "0"
fi
```

```python
#!/usr/bin/env python3
# /usr/local/bin/generate_sla_report.py

import pymysql
from datetime import datetime, timedelta
import matplotlib.pyplot as plt
from fpdf import FPDF

# Conexión a Zabbix DB
db = pymysql.connect(
    host='zabbix-db',
    user='zabbix',
    password='password',
    database='zabbix'
)

cursor = db.cursor()

# Periodo del reporte (mes anterior)
end_date = datetime.now().replace(day=1) - timedelta(days=1)
start_date = end_date.replace(day=1)

print(f"📊 Generando reporte SLA para: {start_date.strftime('%B %Y')}")

# 1. Calcular disponibilidad
query_uptime = """
SELECT 
    ROUND(100 * (1 - (SUM(duration) / (TIMESTAMPDIFF(SECOND, %s, %s)))), 4) as uptime_percent,
    SUM(duration)/60 as downtime_minutes
FROM 
    events e
    JOIN triggers t ON e.objectid = t.triggerid
WHERE 
    t.description LIKE '%%Internet CAÍDO%%'
    AND e.clock BETWEEN UNIX_TIMESTAMP(%s) AND UNIX_TIMESTAMP(%s)
"""

cursor.execute(query_uptime, (start_date, end_date, start_date, end_date))
uptime_data = cursor.fetchone()
uptime_percent = uptime_data[0] if uptime_data[0] else 100.0
downtime_minutes = uptime_data[1] if uptime_data[1] else 0.0

# 2. Calcular latencia promedio
query_latency = """
SELECT AVG(value) as avg_latency
FROM history
WHERE itemid = (SELECT itemid FROM items WHERE key_ = 'icmppingsec[8.8.8.8]')
  AND clock BETWEEN UNIX_TIMESTAMP(%s) AND UNIX_TIMESTAMP(%s)
"""

cursor.execute(query_latency, (start_date, end_date))
avg_latency = cursor.fetchone()[0] * 1000  # Convertir a ms

# 3. Generar PDF
class SLA_PDF(FPDF):
    def header(self):
        self.set_font('Arial', 'B', 15)
        self.cell(0, 10, 'REPORTE MENSUAL DE SLA - INTERNET CORPORATIVO', 0, 1, 'C')
        self.ln(10)
    
    def footer(self):
        self.set_y(-15)
        self.set_font('Arial', 'I', 8)
        self.cell(0, 10, f'Página {self.page_no()}', 0, 0, 'C')

pdf = SLA_PDF()
pdf.add_page()

# Resumen ejecutivo
pdf.set_font('Arial', 'B', 14)
pdf.cell(0, 10, 'RESUMEN EJECUTIVO', 0, 1)
pdf.ln(5)

pdf.set_font('Arial', '', 12)
pdf.cell(0, 8, f"Periodo: {start_date.strftime('%d/%m/%Y')} - {end_date.strftime('%d/%m/%Y')}", 0, 1)
pdf.ln(5)

# Tabla de SLOs
slo_status = "✅ CUMPLIDO" if uptime_percent >= 99.9 else "❌ INCUMPLIDO"
latency_status = "✅ CUMPLIDO" if avg_latency < 50 else "❌ INCUMPLIDO"

pdf.set_font('Arial', 'B', 12)
pdf.cell(80, 10, 'Métrica', 1)
pdf.cell(40, 10, 'Objetivo', 1)
pdf.cell(40, 10, 'Resultado', 1)
pdf.cell(30, 10, 'Estado', 1)
pdf.ln()

pdf.set_font('Arial', '', 12)
pdf.cell(80, 10, 'Disponibilidad', 1)
pdf.cell(40, 10, '>= 99.9%', 1)
pdf.cell(40, 10, f'{uptime_percent}%', 1)
pdf.cell(30, 10, slo_status, 1)
pdf.ln()

pdf.cell(80, 10, 'Latencia Promedio', 1)
pdf.cell(40, 10, '< 50 ms', 1)
pdf.cell(40, 10, f'{avg_latency:.2f} ms', 1)
pdf.cell(30, 10, latency_status, 1)
pdf.ln(15)

# Calcular penalizaciones
if uptime_percent < 99.9:
    if uptime_percent >= 99.0:
        penalty = 5
    elif uptime_percent >= 98.0:
        penalty = 10
    elif uptime_percent >= 95.0:
        penalty = 25
    else:
        penalty = 50
    
    pdf.set_font('Arial', 'B', 12)
    pdf.set_text_color(255, 0, 0)
    pdf.cell(0, 10, f'PENALIZACIÓN APLICABLE: {penalty}% (${15000 * penalty / 100:.2f})', 0, 1)
    pdf.set_text_color(0, 0, 0)
else:
    pdf.set_font('Arial', 'B', 12)
    pdf.set_text_color(0, 128, 0)
    pdf.cell(0, 10, 'SIN PENALIZACIONES - TODOS LOS SLOs CUMPLIDOS', 0, 1)
    pdf.set_text_color(0, 0, 0)

# Guardar PDF
filename = f'/var/reports/SLA_Internet_{start_date.strftime("%Y%m")}.pdf'
pdf.output(filename)

print(f"✅ Reporte generado: {filename}")
print(f"📊 Disponibilidad: {uptime_percent}% {slo_status}")
print(f"📊 Latencia: {avg_latency:.2f}ms {latency_status}")

db.close()
```

## 🎓 Mejores Prácticas

### **DO's (Hacer) ✅**

1. **Definir SLOs medibles y objetivos**
   ```
   ✅ "Disponibilidad ≥ 99.9%"
   ❌ "Alta disponibilidad"
   ```

2. **Usar percentiles además de promedios**
   ```
   ✅ "Latencia P95 < 100ms"
   ⚠️ "Latencia promedio < 50ms" (puede ocultar problemas)
   ```

3. **Establecer Error Budgets**
   ```
   Permite tomar decisiones informadas sobre cambios vs estabilidad
   ```

4. **Documentar exclusiones claramente**
   ```
   ⚠️ Mantenimientos planificados
   ⚠️ Fallas de terceros fuera de control
   ⚠️ Force majeure (desastres naturales)
   ```

5. **Automatizar la medición**
   ```
   Monitoreo 24/7 sin intervención humana
   Reportes automáticos y consistentes
   ```

6. **Revisar y ajustar periódicamente**
   ```
   Reuniones trimestrales de revisión
   Ajustar SLOs según capacidad técnica y necesidades
   ```

### **DON'Ts (Evitar) ❌**

1. **SLOs imposibles de cumplir**
   ```
   ❌ "100% uptime" (irrealista)
   ✅ "99.95% uptime" (alcanzable con redundancia)
   ```

2. **Métricas vanidad sin valor de negocio**
   ```
   ❌ "CPU del router < 50%"
   ✅ "Latencia percibida por usuarios < 50ms"
   ```

3. **SLAs unilaterales sin consenso**
   ```
   ❌ TI define SLOs sin consultar al cliente
   ✅ Negociación conjunta de objetivos realistas
   ```

4. **Penalizaciones sin dientes**
   ```
   ❌ "Crédito del 1% por incumplimiento total"
   ✅ "Crédito del 50% por disponibilidad <95%"
   ```

5. **Falta de comunicación de cambios**
   ```
   ❌ Modificar SLA sin notificar
   ✅ Proceso formal de cambio con 30 días notice
   ```

6. **Ignorar el contexto del negocio**
   ```
   ❌ Mismo SLO para todos (email = ERP crítico)
   ✅ SLOs diferenciados por criticidad
   ```

## 📚 Resumen y Conclusiones

### **Puntos Clave**

1. **SLA ≠ SLO ≠ SLI**
   - SLA es el acuerdo formal
   - SLO es el objetivo específico
   - SLI es la métrica medida

2. **SMART es fundamental**
   - Específicos, Medibles, Alcanzables, Relevantes, Temporales

3. **Tipos de SLA:**
   - Basado en cliente: Un acuerdo, todos los servicios
   - Basado en servicio: Un servicio, todos los clientes
   - Multinivel: Combinación jerárquica

4. **Monitoreo automatizado es obligatorio**
   - Herramientas: Zabbix, Nagios, Prometheus, PRTG
   - Dashboards en tiempo real
   - Alertas proactivas

5. **Error Budget ayuda a tomar decisiones**
   - Balance entre innovación y estabilidad
   - Datos objetivos para freezes de cambios

6. **Comunicación y transparencia**
   - Reportes regulares
   - Dashboards públicos
   - Post-mortems de incidentes P1

### **Relación con FCAPS**

```
SLA define QUÉ debe lograrse
  ↓
FCAPS define CÓMO se logra
  ↓
F (Fallas) → Cumplir SLO de disponibilidad y MTTR
C (Configuración) → Cumplir SLO de éxito de cambios
A (Contabilidad) → Cumplir SLO de uso eficiente
P (Desempeño) → Cumplir SLO de latencia, throughput
S (Seguridad) → Cumplir SLO de tiempo de respuesta a incidentes
```

### **Siguientes Pasos**

Para implementar SLAs efectivamente en tu organización:

1. **Identificar stakeholders** y sus necesidades
2. **Evaluar capacidad técnica** actual
3. **Definir SLOs SMART** realistas
4. **Implementar monitoreo** automatizado
5. **Documentar SLA** formal con firmas
6. **Comunicar** a todos los involucrados
7. **Revisar trimestralmente** y ajustar
