
# Índices

Este documento introduce conceptos de índices en bases de datos (con foco en SQL Server) y ofrece recomendaciones, ejemplos y comandos para su planificación, creación y mantenimiento.

## Contenido

- Planeación de índices
- Cómo accede SQL Server a los datos (table scan vs. index seek)
- Heap vs. Índice clustered
- Índices nonclustered y únicos
- Diseño de índices: selectividad, columnas, INCLUDE y filtros
- FILLFACTOR, PAD_INDEX y fragmentación
- Mantenimiento: REBUILD / REORGANIZE
- Herramientas de diagnóstico (sys.indexes, sys.dm_db_index_physical_stats, sp_helpindex)

---

## 1. Planeación de índices

Antes de crear índices, responde:

- ¿Qué consultas son críticas (SELECT, JOIN, WHERE, ORDER BY, GROUP BY)?
- ¿Las consultas buscan rangos o valores puntuales?
- ¿La tabla se actualiza con frecuencia (OLTP) o es mayormente de lectura (OLAP)?
- ¿Qué columnas son pequeñas y estables (buenas candidatas para claves de índice)?

Crear índices sin planificación puede degradar el rendimiento de inserciones/actualizaciones y aumentar el espacio en disco.

---

## 2. Cómo accede SQL Server a los datos

- Table Scan: el motor recorre secuencialmente todas las páginas de la tabla; suele usarse cuando no hay índices adecuados o cuando se espera leer la mayoría de filas.
- Index Seek/Scan: el motor recorre las páginas de un índice (árbol B) para localizar las páginas de datos o filas que coinciden con la consulta, devolviendo sólo los datos necesarios.

Index seek es mucho más eficiente para selecciones puntuales o rangos estrechos; table scan puede ser más eficiente cuando se necesita la mayoría de las filas.

---

## 3. Heap vs. Índice clustered

### Heap

- Es una tabla sin índice clustered: las páginas de datos no tienen orden lógico.
- Ventajas: menos sobrecarga para inserciones masivas si no hay índices que mantener.
- Cuando usarlo: tablas pequeñas, cargas por lotes donde las búsquedas son pocas o cuando las filas se insertan y eliminan muy frecuentemente (aunque esto puede causar fragmentación y forwards).

Ejemplo: tabla en heap

```sql
CREATE TABLE dbo.log_tmp (
  id INT,
  mensaje NVARCHAR(4000)
);
```

### Índice Clustered

- Determina el orden físico de las filas en disco. Sólo puede haber un índice clustered por tabla.
- Buena elección cuando las consultas realizan búsquedas por rangos o cuando se requiere orden físico (por ejemplo consultas por rango de fechas).
- No es buena opción cuando la columna de la clave cambia con frecuencia o es muy grande.

Ejemplo: crear índice clustered

```sql
CREATE CLUSTERED INDEX ix_persona_fecha ON dbo.persona(fecha_registro);
```

## 4. Índice Nonclustered

- Estructura B-tree que contiene claves de índice y punteros (row locator) a las filas del heap o al clustered index.
- Se pueden crear múltiples índices nonclustered por tabla (el límite depende de la versión; consulte la documentación de su SGBD).

Características y recomendaciones:
- Buen candidato cuando la columna tiene alta selectividad (valores raros) — consultas puntuales.
- Útil para acelerar JOIN, WHERE, ORDER BY y GROUP BY.
- Considere añadir columnas no clave con `INCLUDE` para crear índices cubrientes y evitar lookups.

Ejemplo: índice nonclustered con INCLUDE (cobertura)

```sql
CREATE NONCLUSTERED INDEX ix_usuario_email
ON dbo.usuario(email)
INCLUDE (fecha_creacion, nombre);
```

---

## 5. Índices UNIQUE

- Garantizan unicidad de los valores en la(s) columna(s) indexada(s).
- Al crear un índice único sobre una tabla con datos existentes, el SGBD verifica la unicidad y fallará si hay duplicados; algunas opciones permiten controlar el comportamiento ante duplicados (p. ej. `IGNORE_DUP_KEY` en SQL Server).

Ejemplo:

```sql
CREATE UNIQUE INDEX ux_usuario_email ON dbo.usuario(email);
```

---

## 6. Diseño práctico de índices

- Selección de columnas: prefiera columnas pequeñas y con buena selectividad como primeras columnas de un índice.
- Orden de columnas en índices compuestos: colocar la columna con mayor selectividad al inicio suele ser beneficioso.
- Índices cubrientes: use `INCLUDE` para añadir columnas que aparecen en SELECT pero no en WHERE/ORDER BY, así se evita el lookup.
- Índices filtrados: crear índices con un WHERE para cubrir consultas frecuentes sobre un subconjunto (ej. WHERE activo = 1).

Ejemplo (índice filtrado):

```sql
CREATE NONCLUSTERED INDEX ix_orden_activas
ON dbo.orden (cliente_id)
WHERE estado = 'ACTIVA';
```

## 7. FILLFACTOR y PAD_INDEX

- `FILLFACTOR` define el porcentaje de llenado inicial de las páginas de índice (por ejemplo, 80 deja 20% libre) y ayuda a reducir page splits en entornos con muchas escrituras.
- Recomendación: para OLTP (muchas escrituras), usar un `FILLFACTOR` menor (p. ej. 70-90) para reducir splits; para OLAP/lecturas masivas, usar un `FILLFACTOR` más alto (cercano a 100) para densidad.
- `PAD_INDEX` controla el espacio libre en los niveles intermedios del índice y puede usarse junto con `FILLFACTOR`.

Ejemplo de creación con opciones:

```sql
CREATE INDEX ix_producto_nombre
ON dbo.producto (nombre)
WITH (FILLFACTOR = 80, PAD_INDEX = ON);
```

Nota: valores exactos dependen del patrón de carga; pruebe en staging.

## 8. Fragmentación y mantenimiento

- La fragmentación ocurre cuando las páginas físicas del índice no están contiguas o cuando hay espacio libre interno (fragmentación interna/externa).
- Herramientas para diagnosticar:
  - `sys.dm_db_index_physical_stats` para obtener `avg_fragmentation_in_percent`.
  - `sys.indexes` y `sys.partitions` para información estructural.

Consulta básica de fragmentación:

```sql
SELECT
  db_name() AS db,
  OBJECT_NAME(i.object_id) AS table_name,
  i.name AS index_name,
  ips.avg_fragmentation_in_percent
FROM sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'LIMITED') ips
JOIN sys.indexes i ON ips.object_id = i.object_id AND ips.index_id = i.index_id
WHERE i.index_id > 0;
```

### REORGANIZE vs REBUILD

- `ALTER INDEX ... REORGANIZE`: operación más ligera, hace reordenamiento de páginas y es online (no bloquea lecturas); útil para fragmentación baja a moderada.
- `ALTER INDEX ... REBUILD`: reconstruye completamente el índice, elimina la fragmentación y actualiza estadísticas; puede ser más costoso y puede requerir bloqueo o licencia empresarial para operación online.

Ejemplos:

```sql
ALTER INDEX ix_usuario_email ON dbo.usuario REORGANIZE;

ALTER INDEX ix_usuario_email ON dbo.usuario REBUILD WITH (FILLFACTOR = 80);
```

---

## 9. Métodos y vistas para obtener información de índices

- `sp_helpindex 'schema.table'` — antiguo procedimiento que muestra índices (útil para inspecciones rápidas).
- `sys.indexes`, `sys.index_columns`, `sys.dm_db_index_physical_stats` — vistas dinámicas recomendadas para diagnósticos y automatización.

Ejemplo rápido:

```sql
EXEC sp_helpindex 'dbo.usuario';

SELECT * FROM sys.indexes WHERE object_id = OBJECT_ID('dbo.usuario');
```

---

## 10. Buenas prácticas resumidas

- Planifique índices según las consultas críticas y el patrón de cargas.
- Evite índices innecesarios; cada índice penaliza escrituras.
- Use índices cubrientes (`INCLUDE`) para consultas que devuelven columnas adicionales y así evitar lookups.
- Monitoree fragmentación y programe mantenimiento (REORGANIZE/REBUILD) según thresholds (por ejemplo: REORGANIZE si fragmentación entre 5-30%; REBUILD si >30% — adapte estos umbrales a su entorno).
- Pruebe las decisiones en un entorno de staging y mida el impacto.
