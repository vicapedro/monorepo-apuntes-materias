## Tipos de Integridad de Datos

La integridad de datos es un principio fundamental en las bases de datos relacionales que garantiza la precisión, consistencia y confiabilidad de la información almacenada. Para mantener esta integridad, los sistemas de gestión de bases de datos implementan tres tipos principales de integridad:

### 1. Integridad de Dominio
**Definición:** Asegura que los valores en una columna cumplan con las reglas específicas definidas para ese campo o dominio de datos.

**Componentes clave:**
- **Selección adecuada del tipo de dato:** La elección correcta del tipo de dato es fundamental para la integridad de dominio. Por ejemplo:
  - Usar `INT` para identificadores numéricos en lugar de `VARCHAR`
  - Elegir `DECIMAL(10,2)` para monedas en lugar de `FLOAT` (evita problemas de precisión)
  - Seleccionar `NVARCHAR` para textos con caracteres internacionales
  - Aplicar `DATE` o `DATETIME2` para fechas según la precisión requerida

- **Restricciones de verificación (CHECK):** Limitan los valores permitidos
- **Valores por defecto (DEFAULT):** Establecen valores iniciales consistentes
- **Restricciones NOT NULL:** Previenen valores vacíos cuando no son permitidos

**Ejemplo práctico:**
```sql
CREATE TABLE Producto (
    ProductoID INT NOT NULL,                          -- Tipo correcto para ID
    Nombre NVARCHAR(100) NOT NULL,                    -- NVARCHAR para caracteres internacionales
    Precio DECIMAL(10,2) CHECK (Precio > 0),          -- DECIMAL para precisión monetaria
    Categoria VARCHAR(50) DEFAULT 'Sin categoría',    -- DEFAULT para consistencia
    FechaCreacion DATETIME2 DEFAULT GETDATE()         -- DATETIME2 para precisión temporal
);
```

### 2. Integridad de Entidad
**Definición:** Garantiza que cada fila en una tabla sea única e identificable de manera inequívoca.

**Implementación:**
- **Claves primarias (PRIMARY KEY):** Identifican únicamente cada registro
- **Restricciones únicas (UNIQUE):** Previenen duplicados en campos específicos
- **Campos de identidad (IDENTITY/AUTO_INCREMENT):** Generan valores únicos automáticamente

**Principios:**
- Cada tabla debe tener una clave primaria
- Los valores de clave primaria no pueden ser NULL
- Los valores de clave primaria deben ser únicos en toda la tabla

### 3. Integridad Referencial
**Definición:** Mantiene la consistencia entre tablas relacionadas, asegurando que las referencias entre registros sean válidas.

**Implementación:**
- **Claves foráneas (FOREIGN KEY):** Establecen y mantienen relaciones entre tablas
- **Acciones referenciales:** Define qué sucede cuando se modifica o elimina un registro referenciado
  - `CASCADE`: Propaga cambios automáticamente
  - `RESTRICT/NO ACTION`: Previene cambios que violarían la integridad
  - `SET NULL/SET DEFAULT`: Establece valores alternativos

**Importancia de la combinación:**
Estos tres tipos de integridad trabajan en conjunto para crear un sistema robusto:
- La **integridad de dominio** asegura que los datos individuales sean válidos
- La **integridad de entidad** garantiza que cada registro sea identificable
- La **integridad referencial** mantiene la coherencia entre entidades relacionadas

> **💡 Nota importante:** Una selección inadecuada del tipo de dato no solo afecta el almacenamiento y rendimiento, sino que puede comprometer gravemente la integridad de dominio. Por ejemplo, almacenar fechas como `VARCHAR` impide validaciones temporales adecuadas y puede llevar a inconsistencias de datos.

## Introducción 

## 1. Mecanismos de integridad de datos

1. Integridad declarativa
	 - Definida y aplicada por el SGBD mediante constraints.
	 - Ventaja: el motor garantiza la coherencia sin lógica adicional en la aplicación.

2. Integridad procedural
	 - Definida mediante scripts, triggers y procedimientos almacenados.
	 - Útil para reglas complejas que no pueden expresarse con un CHECK o una FK.

> Determinar qué tipo usar: si la regla puede expresarse mediante un constraint, preferir la integridad declarativa. Use lógica procedural para reglas complejas, pero documente y pruebe bien.

---

## 2. Definiendo constraints

- Se definen con `CREATE TABLE` o `ALTER TABLE`.
- Se pueden agregar constraints a tablas con datos existentes (el SGBD verificará la condición, y fallará si hay violaciones).
- Constraints a nivel de columna (single-column) y a nivel de tabla (multi-column).

Ejemplos básicos:

```sql
-- Constraint a nivel de columna (DEFAULT y NOT NULL)
CREATE TABLE persona (
	id INT PRIMARY KEY,
	nombre VARCHAR(100) NOT NULL,
	pais VARCHAR(50) DEFAULT 'México'
);

-- Constraint a nivel de tabla (check sobre varias columnas)
CREATE TABLE pedido (
	id INT PRIMARY KEY,
	fecha_envio DATE,
	fecha_entrega DATE,
	CONSTRAINT chk_fechas CHECK (fecha_entrega >= fecha_envio)
);
```

**Consideraciones**:
- Los constraints pueden cambiarse con `ALTER TABLE` sin recrear la tabla (aunque algunas operaciones requieren bloqueo o revalidación).
- Las aplicaciones deben manejar errores de violación de constraints.
- Al añadir un constraint a una tabla con datos existentes, el SGBD verificará los datos y rechazará la operación si hay violaciones.

## 3. DEFAULT constraints

- Se aplican cuando se omite la columna en la cláusula `INSERT`.
- Un solo DEFAULT por columna.
- No tiene sentido usar DEFAULT en columnas `IDENTITY`, `ROWGUIDCOL` o `timestamp` en SQL Server.
- Un DEFAULT puede entrar en conflicto con un `CHECK`; el conflicto se detecta en tiempo de ejecución.

Ejemplo:

```sql
ALTER TABLE producto
	ADD precio DECIMAL(10,2) DEFAULT 0.00;

INSERT INTO producto (id, nombre) VALUES (1, 'Tornillo');
-- precio será 0.00 si no se especifica
```

Notas importantes y comportamiento:
- Si se elimina una columna que tenía un DEFAULT, el DEFAULT se elimina con la columna.
- `NULL` tiene prioridad: si se inserta explícitamente `NULL`, el DEFAULT no se aplica.
- SQL Server ofrece la opción `WITH VALUES` al agregar un DEFAULT para aplicar el valor por defecto a las filas existentes (ver `ALTER TABLE ... ADD CONSTRAINT ... WITH VALUES`).

---

## 4. CHECK constraints

- Se evalúan en operaciones `INSERT` y `UPDATE`.
- Pueden usar funciones del sistema (ej. `GETDATE()` en SQL Server) y expresiones que hagan referencia a varias columnas de la misma fila.
- No pueden contener subconsultas en la mayoría de SGBD.
- Restricciones típicas: rangos numéricos, formatos, condiciones entre columnas.

Ejemplo:

```sql
CREATE TABLE empleado (
	id INT PRIMARY KEY,
	salario DECIMAL(10,2),
	horas_semana INT,
	CONSTRAINT chk_salario CHECK (salario >= 0 AND horas_semana BETWEEN 0 AND 60)
);
```

Limitaciones comunes:
- No se usan con columnas `IDENTITY`, `timestamp` o `uniqueidentifier` en algunos SGBD.
- No permiten subconsultas en la expresión CHECK.

---

## 5. PRIMARY KEY

- Cada tabla puede tener sólo un `PRIMARY KEY` (pero puede ser compuesto: varias columnas).
- Los valores deben ser únicos y `NOT NULL`.
- El SGBD crea automáticamente un índice `UNIQUE` (por defecto `CLUSTERED` en muchos sistemas).
- Para eliminar el índice creado por una PK se debe usar `ALTER TABLE DROP CONSTRAINT <pk_name>` y no `DROP INDEX`.

Ejemplo:

```sql
ALTER TABLE cliente
	ADD CONSTRAINT pk_cliente PRIMARY KEY (id_cliente);
```

Notas:
- Aunque técnicamente se puede definir un DEFAULT sobre una columna PK, no suele tener sentido si la PK es manejada manualmente o es identidad.
- Si se añade una PK a una tabla con datos existentes, el SGBD verificará unicidad y no-null.

---

## 6. UNIQUE constraints

- Permiten `NULL` (comportamiento concreto depende del SGBD — SQL Server permite múltiples NULLs; Oracle trata NULLs diferente).
- Se pueden definir múltiples `UNIQUE` por tabla.
- Pueden aplicarse a una o más columnas.
- Generan índices (dependiendo del SGBD) para acelerar la búsqueda de duplicados.

Ejemplo:

```sql
CREATE TABLE usuario (
	id INT PRIMARY KEY,
	email VARCHAR(255),
	CONSTRAINT ux_usuario_email UNIQUE (email)
);
```

---

## 7. FOREIGN KEY (Integridad referencial)

- Una `FOREIGN KEY` debe referenciar una `PRIMARY KEY` o una `UNIQUE` en la tabla referenciada.
- Proporciona integridad referencial (evita referencias a filas inexistentes).
- Dependiendo del SGBD, la creación de FK no siempre crea índices automáticamente en la tabla referida (es recomendable crear índices para mejorar el rendimiento de las comprobaciones y joins).

Ejemplo:

```sql
CREATE TABLE orden (
	id INT PRIMARY KEY,
	cliente_id INT,
	CONSTRAINT fk_orden_cliente FOREIGN KEY (cliente_id) REFERENCES cliente(id_cliente)
);
```

Acciones ON DELETE / ON UPDATE:

```sql
CONSTRAINT fk_orden_cliente FOREIGN KEY (cliente_id)
	REFERENCES cliente(id_cliente)
	ON DELETE CASCADE
	ON UPDATE NO ACTION;
```

## 8. Desactivar/Validar constraints

- Para desactivar temporalmente la comprobación de algunas constraints (por ejemplo durante una carga masiva), en SQL Server se usa `WITH NOCHECK` al añadir o habilitar constraints, o `NOCHECK CONSTRAINT` para deshabilitarlas.

Ejemplo (SQL Server):

```sql
-- Deshabilitar comprobación de una FK
ALTER TABLE orden NOCHECK CONSTRAINT fk_orden_cliente;

-- Volver a habilitar y forzar verificación (puede fallar si hay datos inválidos)
ALTER TABLE orden WITH CHECK CHECK CONSTRAINT fk_orden_cliente;
```

---

## 9. Orden de comprobación de la integridad (general)

El orden típico en que un SGBD aplica comprobaciones durante una operación de inserción es:

1. Se aplican los valores por `DEFAULT`.
2. Se emiten violaciones `NOT NULL`.
3. Se evalúan las restricciones `CHECK`.
4. Se aplica la comprobación de `FOREIGN KEY` (dependiendo del SGBD y del orden de operaciones internas).
5. Se comprueban `UNIQUE` y `PRIMARY KEY`.
6. Se activan los `TRIGGERS`.

> Nota: el orden exacto puede variar entre SGBD; consulte la documentación específica del motor.

## 10. Tablas temporales

### Privadas (prefijo `#` en SQL Server)
- Se crean con un nombre que inicia por `#`.
- Sólo la conexión/usuario que crea la tabla puede acceder a ella.
- No se pueden conceder privilegios a otras conexiones.
- Pueden existir otras tablas con el mismo nombre en conexiones distintas (son independientes).
- Existen mientras la conexión que las creó esté abierta.

Ejemplo (SQL Server):

```sql
CREATE TABLE #temp_usuarios (id INT, nombre VARCHAR(100));
INSERT INTO #temp_usuarios VALUES (1,'Ana');
```

### Globales (prefijo `##` en SQL Server)
- Se crean con `##nombre` y son accesibles por otras conexiones.
- Persisten hasta que la conexión que las creó termina y no haya más usuarios usando la tabla.

Ejemplo (SQL Server):

```sql
CREATE TABLE ##global_temp (id INT, valor VARCHAR(50));
```

---

## 11. Recomendaciones y notas finales

- Prefiera constraints declarativos siempre que sea posible: son más fáciles de mantener y el SGBD optimiza su aplicación.
- Documente las reglas implementadas de forma procedural (triggers/procedures) para evitar comportamientos inesperados.
- Antes de añadir constraints a tablas con datos existentes, haga un respaldo y pruebe la verificación en un entorno de staging.
