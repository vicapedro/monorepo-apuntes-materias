# 1.3 Modelos de datos

Un modelo de datos es una representación abstracta que define cómo se organizan, almacenan y manipulan los datos en un sistema de gestión de bases de datos. A lo largo de la evolución de la informática, han surgido diferentes modelos, cada uno con características específicas que los hacen adecuados para diferentes tipos de aplicaciones y necesidades.

## 1.3.1 Evolución histórica de los modelos de datos

### Modelo Jerárquico
El modelo jerárquico fue uno de los primeros en utilizarse comercialmente, popularizado por el sistema IMS (Information Management System) de IBM en la década de 1960. En este modelo:
- Los datos se organizan en una estructura de árbol
- Cada registro tiene un único registro padre
- Las relaciones son de tipo padre-hijo (1:N)
- **Ventajas**: Eficiente para consultas que siguen la jerarquía, buena performance
- **Desventajas**: Inflexible, no maneja bien relaciones M:N, redundancia de datos

### Modelo de Red
Desarrollado por CODASYL (Conference on Data Systems Languages) en los años 70, el modelo de red:
- Permite que un registro tenga múltiples padres
- Utiliza punteros para conectar registros relacionados
- Más flexible que el modelo jerárquico
- **Ventajas**: Maneja relaciones M:N, menos redundancia que el jerárquico
- **Desventajas**: Complejidad en la programación, dependencia de la estructura física

## 1.3.2 El Modelo Relacional

Propuesto por Edgar F. Codd en 1970, el modelo relacional revolucionó el mundo de las bases de datos:

### Características fundamentales:
- **Simplicidad conceptual**: Los datos se representan como tablas (relaciones)
- **Independencia física**: Los programas no dependen de cómo se almacenan físicamente los datos
- **Lenguaje declarativo**: SQL permite especificar QUÉ se quiere, no CÓMO obtenerlo
- **Base matemática sólida**: Fundamentado en álgebra relacional y cálculo relacional
- **Normalización**: Técnicas para eliminar redundancia y anomalías

### Ventajas del modelo relacional:
- **Flexibilidad**: Fácil modificación de la estructura
- **Integridad**: Soporte robusto para restricciones de integridad
- **Independencia de datos**: Separación entre la vista lógica y física
- **Lenguaje estándar**: SQL es ampliamente conocido y estandarizado
- **ACID**: Garantiza propiedades de transacciones (Atomicidad, Consistencia, Aislamiento, Durabilidad)

## 1.3.3 Modelos de datos modernos

### Modelo Orientado a Objetos
Surgió en los años 80 para manejar datos complejos:
- **Características**: Encapsulación, herencia, polimorfismo
- **Uso típico**: Aplicaciones CAD/CAM, multimedia, sistemas complejos
- **Ejemplos**: ObjectDB, db4o
- **Limitaciones**: Menor adopción, falta de estándares consolidados

### Modelo Objeto-Relacional
Combina características de ambos modelos:
- **Extensiones al modelo relacional**: Tipos de datos definidos por usuario, métodos
- **Ejemplos**: PostgreSQL, Oracle, SQL Server (características avanzadas)
- **Ventaja**: Mantiene compatibilidad con SQL mientras añade capacidades orientadas a objetos

## 1.3.4 Bases de datos NoSQL

Con el crecimiento del big data y aplicaciones web masivas, surgieron modelos alternativos:

### Bases de datos de documentos
- **Estructura**: Almacenan documentos (JSON, XML, BSON)
- **Ejemplos**: MongoDB, CouchDB, Amazon DocumentDB
- **Casos de uso**: Aplicaciones web, gestión de contenido, catálogos de productos
- **Ventajas**: Esquema flexible, desarrollo ágil, manejo natural de datos semiestructurados

### Bases de datos clave-valor
- **Estructura**: Pares simples clave-valor
- **Ejemplos**: Redis, DynamoDB, Riak
- **Casos de uso**: Cachés, sesiones de usuario, configuraciones
- **Ventajas**: Muy alta performance, escalabilidad horizontal simple

### Bases de datos de grafos
- **Estructura**: Nodos y aristas para representar relaciones complejas
- **Ejemplos**: Neo4j, Amazon Neptune, ArangoDB
- **Casos de uso**: Redes sociales, detección de fraudes, motores de recomendación
- **Ventajas**: Consultas eficientes sobre relaciones complejas

### Bases de datos columnares
- **Estructura**: Datos organizados por columnas en lugar de filas
- **Ejemplos**: Cassandra, HBase, Google Bigtable
- **Casos de uso**: Análisis de big data, data warehousing
- **Ventajas**: Compresión eficiente, consultas analíticas rápidas

## 1.3.5 Bases de datos NewSQL

Intentan combinar lo mejor de SQL y NoSQL:
- **Características**: ACID + escalabilidad horizontal
- **Ejemplos**: Google Spanner, CockroachDB, VoltDB
- **Objetivo**: Mantener las garantías ACID mientras escalan horizontalmente

## 1.3.6 ¿Por qué seguir estudiando el modelo relacional?

A pesar de la proliferación de nuevos modelos, el modelo relacional sigue siendo fundamental por las siguientes razones:

### 1. **Fundamentos teóricos sólidos**
- **Base matemática**: Álgebra y cálculo relacional proporcionan fundamentos rigurosos
- **Comprensión universal**: Entender el modelo relacional facilita el aprendizaje de otros modelos
- **Principios aplicables**: Conceptos como normalización y integridad son transferibles

### 2. **Predominancia en el mercado empresarial**
- **Sistemas críticos**: La mayoría de sistemas empresariales críticos usan bases de datos relacionales
- **ERP y CRM**: Sistemas como SAP, Oracle ERP, Salesforce se basan en modelos relacionales
- **Sector financiero**: Bancos y sistemas financieros confían en las garantías ACID

### 3. **Madurez y estabilidad**
- **50+ años de evolución**: Décadas de optimizaciones y mejoras
- **Herramientas maduras**: Ecosistema completo de herramientas de desarrollo, administración y monitoreo
- **Conocimiento consolidado**: Abundante documentación, mejores prácticas y expertise disponible

### 4. **Garantías de consistencia**
- **ACID**: Transacciones confiables para aplicaciones críticas
- **Integridad referencial**: Garantías automáticas de consistencia de datos
- **Concurrencia**: Manejo maduro de acceso concurrente con diferentes niveles de aislamiento

### 5. **SQL como estándar**
- **Lenguaje universal**: SQL es conocido por millones de desarrolladores
- **Transferibilidad**: Conocimiento aplicable en múltiples sistemas
- **Evolución continua**: SQL sigue evolucionando (SQL:2016, SQL:2023)

### 6. **Integración con modelos modernos**
- **Bases de datos multimodelo**: PostgreSQL, Oracle, SQL Server incorporan capacidades NoSQL
- **SQL en big data**: Spark SQL, Presto, BigQuery traen SQL a ecosistemas de big data
- **NewSQL**: Mantienen interfaces SQL mientras añaden escalabilidad

## 1.3.7 Cuándo elegir cada modelo

### Usar modelo relacional cuando:
- Se requiere consistencia estricta (ACID)
- Los datos tienen estructura bien definida
- Se necesitan consultas complejas con JOINs
- El sistema maneja transacciones críticas
- Se requiere cumplimiento normativo estricto

### Considerar NoSQL cuando:
- **Documentos**: Datos semiestructurados, desarrollo ágil
- **Clave-valor**: Necesidades de cache, alta velocidad de acceso
- **Grafos**: Relaciones complejas, análisis de redes
- **Columnares**: Análisis de grandes volúmenes, data warehousing

### Considerar NewSQL cuando:
- Se necesita escalabilidad horizontal
- No se pueden comprometer las garantías ACID
- Se requiere distribución geográfica
- El volumen de transacciones es muy alto

## 1.3.8 Conclusión

El panorama actual de bases de datos es diverso y cada modelo tiene su lugar según los requisitos específicos. Sin embargo, el modelo relacional continúa siendo:

1. **La base conceptual** para entender otros modelos
2. **El estándar de facto** para aplicaciones empresariales
3. **El modelo más maduro** en términos de herramientas y conocimiento
4. **La opción más segura** para sistemas que requieren consistencia

El estudio del modelo relacional no solo proporciona habilidades inmediatamente aplicables, sino que también construye los fundamentos conceptuales necesarios para entender, evaluar y utilizar efectivamente cualquier tecnología de bases de datos, ya sea actual o futura.

En un mundo donde "no hay bala de plata", entender profundamente el modelo relacional permite tomar decisiones informadas sobre cuándo usarlo y cuándo considerar alternativas, maximizando así el valor de cualquier solución de datos implementada.
